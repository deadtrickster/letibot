### R1 P1 - Claude opus (`A5-r1-p1-opus.txt`)

```
A5 R1, position 1. Read at 9e9312b06, paths under crates/. No test run.

THESIS
A committed row is safe only after the store's shape is settled. Carve, migration and import each write the shape without holding the write lock across their own check, so a box-wide upgrade or a carve that runs while daemons are live can delete committed rows, wedge an open, or leave tables in the wrong file.

FINDINGS

1. HIGH - carve deletes rows committed after its check. `tokencore/src/migrate_split.rs:228-247` checks claims once. `:236` opens a raw `from`. The copy and `verify_chains` (`:272`) run with no lock. The deleting tx (`:274`, deferred) removes every row of the transcripts staged in `temp.mine_transcript` (`:648-652`, `:781-785`). A daemon of that key that starts in the window gets `open_transition`, which returns a set with no project file (`store/split.rs:584-585`), and appends to `sessions.db`. Scenario: a long copy, then a daemon resumes session S and appends seq 900-910. Carve commits, and 900-910 are deleted although they were committed. S's next append fails the trigger (`store.rs:539-545`, MAX(seq) is gone), so the session is wedged. Change: take BEGIN IMMEDIATE on `from` before staging and hold it to commit, or re-check claims and the per-transcript max(seq) inside the deleting tx and refuse if either moved.

2. HIGH - migration has no tx and no lock. `store.rs:1867-1874` runs `migrate_from`, then a DELETE and an INSERT on `schema_version`, each in autocommit. The arms check and then act (v51 at `:2690-2711`). Scenario: a box-wide restart, and two v51 daemons both read 50. One ALTER wins, and the other fails with "duplicate column" and does not open (daemon reaction HYP). Between the DELETE and the INSERT, `SELECT version` returns Ok(None). That is not "no such table", so a concurrent opener takes the fresh path (`:1890-1907`) and runs unfiltered `SCHEMA_SQL` into `shared.db` (transcript_item and its triggers, job, ...). An older build in the same gap stamps its own lower version. A crash in the gap leaves `schema_version` empty for good. Change: run migrate under BEGIN IMMEDIATE, re-read the version inside it, stamp with one UPDATE, and treat an empty `schema_version` in a file that has tables as corrupt, not fresh.

3. MEDIUM - unguarded arms leave project tables in shared.db. The split exists from v44 (`git show bdf15086d`). v47 `RECALL_SQL` and v50 `GRANTS_SQL` (`store.rs` arms `from < 47`, `from < 50`) run on every file. v51 then ALTERs the stray `session_grant` (`:2713-2720`). Every shared.db created at v44-49 holds an empty `recall_unit` and `session_grant`. On those files an unrouted read gets an empty result and an unrouted write lands in shared.db, where on a fresh file it would fail with "no such table". `an_older_set_migrates_both_files` (`store/split_tests.rs:449`) checks only the v48 tables. Change: guard both arms with `split::holds`, and assert after migration that each file's table set equals `tables_in(file)`.

4. MEDIUM - the coverage scan skips grants.rs. `store/split_coverage_tests.rs:13-31` SOURCES has no `grants.rs` (`mod grants`, `store.rs:36`). It is routed correctly today (`grants.rs:91` `at`, the rest through `exec`). A regression there fails neither the test nor production, because of #3. Change: derive SOURCES from the `mod` list, or assert that they match.

5. MEDIUM - `import_tx` commits two WAL files one after the other (`store/transfer.rs:312-338`, conceded at `:308-310`). Scenario: a crash after the project commit. The project rows have no index row, so `session(id)` is None (`:241`), the retry INSERTs collide on the transcript PK, and the import stays refused with orphan rows. Commit order is the project file first (HYP, SQLite attach order). Change: make the re-import detect and verify an orphan prefix, or write a pending marker in shared.db first and clear it last. The ATTACH is also a second connection to shared.db held at IMMEDIATE for the whole import. The process's own shared connection waits in `on_busy` for at most 5s (HYP).

6. LOW-MEDIUM - `letibot migrate` does not know about the split (`letibot/src/migrate.rs:1813`, `:2021`, `:664`). On a split box, `Store::open(sessions.db)` passes `refuse_creating_beside_legacy` (`store/split.rs:606-635`, dir=None), creates a full-schema stray `sessions.db` and finds no session. This adds to P7's XDG finding. Change: open through `StoreAt`/`open_set_existing`.

7. LOW - carve's raw `from` (`migrate_split.rs:236`) has no busy handler. Any write by another project's daemon refuses the carve, which contradicts the "other projects' daemons are not a reason to stop" message (`:245`). Change: `pragmas(&from)`.

CONCESSIONS
- R313 routing holds. I found no production `self.conn()` or `connection()` read of a project table. Every hit is a test.
- The arms after v44 that ALTER are guarded. No arm deletes transcript rows. The floor never goes down, so a version regression from #2 is recoverable.
- The fresh set path (`prepare`, `split.rs:692`) is filtered and stamped.

ANTICIPATED
- Position 2: WAL+FULL and the triggers protect against process death. #1 is the carve dropping the triggers and deleting while writers are live (`:313-351`). The coverage test runs on fresh files and cannot see #3.
- Position 3: agreed that carve-in-progress is the complexity, and #1 is where it fails. The simpler fix is one lock file that stops the key for the whole carve, not more state.
```

### R1 P2 - DeepSeek (`A5-r1-p2-deepseek.txt`)

```
[model: deepseek/deepseek-flash (the default; the one-shot ignored --model)]
THESIS: For the workload this box actually runs — one data directory, a handful of daemons, an additive schema bump every few days — the store's migration and durability machinery is sound, and its two load-bearing guards fail on the *class* of bug rather than on a list a hand keeps in step. Position 1's corruption story needs a path where an older reader silently misreads, or a migration half-lands. I traced both and could not find one: every skew path I found refuses by name.

1. The durability story is the floor, not `synchronous=FULL`. `store.rs:1608` only covers a commit that reaches disk; the interesting case is a daemon that outlives a migration. `open_newer` (`floor.rs:205-224`) opens a store ahead of this build when the floor allows it and refuses with the fix in the sentence when it does not (`tests.rs:3043`, `:3087` — fails closed when no floor was recorded). Better, the queue lease re-reads the version *inside its own transaction* (`queues.rs:1377-1379`, `stored_schema_version` `:783`), so a daemon already running learns about skew at the lease rather than at a failed write, and `LeaseOutcome::WrongSchema` is announced once and the lease not taken (`serve.rs:3717-3723`). Failure prevented: yesterday's daemon silently misreading a 51→52 bump. Severity: none — HOLDS. Missing test: a second process opening during a migration.

2. The untransacted migration is idempotent by construction, so the window is benign. `migrate` (`store.rs:1848`) runs arms outside a transaction and `DELETE FROM schema_version` (`:1870`) precedes its INSERT. I checked the consequence, not the comment: all 17 DDL statements in `SCHEMA_SQL` (`store.rs:227-545`) are `IF NOT EXISTS`, and the block holds no bare INSERT/UPDATE/DELETE. A crash there lands the store on the `None` arm (`:1892`) and `SCHEMA_SQL` (`:1894`), where every CREATE is a no-op — stamped at `SCHEMA_VERSION` with rows intact. Both recent arms re-check before ALTER (`:2617`, `:2622`). Severity low.

3. The split coverage test is a source scan with a transitive closure, which is why it catches what R313 was. `split_coverage_tests.rs:113-161` marks each fn naming a project table, closes over `self.`/`Self::`/`store.` calls (`:139-156`), then fails any public method in that set `EXERCISED` (`:164`) does not call (`:253-266`). A new unrouted method is red by construction. Gap: it sees no `tx.`/`conn.` and cannot see a `format!`ed table name. Proposed: add those patterns at `:145`.

4. Append-only is enforced *through* the one path that copies rows. The insert trigger demands `NEW.seq = MAX(seq)+1` (`store.rs:538-551`); the export orders `transcript_item` by `transcript_id, seq` (`transfer.rs:35`), and the import refuses an overlapping row whose `h_k` differs (`transfer.rs:491-530`) rather than overwriting. "Rows cannot be recreated" survives the transfer.

CONCESSIONS. "Unwind and reopen per version" overstates: it is ~13 versions (`tests.rs:614,723,1382,1487,1575,1668,2114,2660,3179,3601,3731`), not 50; the rest of the argument is that additive arms share one shape. And `import_tx` (`transfer.rs:312-338`) commits two files in sequence with nothing marking a half-import. Proposed: a marker row beside `carved_project` (`split.rs:34`).

ANTICIPATE. Position 1 must produce a *silent* path; the ones I traced all refuse by name — `SchemaTooNew`, `WrongSchema`, `unsplit` (`split.rs:648-657`), and `open_transition` refusing a mid-carve key with the fix spelled out (`split.rs:588-594`). "No lock" is real, but by finding 2 its cost is a re-run, not a corrupt file. Position 3's complexity complaint is fair and mostly cosmetic: the carve state, the string-replaced FKs (`split.rs:308`) and out-of-order arms 19/20/21 cost lines, not correctness — `every_migration_arm_declares_whether_it_breaks_a_reader` (`tests.rs:2940`) compares the arm *set* against the source, so sequence is not a claim the code makes.
```

```
A5 R1, position 3 (read at 9e9312b06, no test run). Not a position-1 or position-2 finding: both come out of the same smell.

Thesis: the store's safety rests on hand-kept parallel lists and text surgery, each guarded by a test that checks only part of the list. WAL+FULL and the triggers are fine (conceded). The cost is that every schema change needs five edits that must agree, and nothing makes them agree.

Findings

1. HIGH. Two hand-kept batch lists.
- `Store::migrate` runs 18 `execute_batch(X_SQL)` calls (`tokencore/src/store.rs:1895-1913`).
- `split::batches()` (`store/split.rs:160-181`) lists the same batches by hand, with a hard-coded `[&str; 19]`.
- Its doc says "One list, so a batch added there is routed or refused here". That is false: the fresh path never calls `batches()`.
- Failure: someone adds `FOO_SQL` to `migrate` and forgets `batches()`. Single-file stores get the table, but `schema_sql(Shared/Project)` omits it. A split set has no table, and the first write fails at runtime. `every_statement_the_schema_is_built_from_names_its_table` (`split_tests.rs:240`) iterates `batches()` only, so it cannot see the omission.
- Change: one `const BATCHES: &[&str]` that `migrate` loops over. Delete the array.

2. HIGH. A project file's schema is the shared DDL with text deleted from it.
- `without_cross_file_keys` (`split.rs:307-310`) does two `String::replace` calls on exact spellings.
- Failure: any new column written `REFERENCES session (id)`, `REFERENCES session(id) ON DELETE SET NULL`, or on a new line leaves a dangling foreign key in the project file. With `foreign_keys` on, every append to that table is refused. No test asserts that a project file has no `REFERENCES session`.
- Change: drop the FKs from the DDL source (`session_id` is a plain column everywhere, as v48 already treats it), or add the one-line test `schema_sql(Project)` contains no `REFERENCES session`.
- `statements()` (`split.rs:186-201`) splits SQL on lines that start with `CREATE `. This is also text parsing. The `table_of` test covers it only for current text.

3. MEDIUM. Migration arms probe the schema to guess which file they are in, and a failed probe passes silently.
- v48 (`store.rs:2588-2599`) runs `OWNERS_SQL` only if `sqlite_master` has `session`. v49 and v51 check `process` and `session` the same way.
- The probe is `.and_then(|st| st.exists([])).unwrap_or(false)`. There are 25 `unwrap_or(false)` in `store.rs`.
- Failure: a probe that errors (SQLITE_BUSY from a second daemon, I/O error) reads as "no session table". v48 is skipped, `migrate_from` returns Ok, and the version is stamped 51 (`store.rs:1867-1875`). `owner`/`holding` never exist, and nothing retries.
- v50 (`:2617-2620`) is unguarded, so a project file at v49 gains a stray `session_grant`. `session_grant` is shared per `split.rs:82`. v48 shows the author knew the guard was needed.
- Change: a `fn has(&self, sql) -> Result<bool>` that propagates errors, and pass the file kind into `migrate_from` instead of probing for it.

4. MEDIUM. The arms are out of numeric order: v21 at `store.rs:2225`, then v20 at 2241, then v19 at 2276, then v22.
- This is harmless today because they touch separate things. Nothing enforces that, and the version is the only sequencing.
- Change: renumber the arms into order, or add a test that scans `migrate_from` and asserts the `from <` guards are ascending.

5. MEDIUM. The carve-in-progress state needs a third mode.
- A directory can be a single file, a set, or mid-carve. Mid-carve has its own table (`CARVED_TABLE`, a table created by no schema, `split.rs:23-34`) and its own handle rules (`:574-650`).
- The state machine is spread over `carved_keys`, `refuse_unsplit` and `carve_into` (`migrate_split.rs:120-262`).
- P4 left check-then-act against a daemon starting mid-carve as HYP. I did not trace it either (HYP).
- Change: carve-by-key is operator tooling for a box with a handful of projects. Cut it to the offline `migrate` plus `--finish`. That removes `carved_project`, the key checks, and roughly 600 lines of `migrate_split.rs` (1229 lines total).

6. LOW. The v18, v20 and v22 arms each carry a full copy of `CREATE TABLE merge_review`/`merge_queue` beside the fresh-schema copy. I found no test that diffs a migrated store's schema against a fresh one. Only per-version tests exist (`store/tests.rs:614`, 723, 865, ...).

Concessions
- Transcript rows are safe: WAL+FULL (`store.rs:1608`), append-only triggers (`:527-541`), and no arm deletes rows (P4).
- The split coverage test (`split_coverage_tests.rs`) is a real guard for routing. It does not cover the schema text in findings 1-2.
- Per-arm idempotence makes the missing migration transaction survivable (position 1's ground).

Anticipated replies
- Position 1 will say these are hygiene, not corruption. Finding 3 is silent loss of a table behind a stamped version, so it is corruption by omission.
- Position 2 will say tests exist. They cover the current text, not the next edit. Findings 1 and 2 each need a one-line test or a deleted duplicate.
```

## Synthesis

Raised by opus R1, conceded and verified by fable, GLM and Kimi R2, also DeepSeek (supplementary). DeepSeek R1 did not address it. Verified.
- **F2 MEDIUM - migration and stamp run with no tx and no lock.** `tokencore/src/store.rs:1867-1874`. Between `DELETE FROM schema_version` and the INSERT a concurrent opener sees `None` and runs the unfiltered fresh path (`:1893-1911`) into a split `shared.db`. Two daemons reading 50 race the check-then-ALTER and the loser fails to open. Opus raised it as HIGH. Verified.
- **F3 MEDIUM - unguarded v47 and v50 arms create project tables in `shared.db`.** `store.rs:2582-2586` (`RECALL_SQL`), `:2617-2620` (`GRANTS_SQL`). v48 (`:2588-2599`) shows the guard. ### Disagreements
