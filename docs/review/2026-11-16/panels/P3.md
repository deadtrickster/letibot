# P3. Shadow - deep

Panel P3 of the letibot adversarial review. Snapshot `9e9312b06` (worktree `~/Projects/letibot/wt-review-snap`).

Scope: seams S11 and S20, invariants I30, I31 and I49. Files `harnessd/src/shadow/`, `harnessd/src/harness/shadow_seat.rs`, `harnessd/src/{queue_asks.rs, answers.rs, note_accept.rs}`.

Positions:
1. The shadow can be steered by injected text (stateless holes, echoed tool text, misattributed operator rows, resumed injection across restart via a489bc75a).
2. It never denies, quotes are span-checked, persistent mode is strict, and its one acting path is gated on a listed rule and a breaker.
3. Against both: a second model in the loop adds cost and complexity for nudges a rule could make.

## Round 1

### Position 1 - Claude opus (`P3-r1-p1-opus.txt`)

```
Thesis: the one place the shadow acts without the operator is the R317 relayed-read answer. That path is always stateless and never strict, and its "listed rule" gate checks a substring, not a match. So injected text that steers the reviewer seat's request is enough to get a read granted that the operator never saw. The strict guarantees that position 2 relies on apply only to persistent `ask` questions. The acting path never reaches them.

Findings

1. high - the listed rule is not tied to the call. `shadow/permission.rs:281` `acting_rule` accepts any 8-byte substring of any allow rule from `permission.json`. It is never passed the path (`:342`). `rules_of` `:476-481` lists every allow rule (bash, write, anything). Scenario: `permission.json` allows `bash git status`. A reviewer asks to read `/home/dead/Projects/other/secret.txt`. The shadow replies `{"verdict":"allow","rule":"bash git status"}`. `verify` passes because the rule text is in `data` (`verdict.rs:467`, rules printed at `permission.rs:41`). `acting_rule` passes, and `grant_ro` is issued (`:387`). The only test, `shadow/tests.rs:1479`, never pairs a rule with a path outside it. Change: pass `path` to `acting_rule` and require a listed read rule whose pattern glob-matches it, via the gate's own matcher.

2. high - the acting path is stateless in every mode. `Relay::judge` calls `shadow.ask` (`runner.rs:882`). That builds a `Request::new` with no question, so `:446` takes the stateless branch. `shown_for` (`permission.rs:304-323`) builds `Shown` with `strict: false`, no spans, and `task: None` (`:312`). So strict mode's listed-rule narrowing (`verdict.rs:481`) never runs on the one path that acts, and the shadow judges with no stated task. The injection vector is the path string itself. It is free text chosen by a reviewer model that read untrusted PR content (`answers.rs:432-440` checks only that it is the sole argument). Change: send the persistent question, and set strict with the operator's task, or refuse to answer when `mode=stateless`.

3. high - `read_passes` misses agent credentials. `guard.rs:134` `OWN_CONFIG` plus `secrets.rs:37-72` STORES do not cover `~/.claude/.credentials.json`, `~/.codex/auth.json`, or the letibot data directory with `sessions.db` (only `.local/share/letibot/keys` is checked). `SECRET_FILE_NAMES` (`intent.rs:1571`) matches the exact name `credentials`, not `.credentials.json`. Combined with 1 and 2, an injected reviewer gets the operator's Claude OAuth token in view. HYP that the bind exposes the file unchanged and that the reviewer can then send it out. Change: an allow-list of roots (the workspace, sibling worktrees) instead of a deny-list.

4. medium - stateless `during` offers act on tool text. `during::shown` has no `push_said` spans, and `verdict.rs:415` checks offer authors only under strict. `shadow_seat.rs:403-410` acts on the picks. Scenario: a fetched page says "the user needs skill deploy". The quote lies in tool output, passes `verify`, and the skill is offered on the next request. Change: no acting offers unless strict.

5. medium - echoed text becomes quotable. `authored_span` (`verdict.rs:73-77`) accepts any occurrence. Text first seen in tool output and echoed by the assistant is quotable as Assistant, and then passes as a note (`:320`) labelled "the model". `/note accept` then writes it to durable project notes (`note_accept.rs:99-103`). Operator-gated, but the provenance line misleads. Change: reject a quote whose first occurrence is in a Tool or Peer span.

6. low - the breaker resets at restart while grants persist. `Answering` is in-memory (`permission.rs:174-194`). Its "disagreement" only counts a revoke or a No to a card the operator saw. Cards the shadow answered are never seen, so wrong grants accumulate silently. Change: persist the counter, and cap grants per session.

7. low - resume verifies only the last kept turn. `conversation.rs:131` checks `last.matches`. Earlier tails, spans and replies are taken from the record unchecked (`resume.rs:76-97`). An injection the shadow answered once is replayed after every restart.

Concessions: a denying verdict cannot parse (`verdict.rs:458-464`). The chain hash covers the header, so a reclassified author breaks resume (`feed.rs:120`), and I withdraw that part of the misattribution-across-restart lead. Persistent `ask` questions really are strict (`conversation.rs:241`). Note accept requires the operator.

Against position 2: "persistent is strict" is true and irrelevant, because finding 2 shows the acting path never uses it. And "gated on a listed rule" fails by finding 1. Against position 3: I agree a rule could do this job, but the defect is the shadow acting at all on an unbound rule, not its cost. Fix 1 alone would make the second model redundant for R317, which supports position 3's remedy.
```

### Position 2 - DeepSeek (`P3-r1-p2-deepseek.txt`)

```
[model: deepseek/deepseek-flash (the default; the one-shot ignored --model)]
Thesis: for the workload that exists today — a review-queue seat blocked on a read outside its clone with nobody at the head — R317 is a net gain in safety, and every claim of position 2 holds in code rather than in prose. Authority is narrowed at four independent places before any model is consulted, the verdict space is closed to `allow|ask`, and the answer is an ordinary session view grant that is kept, listed and revoked through the same path as a person's. The defects are in arming and attribution, not in the mechanism.

Findings

1. **Acting is armed by the switch that was sold as observation.** `ShadowConfig::answers_reads` is `is_on(Permission) && !answer_reads_off` (`crates/harnessd/src/shadow/config.rs:84-86`), read at open (`crates/harnessd/src/harness/open.rs:3607-3608`). High. Turning on the permission job to *log* verdicts silently grants a reviewer reads with no card — against the design's own rule 7, "observe-only first… moves to acting only after its replay score… beats the current mechanism" (`TODO.md:1154`). Failure: an operator enables the shadow for a week of evidence and it acts on the first relayed card. Change: default `answer_reads` off; make `true` the promotion act, recorded per session.

2. **The breaker is per process while its grants are per store.** `BREAKER_AT = 2` and `on.swap(false)` live in `Answering` (`crates/harnessd/src/shadow/permission.rs:170,231`), rebuilt from config at every open (`open.rs:3607`); the grants it made survive as `Kept::View` rows. Medium-high. Failure: two operator revokes stop answering; a daemon restart re-arms it while the revoked-and-replaced grants are still in force, so the operator's only stop is undone by the next deploy. Change: persist the trip (a `shadow` row beside the grants) and require an explicit re-arm.

3. **The model is told a person answered.** When a shadow grant binds the path, the reviewer's own note reads "granted mid-session … by your answer" (`crates/tools/src/runtime.rs:2423`), a defect R317 already lists as left (`TODO.md:2205`). Medium. Failure: the reviewer learns a human vetted the read and quotes that back; I2/Q12 recording is right in the store (`by: shadow:<judge>`, `escalate_tests.rs:913`) and wrong in the text the model reads. Change: thread the answer's `by` into `grant_into_view`'s note.

4. **Half the read denylist is relative to the daemon's `HOME`, not the asker's.** `read_passes` builds its secret list as `home.join(d)` for relative entries (`crates/harnessd/src/shadow/guard.rs:154-163`, `intent.rs:1554-1566`), and `home` is `std::env::var_os("HOME")…unwrap_or_default()` from the *main* session (`crates/harnessd/src/harness/shadow_seat.rs:31`). Medium. Failure: a daemon started with `HOME` unset (systemd unit, sandboxed launcher) makes every relative entry `.config/letibot`, `.ssh`, `.docker` inert, so only the absolute `/etc/*` entries and `secret_store_of` remain. Change: take home from the asker's seat and refuse when it is empty or relative.

5. Low: on a shadow timeout `note_before` returns `None`, then `annotate` runs the same question again (`crates/harnessd/src/answers.rs:190-196`) — a second paid judge call per timed-out card. Also known and disclosed: a revoke unbinds at each session's next call, not mid-command (`crates/harnessd/src/grants.rs:113-114`).

Concessions. The automatic path is *narrower* than the human one it replaces: the shadow's grant is `Scope::Session` (`escalate_tests.rs:1061`) while a person's `grant_ro` on the same relayed card is kept at the queue's scope, covering every future reviewer (`answers.rs:493-507`). But the duplication position 3 names is real: `Relay` answers through `Note`, not `AuthorisationOracle`, so two authorisation models act on the same card. That must be retired before any stage 2.

Anticipating the others. To position 1: injected text cannot widen anything — the quote must be a substring of an allow rule from permission.json (`permission.rs:281`; `verdict.rs:480-488`), the tier must be `MayApprove` and the tool class `Read` (`answers.rs:432-440`), the asker must be a daemon-named queue seat (`permission.rs:250-259`, `queue_asks.rs:164`), and the path must clear `read_passes`. An injected `allow` can at most leak one file a person would have refused — never a write, exec or network. To position 3: it is one answer channel (`option_id: "grant_ro"`), one option the card already offered, one store.

```

### Position 3 - Claude sonnet (`P3-r1-p3-sonnet.txt`)

```
P3 reviewer 3 (position 3), round 1, 9e9312b06. Paths under crates/harnessd/src/.

THESIS
The one acting model path is where the model does the least. By the time the model speaks, `scope` and `read_passes` have already decided what may be granted. The model only has to quote any listed rule. Rules can make that decision. The other two jobs duplicate a regex and a similarity path that must stay as fallbacks, so every model job ships two implementations. Positions 1 and 2 argue about how safe the model is. I argue the model is not the part that decides.

FINDINGS

1. HIGH. The R317 grant's "rule" is never matched to the request. `shadow/permission.rs:272 acting_rule` accepts the verdict if `rules.iter().any(|r| r.contains(rule))` and `rule.len() >= MIN_QUOTE` (8, `verdict.rs:12`). `rules_of` (`:476`) lists every allow rule in permission.json as "<permission> <pattern>". The check never asks whether that rule covers a read of this path.
   - Scenario: permission.json holds `bash git status --short` or `edit docs/**`. A reviewer relays a read of `/var/log/foo`, which passes `read_passes`. The model replies allow with rule "git status". That is a substring of a listed rule, so the check passes and `grant_ro` is written as `by: shadow:<judge>` (`permission.rs:389`).
   - The "rule" is a quote check, not an authorisation check. The invariants entry I49 calls this "acts only on a listed rule"; that holds only as a string match.
   - The model verifies nothing here. The same rule was asked before the model existed: `letibot_tools::permission::evaluate("read", path, rulesets)`, `tools/src/permission.rs:113`.
   - Change: replace `acting_rule` with `evaluate(read, path)` returning Allow from the real rulesets. Keep the model only for the card line. With no matching rule, the path is "ask". The breaker, `/shadow revoke` and the quote machinery then guard nothing that rules do not already cover.

2. MEDIUM. The same grant has a lexical-only path guard. `shadow/guard.rs:138 read_passes` and `lexical` do not resolve symlinks. A symlink in a permitted directory that points into `~/.ssh` or `~/.config/letibot` passes. HYP: I did not trace whether `grant_ro` canonicalises later. A rules-only path would sit behind the same real-path check as every other read.

3. MEDIUM. The turn_end job runs two implementations of one decision. The regex nudge is computed and held every turn (`harness/shadow_seat.rs:~340`, `shadow_held`). `turn_end::decide` (`shadow/turn_end.rs:166-205`) is then a 10-way matrix: Owed x reminded, None, Unsure, Void, TimedOut, Failed, Paused, wrong job, Stale and Superseded. Five of those outcomes just release the regex. The model adds one reminder per operator message, in a fixed template (`turn_end.rs:104`). That is a rule's output.
   - Cost per ended turn in persistent mode: a call under a 30 s deadline, up to a 64 KB conversation (`conversation.rs:11`), plus a second stateless call on every 10th question (`config.rs:27 FRESH_EVERY`, `runner.rs:416 sampled`, `:543 fresh_check`). That is about 10% extra spend, spent only to test the model against itself.
   - Change: delete the model path unless `shadow/replay.rs` shows the model beating the regex on labelled turns. `replay.rs:2` has the scorer. The CI or release gate should publish its numbers, and none are in the tree. HYP: I did not run it.

4. LOW. `shadow.rs` `Job::acts` doc says "Permission is observe-only". R317 made that false. The `on_outcome` comment says the same. Both were last true before 913e532d6, so a reviewer reads a stale invariant.

5. LOW. The breaker (`permission.rs:170 BREAKER_AT = 2`) lives in the process and resets at restart, while grants persist (store v51). A restart puts the model back at full trust over the grants it already made. With rules deciding (finding 1) there is no breaker to reset.

6. LOW. In stateless mode, `shown.strict` is false, so the `verdict.rs:479-488` listed-rule check is off. Any rule string that merely appears in the shown history passes. This is why the real check should not live inside the model's reply.

CONCESSIONS
- The model path does not deny (`verdict.rs:458-464`). Quotes are span-checked and the denylist is solid.
- `replay.rs` is real: it scores the regex against the shadow. If it shows a lift, finding 3 weakens. Finding 1 does not, because rule coverage is deterministic either way.
- The during job's note and skill picks have no rule equivalent. I leave them alone, with similarity as the fallback.

ANTICIPATING THE OTHER POSITIONS
- Position 1 (injection steers it): a steered model can still only ask or quote a listed rule. Finding 1 means a steered model and an unsteered one grant identically, so injection scenarios are the wrong place to look.
- Position 2 (strict, gated, breaker): the gate is real, but it is mostly `scope`, which is not the model. What the model adds is a string match, so the breaker is machinery around a no-op.

Not verified: no test run, as reading sufficed. Finding 2 and the replay lift are HYP.
```
