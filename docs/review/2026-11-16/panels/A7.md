## Round 1

### Position 1 (opus)
Thesis: the reaper and the restart still lose live work at 9e9312b06. P5 settled the reaper's ordering faults. The bigger loss in this area is newer and has not been filed. The launcher interrupts every turn before it sends SIGTERM, so the daemon judges its own restart as a person's stop. It then records every running subagent as killed. R313 "left" names only the wake window, which is the smaller half.

Findings

1. HIGH. `--restart` and `--stop` record live subagents as killed, so the next daemon does not resume them.
- `scripts/letibot:2669` calls `interrupt "$SOCKET"` before `stop_one` (`kill "$pid"`, :2590).
- `interrupt_turns` (`tui/src/head.rs:714-723`) interrupts every running session. `Registry::list` includes children (`sessionlog/src/registry.rs:2271-2272`, keep-all filter).
- The parent's Interrupt runs `stop_children_first` (`harnessd/src/harness/hub_io.rs:262`). That calls `stop_all`, then `kill` (`children.rs:3215-3222`, :2866), then `TaskSlot::kill` (:360-366), then `SubagentRecord::killed` (`subagent_record.rs:385-395`).
- `is_stopping()` is false at that point. It is set only inside `Registry::close` (`registry.rs:2566`), which runs after the signal. So the record is written as `settle_subagent_run(child, "killed", "stopped")`. The `interrupt_subagent_run` keep-running branch (:271-278, :362-366) is never taken.
- Failure: `letibot --restart` with a subagent mid-turn. The new daemon reads a killed row and does not resume the child. The parent's `task_result` says stopped, and the child's work is lost.
- The tests miss it. `restart_restore.rs:152-153` stops through `registry.close()` first, so the resume tests (:359, :568) prove an order the launcher never uses.
- Change: one of these two.
  - (a) The launcher sends SIGTERM first. `Registry::close` already interrupts turns before runs (`registry.rs:2590-2605`).
  - (b) Add a frame that sets `stopping` before `--interrupt-all`.
- Either way, add a test that interrupts through the socket and then closes.
- HYP: the reason the launcher comment gives at :2662-2665 (a worker finishes its turn after the listener is gone). (a) has to answer it.

2. MEDIUM. R313 left: a wake can open a turn after the interrupt.
- The window is up to `INTERRUPT_WAIT` (30 s, `head.rs:559`) plus the wait before the signal.
- `wake` checks `is_stopping` at `turns.rs:440` and :668, and both read false.
- Failure: a room line or a job end opens a turn that `close` then kills mid-tool. It costs a generation, and it reproduces the rano incident in the R313 TODO (`TODO.md:2245`).
- Change: the same fix as 1.

3. HIGH, with area evidence added to P5 A1 and D2.
- P5 accepted D2 (a hard close ends the owner's own jobs, `reap.rs:717`, :779) only because a hard TTL is a backstop.
- With A1 unfixed (`lifecycle.rs:460`, `reap.rs:159-163`), the backstop fires on any package reopened more than the TTL after it was created, within one sweep. Its jobs are killed and no restart marker is left for them.
- D2 can be accepted only after A1 lands, so A1 has to stay first in the order.

4. HIGH. U1 stands and is unrebutted.
- When a package's own daemon idle-closes it, the owner stays `Closing` for good: `reap.rs:1175-1179` and :749-771, `reap_pass.rs:91-101`.
- `end_processes` kills each new job on every pass.
- Change: write `Close` when the only compute left is this process's own daemon.

5. MEDIUM. `retire_if_empty` force-removes a tree without `why_kept`.
- Sites: `serve.rs:1627`, `mergequeue/git.rs:846`, `tools/src/git.rs:344-347`. This is P5 A2.
- I keep the severity at medium, not low. `--force` deletes ignored `target/` and scratch files under a live session in another daemon.

6. MEDIUM. There is no reaper on the host side: `remote.rs:173` has one caller, `disks.rs:609`. This is P5 A3. Build the timer that d.3 promises.

Against position 2
- Restart markers and R313 marking protect host jobs and deliveries. They do not protect subagent rows.
- `why_kept` guards `settle_tree` but not `retire_if_empty`.
- The mechanisms are real, but finding 1 goes around them all through the one fact they trust, `is_stopping`.

Against position 3
- Finding 1 is a split fact. The launcher acts over the socket, and the "we are stopping" flag lives only inside the process.
- The fix is one flag set earlier or one reordered signal, not a per-tree stamp.
- Agreed that the design doc and tests describe the close-first order while the launcher does the opposite.

Concessions
- `autoarchive::refusal` checks writer, pid, jobs and asks before archiving (`autoarchive.rs:290-315`).
- An idle close never fires with busy work (`reap.rs:181`).
- `wake` does check `is_stopping` twice.
- Restore after `registry.close` is well tested (`restart_restore.rs:359`, :568).
- The parent-before-busy order (D1) is documented policy.

No test was run. Every claim above was checked by reading the code.

### Position 2 (deepseek)
[model: deepseek/deepseek-flash (the default; the one-shot ignored --model)]
Thesis. Position 2 holds for the failures that actually bit: a session closed under a live head, a worktree removed under a live session, a job lost across a restart, a restart notice dropped. Each has one mechanism and a test. But the mechanism is a lease renewal plus a proof-and-keep closure, and each guard I cannot cite is a real hole. Two are high.

F1 (critical). The hard TTL clocks from `created_ms`, which a reopen deliberately preserves (`crates/tools/src/lifecycle.rs:459-460`, `crates/tokencore/src/store/owners.rs:593-598`), and it is evaluated before `starting` and before `busy` (`crates/tools/src/lifecycle/reap.rs:159-168` vs `:169`, `:181`). Failure: a package resumed after 24h from its first creation (`PACKAGE_HARD_TTL_MS`, `lifecycle.rs:433`) is set `Closing` on the next sweep (≤60s) while a turn is in flight; `reap_compute` then ends its scope and daemon (`reap.rs:656`, `:707-718`). Every reopen re-arms it, so the id is permanently unusable. Fix: stamp a `live_since_ms` at each return to `live` (`owner_for_open`, `reopen_owner`) and measure the hard TTL from it; keep `created_ms` as the record.

F2 (high). `retire_if_empty` (`crates/harnessd/src/mergequeue/git.rs:846-863`) removes a superseded branch's worktree and deletes the branch on commit proof alone — no `in_use::why_kept`, no cwd check — while `settle_tree` (`serve.rs:1455-1471`) and `reap_worktrees` (`serve.rs:1300-1302`) both ask. Failure: a clean, superseded tree is an operator shell's cwd or a second daemon's session; it is removed and the ref deleted. `TODO.md:5440` admits it as "Left". Fix: thread the `in_use` closure into `retire_if_empty` and skip-and-say.

F3 (medium). `why_kept`'s cwd half reads only this box's `/proc` (`crates/tools/src/lifecycle/in_use.rs:57-77`). A seat's own `bash` runs inside bwrap's PID namespace, so no host process has a cwd inside the tree: the guard misses exactly the processes a seat creates. HYP on bwrap's outer cwd; the code path is not. Fix: have the seat write a per-worktree pid stamp, and check it here.

F4 (low). Plan and executor disagree: `judge` (`crates/tools/src/lifecycle/plan.rs:746-773`) says `Now` for a settled owner's Work without asking `in_use`, while `crates/tools/src/lifecycle/work.rs:205` keeps it. `gc --plan` therefore tells an operator a live tree may go. Fix: inject the in_use closure into `judge`.

Concessions. `renew_held` (`crates/harnessd/src/reap_pass.rs:149-171`) is the real answer to "closed under an attached head": lease in `shared.db`, renewed for a head, a turn or an open job. `served_by` (`reap.rs:181`, `:387-392`) keys daemon records on the owner's own workspace (`harness/open.rs:1986`), so a package's dedicated daemon is found, and `crates/tools/src/lifecycle/reap/tests.rs:598` asserts it. Kept jobs are a `DETACHED_JOB` holding that outlives the daemon (`reap.rs:377-380`, `plan.rs:585`). R313 marks delivery only inside the store callback (`turns.rs:695`, `:800`) and splices the handles back when the door does not open (`:737-739`, `:804`). Archive-before-delete is the executor's order (`work.rs:205→211`, `worktree.rs:253-272`). But F1 shows the hard TTL is a bound on row age, not on work, and it fires first — so "whatever it is doing" is the design, and the design is wrong for a resumed owner.

Positions 1 and 3. Position 1 gets F1 and F2 and should take them; its other three claims it cannot make: interactive sessions are excluded from every closing rule (`reap.rs:159`, `:172`, `:184`), a daemon's own attached head renews, and remote owners are leased by `remote.rs:315-441`. Position 3 gets most of F3/F4, but both fixes are closure injections, not a redesign of the seven inputs.


### Position 3 (sonnet)
A7 reviewer 3 (position 3), round 1, 9e9312b06.

THESIS
The lifecycle design says one fact decides an owner's life: "this tree is owned and alive". The code has no such fact and no second reaper. Liveness is rebuilt per call from owner rows, `process` rows in per-project DBs, cgroups, `/proc/*/cwd` links, daemon records matched by repo path, and git state. Both other positions patch holes in that rebuild. The design doc tells operators two backstops exist that do not. I build on P5 (A1, A2, U1, U2, A3) and do not repeat it.

FINDINGS

1. HIGH. `letibot-gc.timer` does not exist.
- docs/lifecycle.md:18 says the reaper is "a box-level program run by a systemd user timer and by the daemons". :586 names a "box reaper" for a gone daemon. :807 says "a systemd user timer `letibot-gc.timer` every 10 minutes on every box (the path that needs no daemon)".
- Grep of crates, scripts and docs finds no unit, no `OnUnitActiveSec` and no installer. The only hit is a test fixture string (crates/tools/src/lifecycle/systemd.rs:204).
- The only periodic reaper is `reap_pass::SWEEP` (harnessd/src/reap_pass.rs:28, :173-204), which runs inside a daemon.
- Scenario: a package daemon is SIGKILLed or OOM-killed while its VM, docker containers or remote holdings live. No daemon runs a pass, and `vm_reap::pass` is also daemon-driven (vm_reap.rs:494). Nothing reaps until someone starts another daemon or types `letibot gc`.
- Change: either ship the timer and `letibot gc --now`, or strike d.6, :18, :586 and :807 and say plainly that only a live daemon reaps.

2. HIGH. The `RuntimeMaxSec` hard-TTL backstop is never set.
- docs/lifecycle.md:585, :738 and :855-857 say a package daemon adds `-p RuntimeMaxSec=<hard TTL + 1 h>`, "enforced by the user manager, so it holds with every letibot process wedged".
- scripts/letibot:295-325 adds it only when `LETIBOT_SCOPE_RUNTIME_MAX` is exported by the caller.
- That name appears only in scripts/letibot and tests/launcher.sh. No Rust code exports it.
- The reaper's own TTL check (reap.rs:158-164) is therefore the only bound. A wedged reaper means no bound at all.
- Change: have the daemon spawner compute and export it from `hard_ttl_ms`, or remove the claim.

3. MEDIUM-HIGH. The two checks that keep a tree alive read different facts and fail open.
- `in_use::why_kept` (tools/src/lifecycle/in_use.rs:13-21) asks `store.writers_under` (the `session_writer` table) and then scans `/proc/*/cwd`.
- `cwd_inside` (:58-66) returns None when `/proc` is unreadable, and skips any process whose cwd link it cannot read. That includes another user's process and a process in another PID namespace or a sandbox. The comment (:55-56) calls that "not one of ours".
- This is a separate, unlogged "not in use" answer, distinct from P5's I29 finding. The `process` table and the cgroup (`busy()`, reap.rs:433-451) are not consulted at all.
- Scenario: the gc plan or the merge queue removes a tree under a shell or editor run in a bwrap or VM-shared mount. Under a different uid or a hidepid mount the link is unreadable and the tree is judged free.
- Change: make `/proc` read failure return "keep, cannot tell". Add the `holding` and `process` rows as a third input.

4. MEDIUM. `daemons_of` (tools/src/lifecycle.rs:859-872) matches daemon records to an owner by canonicalized repo path, and that is the only link between the two.
- P5 U1 shows the consequence: an own-daemon idle close becomes `Closing` forever.
- Beyond U1, a worktree daemon spawned from another folder writes under a different `store_key`. Doc :608-614 admits this and relies on `open_job_elsewhere`, which is a per-call scan of every project DB.
- Two daemons on one path, or a symlink that canonicalizes differently on a remote host, break the match silently. `unwrap_or_else` falls back to the raw path on a canonicalize error.
- Change: store `daemon_id` or pid and start time on the owner row at spawn (P5's stamp).

5. LOW. docs/lifecycle.md:585 says "since creation or last reopen". The code uses `created_ms` only (reap.rs:161). Already P5 A1 and conceded.

ANTICIPATING THE OTHER POSITIONS
- Position 1 is right on the hard-TTL-on-reopen and parent-before-busy points, which P5 verified. These are symptoms of the split in findings 3 and 4.
- Position 2 lists lease, busy and served-by, restart markers, `why_kept` and gc plans as handled. But `why_kept` fails open on unreadable `/proc` (finding 3), and the two things that make the design survive a dead daemon (findings 1 and 2) are not built. Every "handled" case assumes a live daemon with a working sweep.

CONCESSIONS
- The comparison tables in the doc that mention `cleanup_ttl_days`, `auto_stop_machines` and `kill_all` describe other harnesses, so they are not stale claims. The `vm_reap::daemon_of`, `teardown_session`, `supervise.rs:14` and `commit_proof` references exist.
- Position 2's R313 and restart-marker machinery is real and tested. I did not trace it.
- HYP: whether the daemon's own idle exit bounds the unreaped state in finding 1 (P5 already left this open). I ran no test.
