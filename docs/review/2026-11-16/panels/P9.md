## Round 1

### Round 1, position 1 - Claude opus

P9 reviewer 1 (Against), 9e9312b06

Thesis. R317's relayed-read path already does what the oracle seam was built to stop. A model's free-text quote is enough to widen a mount namespace. No trail is cited, the tier is hardcoded, the grant covers the whole queue, and a breaker that forgets at restart sits over grants that do not. Stage 1 should not widen until the items below are fixed.

Findings

F1 high. The cited rule never has to cover the path. `harnessd/src/shadow/permission.rs:272-282` `acting_rule` only checks that the quote is at least 8 bytes long and is a substring of some listed allow rule (`MIN_QUOTE`, `shadow/verdict.rs:12`). The rules are the main session's (`harness/shadow_seat.rs:29`), not the asker's. The test `shadow/tests.rs:1481` only checks that the quote is listed. Scenario: the only rule is `read /build/**`. A reviewer asks for `/home/dead/.claude/.credentials.json`. The shadow answers allow with rule `read /build/**`, and `grant_ro` binds the file. Change: match the path against the cited rule's glob, or refuse to act.

F2 high. The read denylist is lexical and incomplete, and the bind key resolves symlinks. `read_passes` (`shadow/guard.rs:146-170`) checks the path as spelled, but the grant is recorded under `view::key`, which canonicalises (`tools/src/view.rs:71-90`, `:222`). Two scenarios. First, an author creates `wt-feature/link -> ~/.ssh` and a reviewer asks for that link: the check passes and the canonical `~/.ssh` is recorded. Second, `~/.claude/.credentials.json`, `/proc/<pid>/environ` and `~/.local/share/letibot/sessions.db` are not covered by `STORES`/`secret_dirs` (`tools/src/secrets.rs:37-72`, `intent.rs:1554`). Only `.../letibot/keys` is guarded. Change: run `read_passes` on `key(path)`, deny `/proc`, `~/.claude` and the letibot data dir, and allow by list rather than deny by list.

F3 high. The always-ask list cannot reach view reads, because the tier is never derived. `ask_to_see` hardcodes `tier: Tier::MayApprove` and passes `AuthorisationTrail::default()` (`tools/src/adjudicate.rs:2783-2787`). `view_read` checks only that tier (`harnessd/src/answers.rs:432-440`). So `credential_use` is never evaluated for the path. Compare `grant_memory` (`:2890`), which is `AlwaysAsk` "so a guard model widening it would not be the model granting itself the box". Change: classify the path with `Surroundings`, set the tier from that, and carry the asker's trail.

F4 high. One answer becomes a standing grant for the whole queue. A shadow answer is relayed, so `keep_grant` stores it at `Scope::Queue` (`adjudicate.rs:1733-1738`). That scope covers every future reviewer until it is revoked (`grant_ledger.rs:14`). The shadow's own row says "for that session" (`permission.rs:367`), which is false. Change: store shadow grants at `Scope::Session`.

F5 medium. The breaker forgets at restart and the grants do not. `Answering::new` resets `disagreements` and `granted` (`harness/open.rs:3608`, `permission.rs:185`), while the ledger grants persist. A No to a shape granted before the restart no longer counts (`permission.rs:414-441`). Change: persist the breaker count, or rebuild `granted` from `shadow_grants`.

F6 medium. A revoke does not unbind running commands. `ViewGrants::revoke` only queues the path (`view.rs:237`), and binds are dropped "at its next call" (`harnessd/src/grants.rs:112`). A background job or an open fd keeps the read. Change: when a shadow grant is revoked, kill or unmount that job's namespace.

F7 medium. Shadow grants never reach the corpus. Neither `ask_to_see` nor `grant_view` calls `self.record` (`adjudicate.rs:2678-2876`), although the doc comment at `:2830` says they do. Effect on R316: stage replay cannot measure the shadow's own grants from the corpus. If they are added naively, labels written by `shadow:` judges get scored against themselves. Change: record view asks, and exclude `verdict_by` starting `shadow:` from the agreement metrics.

F8 low. `a_reviewers_probe` admits `Intent::Unknown` (`adjudicate.rs:1555`). That goes against the "asked, not admitted" contract at `intent.rs:5002`. `rclone` and `lftp` are not in the table at all, so they classify as Unknown. HYP: whether the reviewer's boundary blocks egress.

Siblings: a `Claim::Shares` waiter gets Covered from the shadow's answer (`adjudicate.rs:2849-2854`). This only multiplies F4.

Not verified (HYP): that the model can be steered by the asker-controlled path text shown at `permission.rs:316-321`. `read_passes` only requires the path to be absolute, so it may contain newlines.

Concessions. `Blocked` is excluded and `AlwaysAsk`-tier calls do not reach the shadow. The shadow only answers `grant_ro`, never rw (`permission.rs:388`). `allow_always` on a relayed card is refused (`answers.rs:204-215`). Grants are tagged `shadow:` and can be revoked through one path (`grants.rs:85`). The `keys` path component is denied.

Against position 2: "Layer A settles tiers first" does not hold here, because a view read has no layer A reading and its tier is a literal. "Every grant is listed and revocable" holds only for future calls (F6), and the grant is queue-wide (F4).

Against position 3: I agree that two models coexist. But removing `Relay` is not a precondition for safety. Fixes F1-F4 are local and small, and they should land before any stage widens.

### Round 1, position 2 - DeepSeek

[model: deepseek/deepseek-flash (the default; the one-shot ignored --model)]
THESIS. The staged design holds, and I can show it from code rather than intent: the shadow's acting path is bounded four ways at once — read-only and `MayApprove` only (`crates/harnessd/src/answers.rs:432-439`), review-queue seats only (`crates/harnessd/src/shadow/permission.rs:250-268`), a path past `read_passes` (`:266`), and `allow`-with-a-listed-rule only (`:272-283`). Its grants are session-scoped, not queue-scoped (`crates/tools/src/adjudicate.rs:1736-1738`, asserted at `crates/harnessd/src/answers/escalate_tests.rs:1061`), and the always-ask list cannot reach it at all: `view_read` requires `Tier::MayApprove`, and `AlwaysAsk` blocks the model's admit (`adjudicate.rs:3559`), the session rung (`:3639`) and any allow rule (`:3362`). The gaps that remain are in the *bound on the model*, not in the architecture, and each is one function.

FINDINGS.

1. `read_passes` is the only bound on what the model may grant, and it misses credential files. `shadow/guard.rs:138-165` refuses secret stores, `keys` components, `intent::secret_dirs()` (`crates/tools/src/intent.rs:1554-1565`) and `SECRET_FILE_NAMES` (`:1571`). Gap: `crates/tools/src/intent.rs` classifies `/proc`, `/dev`, `/sys` as `Region::Device` but `guard.rs` never asks; `~/bin/fleet` (I17) matches no store and no file name.
Severity: high. Scenario: a reviewer asks to read `/proc/1234/environ`; `read_passes` returns `Ok`; the shadow quotes a rule and the grant lands in the reviewer's view, so a same-user process's tokens become readable with no card. Proposed: refuse `Region::Device` outright, and run the fetched path through the fence's own secret check instead of a second list. Add both paths to the deny test at `escalate_tests.rs:968`.

2. `acting_rule` ties the quote to *any* allow rule, not to a read rule nor to the path: `permission.rs:281` accepts `rule.len() >= 8` and a substring of any line `rules_of` produced (`:476-481`).
Severity: medium. Scenario: `permission.json` holds `bash clippy-driver *`; the shadow answers "allow" citing `clippy-driver`; the row and the store record name an exec rule for a path read, so the operator's audit cannot reconstruct the authority. Proposed: the matched rule must have permission `read` and its pattern must cover the path; keep the fragment test as a second gate.

3. The breaker is process state while its grants are store rows: `Answering` holds `disagreements` in memory (`permission.rs:174-176`, tripping at `:231`) and resets at restart, while `Kept::View` rows persist (`crates/tokencore/src/store/grants.rs`).
Severity: medium. Scenario: two operator revokes trip the breaker; a restart restores `answer_reads` with zero disagreements and every path it granted still bound. Proposed: keep the count (or a trip) in a row read at open; refuse to answer until the operator clears it.

4. `GENERATION` is a process-wide atomic (`crates/tools/src/grant_ledger.rs:17`) and `refresh_grants` returns early when it has not moved (`adjudicate.rs:1659-1662`), silently keeping the old copy on a read error (`:1667`).
Severity: medium. Scenario: a queue reviewer's gate in the folder's daemon keeps a path after the operator revokes it at the gatekeeper's head, until reopen. Proposed: make the generation check fail-safe for view claims — load, or compare a store-side max row id.

CONCESSIONS. No `ShadowOracle` exists (`grep` finds nothing); "staged" is a claim about plan, not code, and stage promotion on a corpus that contains the shadow's own grants is not honest measurement — so `ask_to_see` (`adjudicate.rs:2678,2787`) building `AuthorisationTrail::default()` must close before any scope widens. Position 1's queue-scope claim is right for an operator's `allow_session` (`answers.rs:495-526`, the card says so) and wrong for a shadow grant; position 3 is right that two models coexist, but findings 1-2 buy more safety today than a seam rewrite.


### Round 1, position 3 - Claude sonnet

P9 r1, reviewer 3 (position 3: two models, retire Relay before stage 1 widens). All refs at 9e9312b06.

THESIS
The shadow's acting path (R317) is a second authorisation model. It cites a rule string, not a trail index, and it never touches AuthorisationOracle. Its guarantees are local conventions: a substring match, a lexical denylist, and an in-memory breaker. Stage 1 would widen a path that has no tier, no trail and no persisted breaker. The oracle seam should be the only door. Relay should be reduced to an annotator first.

FINDINGS

1. HIGH. The cited rule is never checked against the call. `shadow/permission.rs:272-282 acting_rule` accepts any model-quoted substring of at least 8 bytes (`MIN_QUOTE`, `verdict.rs:12`) that appears in any listed allow rule (`rules_of`, `:476`, formatted "permission pattern"). Nothing checks that the rule's permission is read, or that its pattern covers `path`.
   Scenario: the rules include `bash git status*`. The model answers "allow, rule: git status". The quote passes. `answers.rs:154` returns `grant_ro` for `/var/lib/foo`. The row at `permission.rs:~375` prints "rule: git status" as if it were authority.
   Fix: parse the quote back to one `Rule`. Require its permission to be read and its glob to match the path. Better, have the oracle return the trail index.

2. HIGH. `guard::read_passes` (`shadow/guard.rs:138-165`) is lexical (`lexical()`, `:167`), but the grant is keyed by `view::key` (`tools/src/view.rs:71-78`), which canonicalizes. A path that resolves into the secret store passes the denylist and is stored under its real name.
   Scenario: a repo under review holds a symlink to `~/.config/letibot/keys`. Whether a reviewer's ask can carry the unresolved spelling is HYP, because I did not trace the view check upstream.
   Fix: canonicalize with `view::key` first, then run the denylist on the result.

3. MEDIUM. The audit text lies about scope in one direction. `permission.rs` writes "for that session". Verified: the early return at `answers.rs:154` never inserts into `Answers.relayed` (`:226` is only on the card path), so `take_relayed` is false. `keep_grant` (`adjudicate.rs:1736`) then picks `Scope::Session`. Position 1's "queue-scope grant covers every future reviewer" is therefore false for shadow answers. The operator's card for the same ask, via `queue_scoped` (`answers.rs:178`), grants at `Scope::Queue`.
   Consequence: the identical ask gets a different scope depending on who answers, and nothing records why. Scope follows a side-channel boolean, not the grant.
   Fix: put scope in `Note::Answer`, and have the oracle emit it.

4. MEDIUM. The breaker is in memory (`permission.rs:~197` `Answering`, built at `harness/open.rs:3608`; the text says "observe-only until restart"). Persisted grants survive restart (I51). After a restart the shadow answers again with `disagreements = 0`, over the same shadow-granted rows. A first revoke restarts the count, so the real threshold is 2 revokes per daemon lifetime.
   Fix: persist the disagreement count with the grants, or have the breaker be the oracle's.

5. MEDIUM. Revoke is a path-entry delete (`harnessd/src/grants.rs:85-95`), and it admits that a running session "unbinds at its next call". A command already running keeps its read. The shadow is not the cause, but the shadow's autonomous grants enlarge the exposure.
   Fix: a revoke generation check at exec start, plus a kill of bound children.

6. MEDIUM. `view_read` (`answers.rs:432`) is a structural guess. It requires `Access::Read`, `MayApprove`, a `grant_ro` option and a one-key argument object. The trail is dropped. The only other use of `AuthorisationTrail::default()` is `ask_to_see` (`adjudicate.rs:2787`, R316's gap), where the card is built without one. The corpus therefore holds shadow grants with no trail. R316's replay stages measure the shadow against its own earlier rows (`by == "shadow:..."`, `adjudicate.rs:1712`). That cannot be measured honestly.
   Fix: stamp shadow-answered rows as excluded from the evaluation set. This is a hard precondition for stage 1.

7. LOW. Always-ask: `requires_given` and `ALWAYS_ASK` (`intent.rs:2409`) are not consulted by `note_before`. Reachability is by construction only. `view_read` needs the read class and one `path` argument, so `credential_use`, `changes_its_own_rules` and `persistence` are probably excluded. I did not prove it, so HYP. The guarantee should be one shared predicate, not two filters that happen to agree.

8. LOW. `queue_kind` (`permission.rs:~244`) trusts the `role` string prefix "reviewer of " / suffix "'s gatekeeper". The origin of `role` is `set.asker().role`. I did not verify who can set it. HYP.

CONCESSIONS TO POSITION 2
- The shadow only allows or asks, never denies. Failure falls through to the card.
- Grants are `shadow:<judge>`, listed and revocable through one path (`grants.rs:85`).
- `read_passes` covers secret dirs and ancestors, and `/` and home are rejected.
- The R317 and R305/R314 tests show the intended path works. They do not show the failures above, because no test uses a non-covering rule quote or a symlink.

CONCESSIONS TO POSITION 1
- The shadow's grants are session-scoped, not queue-scoped. Finding 3 corrects that claim. The scope divergence is still real.

AGAINST BOTH
- Position 2's "Layer A settles tiers first" does not describe R317. The shadow path bypasses the oracle and judges rule text, not tier.
- Position 1 attacks a path that is narrow today (reads only). The real defect is architectural. The shadow is a second adjudicator in `answers.rs`. Grants live in four places (`permission.json`, approved shapes, `session_grant`, `ViewGrants`). Each stage widening multiplies those combinations.

PROPOSED ORDER
1. Fix findings 1 and 2 now.
2. Make `Relay` an annotator only. Remove `Note::Answer` from `note_before`.
3. Add a shadow adjudicator behind `AuthorisationOracle` that returns a trail and a scope.
4. Mark shadow rows excluded from replay.
5. Then widen stage 1.

No test run. This was a reading review.
