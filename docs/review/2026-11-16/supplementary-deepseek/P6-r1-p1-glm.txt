THESIS

The gate that lands code does not isolate the box; the gate that isolates the box does not land code. `scripts/gate-at.sh` moves `HOME` and the XDG dirs, but the merge queue's own gate inherits the daemon's entire environment, and the fixture base every harnessd test builds on reads the operator's live config. The isolation that exists is a property of one out-of-tree-shaped shell script, not of the code.

FINDINGS

1. **The queue's gate runs `cargo test --workspace` with the daemon's real `HOME` — critical.**
`crates/harnessd/src/mergequeue/gate.rs:1219-1230` spawns `sh -c <step>` with `env.apply` (`:474-480`), which sets exactly three variables: `CARGO_TARGET_DIR`, `TMPDIR`, `CARGO_BUILD_JOBS`. No `env_clear`, no `HOME`, no `XDG_*`. Compare `scripts/gate-at.sh:54-55`, which moves all of them. Failure: `TODO.md:899-901` records this precise incident happening — a bridge a test started opened `~/.local/share/letibot/shared.db` **writable** and migrated it to schema 49 before the code carrying 49 had landed, "so the live daemons were running against a store newer than their code" — and records that the fix "lives only in that out-of-tree script, so the next gate written from the repo's instructions starts without it". The queue *is* that gate, in-tree. In addition `LETIBOT_STORE`, `LETIBOT_SOCKET` and any credential in the daemon's env reach every step unfiltered. Change: one `fn isolate(cmd)` beside `StepEnv::apply` that clears and rebuilds the environment (`HOME`, `XDG_CONFIG/DATA/STATE/RUNTIME_HOME`, unset `LETIBOT_STORE`/`LETIBOT_SOCKET`/`LETIBOT_PERMISSION`), called from both placements, plus a test that asserts a step sees a `HOME` that is not the daemon's. Host placement not traced (HYP, `gate_host.rs`).

2. **`gate-at.sh` symlinks the fleet private keys into the test HOME — high.** `scripts/gate-at.sh:39-42`: `for f in hosts.toml keys known_hosts; ... ln -s "$HOME/.config/letibot/$f" "$G/home/.config/letibot/$f"`. Every test binary in the run can read real ssh private keys and reach real fleet hosts; `keys` is a symlink to a *directory*, so a test writing `$HOME/.config/letibot/keys/<host>` writes through into the operator's keyring. This is I17 ("never read into a session") defeated by the gate itself. Change: copy, `chmod` read-only, and only the hosts the remote tests name — or give `tests/remote_*` a scripted `ssh`.

3. **The fixture base is the box — high.** `Config::for_this_box` is documented as what "every fixture builds on" (`crates/harnessd/src/config.rs:1689-1692`), and it sets `permission: parse_permission()` (`:1786`), which reads the operator's real `~/.config/letibot/permission.json` and appends `LETIBOT_PERMISSION` from the caller's shell (`:1634-1653`), and `web_search: default_web_search()` (`:1792`, `:1624-1628`), which reads the operator's Brave key. So a fixture's gate ruleset and tool list are the laptop's. Because gate-at.sh moves `HOME` and the queue does not, the same suite judges different gate rules in the two gates. Change: `Default` (empty ruleset, no search) at `:1786`/`:1792`, as `box_dirs` already does at `:1751-1755`; the fixtures that are *about* the file pass their own.

4. **A test reads the operator's `providers.toml` and every provider's key env — medium.** `crates/harnessd/src/config/tests.rs:407` calls `keys::resolve(p, None, None)`, which defaults to `config_file()` (`crates/provider/src/keys.rs:194-201,209`). No key material is printed, but the verdict is the box, and it is green under gate-at.sh and meaningful only on the operator's laptop.

5. **An inherited `LETIBOT_SOCKET` is honoured, and only hand-written scrubbing stops a test.** `harnessd/src/harness/open.rs:1367-1373` puts `LETIBOT_SOCKET`/`LETIBOT_SESSION` into every spawned command; `bridge/src/daemon.rs:217-222` treats it as authoritative. Each test file scrubs it itself (`letibot/tests/dispatch.rs:45-47`, `where.rs:128-131`, `acp/tests/support/mod.rs:66`) — no shared helper, no guard, so the next file that forgets drives the operator's live daemon (`docs/bootstrap.md:177-184`). Change: one test-env helper that returns a `Command`, plus a lint test that no `tests/` file spawns without it.

CONCESSIONS

gate-at.sh does isolate HOME/XDG; `store_at()` returns `None` for `for_this_box` (`config.rs:1661-1662`), so the fixture base opens no store; the socket scrub is done correctly where it is done. Position 2 is right about the script and wrong about the gate that lands. Position 3's diagnosis is the root cause of finding 5 and I agree with it; my fix is the same helper, called from `StepEnv` rather than from each crate.
