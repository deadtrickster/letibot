THESIS: the bridge does not *use* the room — it re-implements it. `letibot_room` is already a normal dependency of `crates/bridge`, with a typed client, typed `Request`/`Response` and a `Message` whose `reach`/`delivered` are the room's own rules; the bridge nonetheless speaks the wire as raw `serde_json::Value` and keeps a second copy of every rule that decides what a reader sees. The copies have already drifted, and the drift is invisible because the only test of the tool surface runs against a fake the same author wrote.

FINDINGS

1. `crates/bridge/src/rooms.rs:529-533,575-577` — high. `delivered()` recomputes `names_you` from the frame's `to`/text and ignores the coordinator's authoritative flag that `reach()` two functions above *does* accept. The daemon had this exact bug and fixed it: `crates/harnessd/src/room/wake.rs:479-487` ("`names_you` is the room's answer, not a reading of the text… it shows names") with the regression test at `:638-646` ("matching the id against it read a message for arango as someone else's"). The coordinator's flag also covers a reply to the seat's own message (`crates/room/src/server.rs:3634-3637`, `answered == Some(name)`), which the bridge's local rule never sees. Scenario: the operator says a line; `cc@x` replies with `thread: <seq>` and no `@`; the coordinator pushes it addressed; the channel notification says `meta.event = "addressed"` and its text says ", passing by" — one message described two ways in one frame. Change: `delivered()` must take the flag (`delivered(m, names_you, me)`), or, better, deserialize `letibot_room::Message` (`crates/room/src/chat.rs:209-210`, `Deserialize`) and call `Message::delivered(names_you, max)`.

2. `crates/bridge/src/rooms.rs:800-875,945-971,1835-1871` — high. A second client: hello, handshake, one reply channel, redial, replay — against `crates/room/src/client.rs:141-301`, and every outbound frame spelled as a `json!` literal whose keys are the wire. A field renamed in `crates/room/src/wire.rs:146-200` compiles here and fails at runtime as an opaque `refused`. Change: `client.rs:369-370` hardcodes `share: false, family: None` — lift those two (plus the `name_in_use` suffix retry at `rooms.rs:818-825`) onto `Client`, rebuild `RoomLink` on it, and keep only the bridge's own bookkeeping. Minimum, without the refactor: one test feeding the fake's recorded frames (`room_tools.rs:230-238`) through `serde_json::from_value::<letibot_room::Request>`.

3. `crates/bridge/src/rooms.rs:400-414` — medium. The copy of `Reach` maps every `fyi` to `passing`; `crates/room/src/chat.rs:396-398` returns `Addressed` for an `fyi` that names the reader. `reach` has no test in `crates/bridge/src/rooms.rs` and no test in `crates/bridge/tests` (grep: one hit, the definition). A project `push_channel` layer written in the room's vocabulary (`plugins/builtin/push/src/lib.rs:35-39` treats `passing` as silence) drops an `fyi` addressed to the seat. Change: `reach` should take a `letibot_room::Message` and return `letibot_room::chat::Reach`, so the compiler, not a test, keeps the two equal.

4. `crates/bridge/src/rooms.rs:117-128,270-309,341-346` — medium. A third derivation of the socket: `room/src/lease.rs:315-320,442` and `harnessd/src/room/mod.rs:38-44` are the others, and the bridge's fallback `./letibot` (`:126`) has no counterpart in `letibot_data_dir()` (`harnessd/src/mergequeue/git.rs:173-179`), so a bare environment makes the bridge look for a coordinator in the working directory. Only `host_key_of` is pinned (`rooms.rs:2285`); nothing pins `socket_path`.

5. `crates/bridge/tests/room_tools.rs:15,164-181,241` — medium. The fake's `names_you` is `to == Some("claude-code") || text.contains("@claude-code")`: no thread/answered, no family, no etiquette, no 4000-byte cap, no budget. So 400 lines of ack/replay/reraise/reraise-on-unseen are proven against an invented server. Findings 1 and 3 could not fail there. Real-`Server` tests exist (`room_share.rs:18`, `room_nick.rs`, `prompt_unheld.rs:324`) but cover connect/share/family only.

CONCESSIONS. R259's ack path is real and its tests bite; the fork had a reason (a bridge needs `share`/`family` the client refuses to send); the host key is genuinely pinned, in both crates; and the real-Server tests do cover identity, so "the real-`Server` tests cover the paths in use" is true for connection and false for the tool surface. I ran no tests here.

ANTICIPATED. Position 1's arrival-order reply matching (`:1277`) and unbounded suffix recursion (`:818-825`) are symptoms of this fork, not independent defects — both vanish with finding 2, and the room's own client has the same single-slot design, so nothing would have compared them. Position 2 should answer why the drift in finding 1 was fixed in `wake.rs` and left standing in `rooms.rs`.
