[model: deepseek/deepseek-flash (the default; the one-shot ignored --model)]
THESIS. The hub is the authority and the store is a follower. `append_items` publishes `TranscriptAppended` from inside the ledger loop (`turn/src/engine.rs:487`), and `submit_items_then` stores afterwards (`harnessd/src/harness/turns.rs:1711` then `:1713`). Nothing in the tree can un-announce a row — `SessionEvent` has no retraction — so every gap below is a row the operator saw and the store does not have, permanently. I1 is not "practically impossible"; it holds for committed rows and fails at every seam where the two orders disagree.

FINDINGS

1. Show before store, no withdrawal. `turn/src/engine.rs:487` emits per item; `turns.rs:1713` `self.persist()?`. A non-busy store error (SQLITE_IOERR, a split file gone) returns from `submit_items_then` after the head has drawn the prompt. Severity high. Scenario: `<data>/projects/<key>.db` is deleted under a running daemon mid-turn; the head shows the user row, the turn fails, a restart opens the parent with no such row. Change: persist the chunk first and emit after the commit (the ledger row already carries the id and head), or add a retraction event and use it.

2. The busy store's "written when it frees" is false. `turns.rs:4504-4507` returns `Ok` with rows unwritten; the notice at `:4495-4500` promises they are "written when it frees", but no thread retries — only a later `persist()` from the same harness (`:4439` resumes at `persisted`). A stopped turn that is the session's last, then a `--restart` (`daemon.rs:205` `exit(130)`), loses them. Severity high. Change: one owed-write record that is either re-driven by the daemon's idle pass or said as lost.

3. The prompt journal has no shutdown barrier. `sync` only `send`s (`sessionlog/src/hub.rs:528-537`); `journal_settled` (`:809`) has zero production callers (only `hub.rs:2521,2537` and `restart.rs:2066`, both tests); `Hub::close` (`:2368`) and `Registry::close` (`registry.rs:2563`) never flush; the signal thread exits by `std::process::exit` after `SERVE_EXIT_GRACE` (`daemon.rs:70,205`). A prompt accepted while a failed save is retrying on its one-second timer (`hub.rs:443`) is lost by the very `--restart` it was queued for. Severity medium. Change: `journal_settled(2s)` in `Hub::close`, before `Bye`.

4. Room history is destroyed by the store's own healing. `put_item` trims, then `close()`es the row (`room/src/store.rs:176-186`); `append` failing is only an `eprintln` (`:360-366`); `write` then `compact()`s (`:339`), and `compact` rewrites the live file from the shadow (`:373-424`) which no longer holds the trimmed row. Neither file is ever fsynced (no `sync_all` in `crates/room`). `open` (`:91-139`) skips a torn line and does not repair a missing trailing `\n`, and `append` is `O_APPEND` (`:353-357`), so the first record written after a restart glues onto the fragment and is lost too. Severity high — the module doc claims "a failed write is healed by the next compaction", which is exactly backwards for a trimmed row. Change: close before trim commits nothing until `.items-closed` has the bytes, and repair the trailing newline in `open`.

5. Migration is not one transaction and two arms are not idempotent. `store.rs:1932` and `:1951` are bare `ALTER TABLE ... ADD COLUMN`; the version is stamped once at `:1870-1874`. Every later arm is pragma-guarded, so only these two brick — and `StoreSet::create` (`store/split.rs:442-459`) has no cross-process lock, so two daemons opening one `shared.db` after an upgrade can race. A crash or the loser gets `duplicate column name` on every subsequent open. Severity medium.

CONCESSIONS. The append-only triggers (`store.rs:526-538`), `synchronous=FULL` (`:1608`), the atomic journal replace (`store/prompts.rs:41-67`), the pre-fork flush (`wall.rs:1721`) and `delete_empty_session`'s refusal (`:3980-3992`) are real and good.

ANTICIPATION. Position 2 will call these microsecond windows; findings 2, 3 and 4 are not crashes at all, they are ordinary paths. Position 3 will say skew is unprovable; I hand them the missing tests: no failure-injected `persist` with a drawn row, no restart with a torn trailing line, no two-daemon migration.
