THESIS: For the workload this box actually runs — one data directory, a handful of daemons, an additive schema bump every few days — the store's migration and durability machinery is sound, and its two load-bearing guards fail on the *class* of bug rather than on a list a hand keeps in step. Position 1's corruption story needs a path where an older reader silently misreads, or a migration half-lands. I traced both and could not find one: every skew path I found refuses by name.

1. The durability story is the floor, not `synchronous=FULL`. `store.rs:1608` only covers a commit that reaches disk; the interesting case is a daemon that outlives a migration. `open_newer` (`floor.rs:205-224`) opens a store ahead of this build when the floor allows it and refuses with the fix in the sentence when it does not (`tests.rs:3043`, `:3087` — fails closed when no floor was recorded). Better, the queue lease re-reads the version *inside its own transaction* (`queues.rs:1377-1379`, `stored_schema_version` `:783`), so a daemon already running learns about skew at the lease rather than at a failed write, and `LeaseOutcome::WrongSchema` is announced once and the lease not taken (`serve.rs:3717-3723`). Failure prevented: yesterday's daemon silently misreading a 51→52 bump. Severity: none — HOLDS. Missing test: a second process opening during a migration.

2. The untransacted migration is idempotent by construction, so the window is benign. `migrate` (`store.rs:1848`) runs arms outside a transaction and `DELETE FROM schema_version` (`:1870`) precedes its INSERT. I checked the consequence, not the comment: all 17 DDL statements in `SCHEMA_SQL` (`store.rs:227-545`) are `IF NOT EXISTS`, and the block holds no bare INSERT/UPDATE/DELETE. A crash there lands the store on the `None` arm (`:1892`) and `SCHEMA_SQL` (`:1894`), where every CREATE is a no-op — stamped at `SCHEMA_VERSION` with rows intact. Both recent arms re-check before ALTER (`:2617`, `:2622`). Severity low.

3. The split coverage test is a source scan with a transitive closure, which is why it catches what R313 was. `split_coverage_tests.rs:113-161` marks each fn naming a project table, closes over `self.`/`Self::`/`store.` calls (`:139-156`), then fails any public method in that set `EXERCISED` (`:164`) does not call (`:253-266`). A new unrouted method is red by construction. Gap: it sees no `tx.`/`conn.` and cannot see a `format!`ed table name. Proposed: add those patterns at `:145`.

4. Append-only is enforced *through* the one path that copies rows. The insert trigger demands `NEW.seq = MAX(seq)+1` (`store.rs:538-551`); the export orders `transcript_item` by `transcript_id, seq` (`transfer.rs:35`), and the import refuses an overlapping row whose `h_k` differs (`transfer.rs:491-530`) rather than overwriting. "Rows cannot be recreated" survives the transfer.

CONCESSIONS. "Unwind and reopen per version" overstates: it is ~13 versions (`tests.rs:614,723,1382,1487,1575,1668,2114,2660,3179,3601,3731`), not 50; the rest of the argument is that additive arms share one shape. And `import_tx` (`transfer.rs:312-338`) commits two files in sequence with nothing marking a half-import. Proposed: a marker row beside `carved_project` (`split.rs:34`).

ANTICIPATE. Position 1 must produce a *silent* path; the ones I traced all refuse by name — `SchemaTooNew`, `WrongSchema`, `unsplit` (`split.rs:648-657`), and `open_transition` refusing a mid-carve key with the fix spelled out (`split.rs:588-594`). "No lock" is real, but by finding 2 its cost is a re-run, not a corrupt file. Position 3's complexity complaint is fair and mostly cosmetic: the carve state, the string-replaced FKs (`split.rs:308`) and out-of-order arms 19/20/21 cost lines, not correctness — `every_migration_arm_declares_whether_it_breaks_a_reader` (`tests.rs:2940`) compares the arm *set* against the source, so sequence is not a claim the code makes.
