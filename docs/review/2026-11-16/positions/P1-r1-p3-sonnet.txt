P1 R1, reviewer 3 (position 3: no captured old-build frames, no two-build test, so skew behaviour is unknown)

THESIS
Every skew claim in the code (compat::OlderHead, protocol_skew, "Everything this head reads is fine", room "12 only added frames a client must ask for") is a comment-backed assertion. The tests I read build frames with the current serde types or hand-written JSON. They never replay bytes recorded from an older build. The one structural guard, `every_frame_is_accounted_for_at_this_version` (sessionlog/src/protocol/tests.rs:6, :161), is a match over variant names plus `assert_eq!(PROTOCOL_VERSION, 78)`. It catches a new variant. It does not catch a changed field, a changed meaning, or a changed default, and it ties the number to a comment, not to bytes. Position 1 finds individual skews. Position 2 argues the policy. Both rest on behaviour nobody has measured.

FINDINGS
1. HIGH. No golden frames. Tests that decode JSON (protocol/tests.rs:414-541, :766) use hand-written strings. `every_frame_round_trips` (:598) uses the current types on both ends, so it only proves self-consistency. Failure: a frame field is renamed or retyped without a bump (the mechanism behind room `Prompt.from`, invariants I34). Round-trip stays green, and the only evidence is a field silently defaulting on a mixed fleet. Change: check in one JSON line per ClientFrame, ServerFrame and SessionEvent variant, captured from a tagged build (v76, v77, v78, room 11 and 12). Add a test that the current build decodes every line and that each decoded value has the expected semantic, not just that decoding succeeds. Version-gate it with the bump test, so a bump must add a corpus file.

2. HIGH. Serde defaults carry no meaning check. More than 30 `#[serde(default)]` fields in protocol.rs (e.g. :85, :300-:628). A head built before 78 reading `ToolResult` without `ran_ms` and `decision` is fine. The reverse direction, an old daemon sending the new head a row without them, relies on the same default, and nothing tests that `decision: None` renders as "unknown" and not as "ungated". HYP on the UI result. Change: golden test the 77-to-78 pair in both directions.

3. HIGH. No two-build test. `compat::OlderHead` (sessionlog/src/compat.rs:13-157) emulates an older head from inside the current build, using `TURN_ENDED_SINCE - 1`. It is a model of v75, not v75. If the emulation and the real build disagree, the test passes and the fleet breaks. Change: a CI job that runs the previous release tag's head binary against the current harnessd, and the reverse. This is cheap here because `act` and the fleet boxes are available.

4. MEDIUM. The session wire has an unbounded read. `FrameReader::read` (sessionlog/src/wire.rs:62) calls `read_line` with no cap. It is used by the server at server.rs:313, :712, :793 and the client at client.rs:1037. A mismatched or hostile peer that sends bytes with no newline grows `self.line` without limit. The room server bounds this (room/src/server.rs:4987-4993, `take(MAX_FRAME_BYTES+1)`). The room client does not (room/src/client.rs:595). Compare the invariant at server.rs:731: the daemon accepts any version, so this is reachable by skew. Change: apply the room's bounded `read_until` in wire.rs, answer with `Bye` naming the limit, and test it.

5. MEDIUM. I33 is contradicted in the code. The doc comment says "refuse a mismatch by name" (protocol.rs:12-14), and server.rs:731-739 accepts and logs to stderr only. The `protocol_skew` text for an OLDER daemon (protocol.rs:260) says "The session can end on the next command the two do not share". That is the design: the skew surfaces at the first unreadable frame, via `Bye` (server.rs:2146-2157), and the session closes. Failure: a head older than the daemon sends a frame the daemon cannot parse mid-turn. The TUI is seated read-only per invariants.md, but the bridge prompts anyway (seams.md:216, which I did not verify in code). Fix the comment, and add the two-build test from 3 to show the real outcome.

6. MEDIUM. Room version policy has no test of the old client. Room is 12, OLDEST_CLIENT is 11 (room/src/wire.rs:15,19). The justification "12 only added frames a client must ask for" is a comment. `MayPrompt` and Hello `share`/`family` were added under that number (I34). room/tests/wire.rs only uses ROOM_PROTOCOL_VERSION and `+1` (:212). No test sends an 11-client Hello and a full sequence. Change: a recorded v11 session transcript replayed against the coordinator.

CONCESSIONS
- Position 2 is right that accept-and-say beats refusal for a mixed fleet. The `Bye` naming both builds (server.rs:2146) is good, and `protocol_skew` is precise. I am not arguing for refusal.
- Position 1 is right about the room bump hygiene and the I34 gaps. My point is that they are only visible by reading history. A corpus makes them mechanical.
- The room server's bounded reader and the `every_frame_is_accounted_for` signpost are real controls. I only claim they are insufficient.
- I ran no test. Everything here is from reading 9e9312b06. The rano copy (`src/letibot.rs`) I did not read. HYP: it has the same gap, with no corpus on its side either.

PROPOSAL, in order: golden corpus, then two-build CI, then bounded reader.
