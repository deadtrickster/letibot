[model: deepseek/deepseek-flash (the default; the one-shot ignored --model)]
**Thesis.** The launcher's proof surface is real and layered — 1,714 lines of `tests/launcher.sh`, `no_hang.rs`'s two hung-manager cases, a two-directional `check-dist-names.sh`, and a config reference whose drift checks are driven by the real parsers. But it is strong exactly where the launcher is thin and blind exactly where it is deep: it proves *acceptance* (a flag is known, a page exists) and never proves *routing* (a word reaches Rust instead of a model), and the config probes cover the Rust parsers and not the launcher's own bash reader. Position 2 is true as a description of what exists; it is false as a claim that the launcher is covered.

**Findings.**

1. `letibot where`, `letibot hold`, `letibot release` are paid prompts — **critical**. `scripts/letibot:2737` whitelists `stats | boundary | fb | holds | gc`; `crates/letibot/src/main.rs:293-307` also implements `hold`, `release`, `where`; `scripts/letibot:931` advertises `where` among the verbs with a page. The case has no `*)` arm (ends `esac` at `:2824`), so no-arm means fall-through: `:2993-3006` sends `"$*"` as `--prompt` to a one-shot harnessd. `letibot where --json` therefore spends a model turn and runs a tool-capable one-shot in the operator's workspace; `letibot hold S` silently holds nothing while the lifecycle reaper closes the session. Failure: an editor panel shelling out `letibot where`, or an operator calling the documented verb, gets neither answer. Fix: one `where | hold | release)` arm beside `:2737`, or a `*)` refuse for any first word the multicall implements; and walk `:931`'s VERBS line from `tests/launcher.sh` the way `:427-438` walks the flag list.

2. The launcher and the daemon read different `providers.toml` — **high**. `scripts/letibot:1095` hardcodes `$HOME/.config/letibot/providers.toml` and ignores `XDG_CONFIG_HOME` (which `:2019` honours elsewhere); `crates/provider/src/keys.rs:194-200` honours it. With `XDG_CONFIG_HOME` set — common, and not exotic — `--status`, `model_home` and `default_provider` answer from one file while the daemon takes keys and `[default]` from another: the launcher invents an `--endpoint` for a model the daemon's file does not name, or reports "asks for a model on first use" for a daemon that has one. The comment at `:1093` ("points both readers at another file") is false for `LETIBOT_PROVIDERS`, which nothing under `crates/` reads. Fix: derive `PROVIDERS` from the same resolver as `plugins::paths::config_dir`.

3. `keys::config_file` does not filter an empty value — **medium**. `crates/provider/src/keys.rs:195-196` maps `""` to `PathBuf::from("")`, giving the relative `letibot/providers.toml`, i.e. resolved against the daemon's cwd — the workspace. A checkout holding `letibot/providers.toml` then supplies the daemon's provider and defaults. `crates/plugins/src/paths.rs:36-43` states and implements the opposite rule, and `crates/leticode-config/Cargo.toml:20-23` asserts there is one such function. Fix: call that function.

4. `no_hang.rs` never tests the case it exists for — **low**. The `systemd-run` stub answers at 6 s (`crates/letibot/tests/no_hang.rs:104-107`, "so the backgrounded probe ends inside the test"), while `scripts/letibot:226-249` deliberately leaves a timed-out probe running and `:235-236` reaps only probe dirs that *have* an answer — so a wedged manager leaks one dir per launcher run, forever. Fix: a stub that never answers, and an `-mmin` sweep that also drops unanswered dirs older than the daemon's own wait.

**Concessions.** `check-dist-names.sh` is genuinely two-directional (`:44-115`, `:127-145`, `:174-192`) — but its `triple:` grep drops `$`-interpolated matrix values (`:36`), so a renamed workflow key vanishes silently. The config-ref probes are real (`probe.rs:178-221`, with exact field/key comparisons at `provider/src/keys.rs:1626`, `harnessd/src/mergequeue/settings.rs:841-847`, `tools/src/docker/config.rs:278-285`) — and they say nothing about finding 2, which is bash reading TOML.

**Against the others.** Position 1 names three verbs; the defect is the missing `*)` arm, so the next multicall verb repeats it — and it misses the config split, which makes the launcher's *reports* wrong, not just its dispatch. Position 3 is right that 3,173 lines of placement is too much bash, but a port would not have caught finding 1: the dispatch table would still be a whitelist, and it is the launcher suite that must walk it.
