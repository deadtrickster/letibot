THESIS. Positions 1 and 2 both argue about the queue's machinery. I argue the thing underneath both: "green" is not one fact in this tree. The definition of the gate now lives in five machine-read places, and two of them change the rule by machine rather than by decision. So an approved sha (2) and a landed row (1) are both sound *relative to an undocumented local meaning of AGENTS.md:73-82*.

FINDINGS.

1. The merge gate runs in the daemon's environment. gate.rs:474-480 (`StepEnv::apply`) sets only `CARGO_TARGET_DIR`, `TMPDIR`, `CARGO_BUILD_JOBS`; run_step spawns `sh -c` (gate.rs:1219-1238) with no `env_clear`. Every step inherits HOME, XDG_*, `LETIBOT_*`, `SSH_AUTH_SOCK`, provider keys. With `LETIBOT_REQUIRE_APPARATUS=1` (AGENTS.md:77) apparatus present on the operator's box is *demanded*, so box-dependent tests run instead of skipping — config/tests.rs:42-56 calls `Config::for_this_box` (HYP: mechanism per invariants I18). A red target then halts landings (serve.rs:1958, :2072). This repository already knows the hazard: gate-at.sh:30-31,52-55 moves HOME/XDG for exactly this reason — the convenience script isolates, the merge gate does not. HIGH. Change: `StepEnv::apply` clears the env, homes into the run's GateScratch, drops `LETIBOT_*`.

2. The same step means a different rule on a host. `apparatus_prefix` (gate_host.rs:100-108) strips `LETIBOT_REQUIRE_APPARATUS=1` when the host cannot meet it, and the run is still `Passed` (evidence at :62-80). The local runner keeps the demand (gate.rs:1219-1230; asserted at gate_host/tests.rs:507-519). start_gate picks ONE runner for every step (serve.rs:784, :799). So `[queue] gate_host` silently makes AGENTS.md:77 mean "skip is a pass", and a commit whose only breakage is in a cgroup/bwrap test lands green. The parse is a prefix match on one shell line, so `env LETIBOT_REQUIRE_APPARATUS=1 cargo test …` defeats it and turns a host red for infra. HIGH. Change: demand as a field the runner reads, or refuse (Blocked) instead of stripping.

3. Install runs wherever the gate ran. start_gate's single runner (serve.rs:784) also runs the install steps (serve.rs:3030-3043, :3219-3226). With gate_host, `install-gate-build.sh` installs on the remote box; `finish_install` records it (:861-865). `Pushed::NoRemote` sets `may_install=true` (:3026). AGENTS.md:108-111 promises a copy into this box's `target/release`. MEDIUM-HIGH (mechanism of 1's item, not the bug). Change: install always with the local runner; NoRemote does not install.

4. The hand gate is a different gate. gate-at.sh:55 discards cargo's exit status, :58-61 judges by `ok -lt 140`, and no clippy/attrs/dist-names/release step runs though its own header calls it "the local landing gate" (:3). docs/gate.md:57 says AGENTS.md "is the definition", then prints six steps to AGENTS.md's eight; rrun:108-111 prints a third set. MEDIUM. Change: gate-at.sh feeds `parse_merge_gate` over AGENTS.md — one source, one parser already written.

5. No gate lock in the queue. grep for `gate.lock` in mergequeue: zero hits; only gate-at.sh:48-50 takes it. A lead's gate-at.sh and the queue's gate run full workspace suites concurrently, and tests/rrun.sh's fixed unit names collide. MEDIUM. Change: the queue holds the same flock.

6. Scale, measured (not rhetoric): 35,170 lines of mergequeue — 19,046 top-level + 16,124 submodules, ~15k of it `*tests.rs`, all pinning the queue's view while nothing tests the hand copies (gate-at.sh, per seams.md:261). Nine places decide what a step means. MEDIUM as a cause, not a symptom.
