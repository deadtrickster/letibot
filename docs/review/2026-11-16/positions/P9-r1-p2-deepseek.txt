THESIS. The staged design holds, and I can show it from code rather than intent: the shadow's acting path is bounded four ways at once — read-only and `MayApprove` only (`crates/harnessd/src/answers.rs:432-439`), review-queue seats only (`crates/harnessd/src/shadow/permission.rs:250-268`), a path past `read_passes` (`:266`), and `allow`-with-a-listed-rule only (`:272-283`). Its grants are session-scoped, not queue-scoped (`crates/tools/src/adjudicate.rs:1736-1738`, asserted at `crates/harnessd/src/answers/escalate_tests.rs:1061`), and the always-ask list cannot reach it at all: `view_read` requires `Tier::MayApprove`, and `AlwaysAsk` blocks the model's admit (`adjudicate.rs:3559`), the session rung (`:3639`) and any allow rule (`:3362`). The gaps that remain are in the *bound on the model*, not in the architecture, and each is one function.

FINDINGS.

1. `read_passes` is the only bound on what the model may grant, and it misses credential files. `shadow/guard.rs:138-165` refuses secret stores, `keys` components, `intent::secret_dirs()` (`crates/tools/src/intent.rs:1554-1565`) and `SECRET_FILE_NAMES` (`:1571`). Gap: `crates/tools/src/intent.rs` classifies `/proc`, `/dev`, `/sys` as `Region::Device` but `guard.rs` never asks; `~/bin/fleet` (I17) matches no store and no file name.
Severity: high. Scenario: a reviewer asks to read `/proc/1234/environ`; `read_passes` returns `Ok`; the shadow quotes a rule and the grant lands in the reviewer's view, so a same-user process's tokens become readable with no card. Proposed: refuse `Region::Device` outright, and run the fetched path through the fence's own secret check instead of a second list. Add both paths to the deny test at `escalate_tests.rs:968`.

2. `acting_rule` ties the quote to *any* allow rule, not to a read rule nor to the path: `permission.rs:281` accepts `rule.len() >= 8` and a substring of any line `rules_of` produced (`:476-481`).
Severity: medium. Scenario: `permission.json` holds `bash clippy-driver *`; the shadow answers "allow" citing `clippy-driver`; the row and the store record name an exec rule for a path read, so the operator's audit cannot reconstruct the authority. Proposed: the matched rule must have permission `read` and its pattern must cover the path; keep the fragment test as a second gate.

3. The breaker is process state while its grants are store rows: `Answering` holds `disagreements` in memory (`permission.rs:174-176`, tripping at `:231`) and resets at restart, while `Kept::View` rows persist (`crates/tokencore/src/store/grants.rs`).
Severity: medium. Scenario: two operator revokes trip the breaker; a restart restores `answer_reads` with zero disagreements and every path it granted still bound. Proposed: keep the count (or a trip) in a row read at open; refuse to answer until the operator clears it.

4. `GENERATION` is a process-wide atomic (`crates/tools/src/grant_ledger.rs:17`) and `refresh_grants` returns early when it has not moved (`adjudicate.rs:1659-1662`), silently keeping the old copy on a read error (`:1667`).
Severity: medium. Scenario: a queue reviewer's gate in the folder's daemon keeps a path after the operator revokes it at the gatekeeper's head, until reopen. Proposed: make the generation check fail-safe for view claims — load, or compare a store-side max row id.

CONCESSIONS. No `ShadowOracle` exists (`grep` finds nothing); "staged" is a claim about plan, not code, and stage promotion on a corpus that contains the shadow's own grants is not honest measurement — so `ask_to_see` (`adjudicate.rs:2678,2787`) building `AuthorisationTrail::default()` must close before any scope widens. Position 1's queue-scope claim is right for an operator's `allow_session` (`answers.rs:495-526`, the card says so) and wrong for a shadow grant; position 3 is right that two models coexist, but findings 1-2 buy more safety today than a seam rewrite.
