[model: kimi-code-global (the preset's default model)]
Thesis: I2 is enforced by two hand-maintained tables, not by the record’s type. The warning destination table covers only warnings in `TABLE`; `TranscriptItem` still admits operator-only rows, and the “twin” table is prose, not evidence that the model got a row. The implementation is poor for that reason regardless of whether today’s workloads lose data.

Findings:

1. Operator-only rows are a first-class variant. `crates/transcript/src/lib.rs:219-225` defines `Offer` as “display-only”; `crates/harnessd/src/restart.rs:504-509` classes it and `SegmentMark` as rows “the model never reads”; the head draws them at `crates/tui/src/ui/transcript/item.rs:228-237`, while every request renderer discards them (`crates/provider/src/messages.rs:377`). Scenario: the shadow allows a read and appends its `Offer` row (`crates/harnessd/src/harness/shadow_seat.rs:38-51`); the operator sees an authorisation the model was never told about, and a head-only fact is now in the model transcript’s row numbering. Severity high. Change: remove display-only data from `TranscriptItem`; give head-only facts their own durable event/type, or make the row door take an explicit audience and have request renderers reject head-only rows at compile time.

2. The destination table is incomplete and string-typed. `Hub::warn` accepts any `String` (`crates/sessionlog/src/hub.rs:1095-1112`); an unknown code is deliberately Routine/Notes (`warning.rs:1284-1302`). `lifecycle()` emits `format!("lifecycle_{event}")` (`crates/harnessd/src/harness/open.rs:3879,3924`), which `warning_codes.rs:126-167` cannot discover from a format string and `TABLE` does not name. Scenario: a lifecycle layer’s failed `room_say` arrives as routine `/notes` text, occasionally and untested. Severity medium. Change: a warning-code newtype constructed only from a registered table, with exhaustive destination computed at construction; dynamic families must register a prefix rather than bypass the census.

3. Warnings moved “beside” the conversation have no durable copy. `SessionView` keeps at most 128 warnings in memory and drains the oldest (`crates/sessionlog/src/view.rs:339-350,761-768`); restart republishes transcript rows only (`crates/harnessd/src/harness/open.rs:4245-4276`); metrics records the code but not the detail (`crates/sessionlog/src/metrics_tap.rs:108-115`). Scenario: `operator_shell_failed` or `todos_not_stored` is raised, then the daemon restarts; `/notes` loses the sentence that said what failed and how to recover. Severity high. Change: persist every disclosure in an append-only table with fact id, code, detail, time and audience, replay it into snapshots, and age it out by archive rather than deletion.

4. Proving a model twin does not prove the model’s row exists. `TWIN` maps a code to an explanatory string (`warning.rs:1151-1203`); its test only checks that string is long and the code classified (`:1505-1517`). The TUI test synthesises both rows (`crates/tui/src/app/tests/onevent.rs:36-58`), so a production path that stopped writing the notice stays green while `Go::Model` suppresses the warning. Severity medium. Change: make the notice and warning one event carrying both audiences, or bind each twin to a real event constructor and assert the production pair end to end.

Concessions: Position 1 is right that emission precedes persistence (`crates/turn/src/engine.rs:486-493`, `crates/harnessd/src/harness/turns.rs:1711-1713`); reordering alone would not cure findings 3-4, and shadow rows are discarded after `take_rows` when append fails (`shadow_seat.rs:50,374`). Position 2 is right that append-only triggers and `synchronous=FULL` protect committed SQLite rows (`tokencore/src/store.rs:526-534,1602-1609`); they cannot protect rows not yet stored, in-memory warnings, or a head-only display.
