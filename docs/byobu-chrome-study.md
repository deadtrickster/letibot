# byobu's chrome — how it composes, how a click lands, and what letibot should take

Written 2026-10-06 on `lab2x1`, against **byobu 6.11** and **tmux 3.6** as installed on this
box (`/usr/share/byobu/`, `/usr/bin/byobu`, `/usr/bin/byobu-status`, `/usr/lib/byobu/`), and
against **letibot at `501f1ee`** ("Merge branch 'agent/vt-one'"), on the worktree
`agent/byobu-study`. Every letibot citation resolves at that commit and only there.

The operator's framing, in their words: *"look how it composes — right now my status bar and
window switcher even support mouse clicks"* and *"it does exactly what we want - embedding"*.

Nothing in this document changed any code. Nothing was run against the operator's live tmux
server (`/tmp/tmux-1000/default`, up since 2026-09-15) or their live byobu config: every
measurement used a private `TMUX_TMPDIR` and a private `-L` socket, and every server started
for a measurement was killed in the same command.

---

## 0. Evidence, and the five marks

Five kinds of evidence appear below and they are not equivalent. The marks are inline on
every claim.

| mark | means |
|---|---|
| `[local file:line]` | a file **on this box**, read; path and line given |
| `[man page]` | `man tmux`, `man byobu` on this box (`/usr/share/man/man1/`) |
| `[page]` | a page fetched; the URL is given |
| `[local run]` | **I ran it here** and the command and output are given. The strongest mark for behaviour |
| `[recalled]` | my own memory, unverified. A lead, not a fact |

Two of the claims that decide §1 rest on `[local run]` alone, because neither tmux nor byobu
will print a *rendered* status line: `capture-pane` does not capture the status row, and
`display-message -p` expands a format without the renderer's layout pass. Both were read by
attaching a real client and reconstructing the grid two independent ways — a Python pty
reader, and **tmux itself** as the outer emulator (`capture-pane` of a pane running the inner
tmux). The two agree character for character, which is the reason to trust them.

## 1. How the chrome is composed

### 1.1 The whole of byobu is a launcher and a config directory

`byobu` is a shell script that ends in `exec`:

```
exec tmux -u $SCREEN_TERM $BYOBU_PROFILE "$@"
```

`[local /usr/bin/byobu:262]`, with `BYOBU_PROFILE="-f $BYOBU_PREFIX/share/byobu/profiles/tmuxrc"`
`[local /usr/bin/byobu:159]`. `man byobu` says the same thing: *"byobu is a script that
launches a text based window manager (either screen(1) or tmux(1)) in the byobu
configuration"* `[man page]`.

That config file is five `source-file` lines `[local /usr/share/byobu/profiles/tmuxrc:25-30]`,
and they are the whole composition, in order:

```
source-file $BYOBU_CONFIG_DIR/color.tmux       # the four palette variables
source-file $BYOBU_CONFIG_DIR/datetime.tmux    # BYOBU_DATE, BYOBU_TIME
source-file $BYOBU_CONFIG_DIR/profile.tmux     # -> profiles/tmux: every tmux option
source-file $BYOBU_CONFIG_DIR/keybindings.tmux
source-file $BYOBU_CONFIG_DIR/.tmux.conf       # the user's own, LAST, so it wins
```

Those files do not ship with byobu; `byobu-janitor` seeds them on first run
`[local /usr/bin/byobu-janitor:77-96]`, including `color.tmux` generated by stripping
`export ` off `include/colors` `[local /usr/bin/byobu-janitor:78]`. **byobu owns no state a
tmux option cannot express.** The last line is why the operator's own `.tmux.conf` can set
`status-left ""` and win `[local ~/.emacs.d/byobu/.tmux.conf:52-56]`.

### 1.2 A segment is a shell function, invoked by name, cached by a prime

The status line is two tmux options `[local /usr/share/byobu/profiles/tmux:72-77]`:

```
set -g status-style bg=$BYOBU_DARK,fg=$BYOBU_LIGHT
set -g status-interval 1
set -g status-left-length 256
set -g status-right-length 256
set -g status-left '#(byobu-status tmux_left)'
set -g status-right '#(byobu-status tmux_right)'$BYOBU_DATE$BYOBU_TIME
```

`#(...)` is tmux running a shell command and inserting **the last line of its output**
`[man page]`. So each half of the bar is one process per tick, and that process walks the
segment list `[local /usr/bin/byobu-status:110-153]`:

```sh
case "$1" in
	*left|*right)
		eval items="\$$1"
		for i in $items; do
			...
			case "$i" in \#*) continue ;; esac
			get_status "$i"
		done
	;;
esac
```

The lists themselves are `tmux_left` and `tmux_right` in `status`
`[local /usr/share/byobu/status/status:33-35]`, and `#` means *disabled* — the file is
`[local /usr/share/byobu/status/status:24]`. The defaults enable, left to right:
`logo release session` on the left, and
`raid reboot_required updates_available uptime load_average cpu_count cpu_freq memory disk
date time` on the right.

A segment is a file under `/usr/lib/byobu/` defining `__name`; `get_status` sources it and
calls it `[local /usr/bin/byobu-status:73-108]`. The caching is the interesting part and it is
**per segment**, keyed on wall-clock uptime, not on ticks
`[local /usr/bin/byobu-status:91-107]`:

```sh
status_freq "$function"
local expiry=$(($lastrun+$_RET))
find_script "$function" && . "${_RET}"
if [ $NOW -ge $expiry ] || [ "$lastrun" = "0" ]; then
	"__$function" > "$cachepath".new
fi
```

and `status_freq` is a table of **prime** intervals `[local /usr/lib/byobu/include/shutil:229-280]`:

```
cpu_freq)	_RET=2 ;;      load_average)	_RET=2 ;;
network)	_RET=3 ;;      disk_io)	_RET=3 ;;
memory)		_RET=13 ;;     disk)		_RET=13 ;;
uptime)		_RET=29 ;;     release)	_RET=599 ;;
whoami)		_RET=86029 ;;  logo|session|date|time) _RET=9999991 ;;
```

The header of that table states the reason: *"Use prime number intervals, to decrease
collisions, which yields some less expensive status updates"*
`[local /usr/lib/byobu/include/shutil:230-236]`.

**Measured cost** `[local run]`: `byobu-status tmux_right` warm is ~9.6 ms per call (50
iterations, caches present); cold, with `status.tmux` and `.last.tmux` removed before each
call, ~16.8 ms (5 iterations). `strace -f -c -e trace=process` on a warm call shows 7 process
creations. At `status-interval 1` that is two such calls a second, ~19 ms of shell per second
— and tmux does not wait for them: *"tmux does not wait for `#()` commands to finish; instead,
the previous result from running the same command is used"* `[man page]`.

### 1.3 Two clocks, and neither belongs to byobu

There are two independent cadences and they are not synchronised:

| clock | owner | period | evidence |
|---|---|---|---|
| the bar redraws | tmux | `status-interval 1` | `[local /usr/share/byobu/profiles/tmux:73]` |
| a segment re-runs | byobu | the prime table | `[local /usr/lib/byobu/include/shutil:229-280]` |
| a `#()` command's output | tmux | *"the status line will not be updated more than once a second"* | `[man page]` |

So the bar is *sampled* at 1 Hz and each segment is *stale by up to its own prime*. A
`load_average` is at most 2 s old; `whoami` is effectively constant and is computed once
(86029 s). The 1 Hz floor is not byobu's choice and cannot be lowered through byobu.

### 1.4 Colour and separators are the segment's own business

Colour is not a status-format concern in byobu. There are four palette variables —
`BYOBU_DARK`, `BYOBU_LIGHT`, `BYOBU_ACCENT`, `BYOBU_HIGHLIGHT`
`[local /usr/lib/byobu/include/colors:25-34]` — and they are used for two different things:

* **the bar as a whole**, via tmux options: `status-style bg=$BYOBU_DARK,fg=$BYOBU_LIGHT`
  and the four `window-status-*-style` lines `[local /usr/share/byobu/profiles/tmux:53-56,72]`;
* **each segment's own colours**, emitted as **tmux style escapes inside the segment's
  output**. Measured: `byobu-status tmux_right` prints 996 characters of which 950 are
  `#[...]` escapes and 46 are text `[local run]`:

```
#[default]#[fg=brightred,bold,bg=black](R)#[default]#[fg=#EEEEEE]#[bg=#333333] #[default]#[fg=blue,bg=white]20d19h#…
```

There is no separator option anywhere in byobu's tmux profile `[local /usr/share/byobu/profiles/tmux]`
and no `window-status-separator` line in it either — the separator between segments is
whatever the last segment's output ends with, and the separator between window-list entries
is tmux's default, a single space
(`tmux show-options -gw window-status-separator` → `" "` `[local run]`).

The one piece of colour that *is* structured is the screen-only path: `byobu-status color`
prints `$ESC{= $BACKGROUND$FOREGROUND}` `[local /usr/bin/byobu-status:176-180]`, and
`ESC` is `"\005"` for screen and **empty** for tmux `[local /usr/lib/byobu/include/constants:40-46]`
— i.e. on the tmux backend the `color` segment is a no-op `[local /usr/lib/byobu/color:28-35]`.
The old screen quadrant model is dead code on this box.

### 1.5 The window list is not byobu's at all

The operator says *"my status bar and window switcher even support mouse clicks"*. The
switcher is **tmux's**, in the middle of tmux's default `status-format`, and byobu never
touches it: `grep -n "window-status" /usr/share/byobu/profiles/tmux` returns four `*-style`
lines and nothing that changes the format `[local run]`.

The default, read off this box `[local run]` (`tmux -L p -f /dev/null show-options -g status-format`),
is one line, and it is the whole of the composition:

```
#[align=left range=left #{E:status-left-style}]#[push-default]#{T;=/#{status-left-length}:status-left}#[pop-default]
#[norange default]#[list=on align=#{status-justify}]#[list=left-marker]<#[list=right-marker]>#[list=on]
#{W:#[range=window|#{window_index} …]#{T:window-status-format}…,
     #[range=window|#{window_index} list=focus …]#{T:window-status-current-format}…}
#[nolist align=right range=right #{E:status-right-style}]#[push-default]#{T;=/#{status-right-length}:status-right}#[pop-default]#[norange default]
```

Three things in that string decide everything in §1.6 and §2:

* `#{T;=/#{status-left-length}:status-left}` — the `=` limit modifier, applied to both halves;
* `#[list=on]` … `#[list=focus]` … `#[list=left-marker]<` `#[list=right-marker]>` — the window
  list's own trim policy: *"list=focus is the part of the list that should be kept in focus if
  the entire list won't fit in the available space (typically the current window)"*, and the
  markers *"mark the text to be used to mark that text has been trimmed from the left or right"*
  `[man page]`;
* `#[range=…]` — the mouse targets, §2.

### 1.6 How a segment's span is known when the bar is narrow

**It is not.** There is no per-segment span in byobu, and there is no per-segment span in
tmux's status renderer either. The whole of byobu's width arithmetic is three lines
`[local /usr/bin/byobu-status:51-66]`:

```sh
tmux)
	# Fix status printing for small terminal sizes in tmux
	width=$(tmux list-windows -F "#{session_width}")
	…
	for w in $width; do
		if [ "$w" != "$w_last" ]; then
			# go through cat due to possible tmux/epoll bug
			tmux set -g status-left-length $(($w*1/4)) | cat >/dev/null 2>&1
			tmux set -g status-right-length $(($w*3/4)) | cat >/dev/null 2>&1
			printf "$w" > $BYOBU_RUN_DIR/width
			break
		fi
	done
```

Two whole-bar budgets, `w/4` and `3w/4`, recomputed only when `#{session_width}` changes, and
written to a stamp file so the write happens once per resize. **That is the entire width
model.** It is not a span per segment; it is a cap per half, and the caps are recomputed by a
side effect of drawing the bar.

What tmux then does with those caps was measured `[local run]` by attaching a real client at
several widths and reading the rendered bottom row (two independent renderers, agreeing). With
`status-left` = `L1 … L12`, `status-right` = `R1 … R24`, six windows, and byobu's caps:

```
width  60 (caps 15/45)   L1 L2 L3 L4 L5 R1 R2 R3 R4 R5 R6 R7 R8 R9 R10 R11 R12 R13 R1
width 120 (caps 30/90)   L1 L2 L3 L4 L5 L6 L7 L8 L9 L10<ba>R1 R2 … R24
width 140 (caps 35/105)  L1 … L11<h 4:bash- 5:bash*R1 R2 … R13
width 200 (caps 50/150)  L1 … L120:bash  1:bash  2:bash  3:bash  4:bash- 5:bash*     R1 … R24
```

Read that carefully, because it is the answer to the question:

1. **The left half is allocated first**, truncated to `min(its own width, status-left-length)`.
   It is a cap, not a reservation — at width 200 the left takes 35 columns although its cap is
   50.
2. **Then the right half**, same rule. At width 200 it takes 71 although its cap is 150.
3. **The window list gets whatever is left** — `width − left − right`, no reservation, no
   minimum. At width 120 that is 4 columns and the list is drawn as `<ba>`; at width 60 it is
   5 columns and the list is drawn as `<bas>`; at width 40 and 80 (not shown) it is **zero
   columns and the list is not drawn at all**.
4. **Within each half, truncation eats the tail.** The `=` limit's positive form counts from
   the start of the string `[man page]`, and measured directly
   `[local run]`: `T;=10` on `0123456789ABCDEFGHIJ` gives `0123456789`; `T;=-10` gives
   `ABCDEFGHIJ`. On the real byobu right string (996 raw characters, 46 visible), the limit is
   applied to **visible columns and carries the escapes through**: `T;=5` → `(R) 2`,
   `T;=45` → the 45 visible columns, escapes intact. So colour costs nothing against the
   limit and text costs exactly its width.
5. **Inside the window list, trimming is from the left and keeps the current window** — the
   `<` marker is `list=left-marker` and `list=focus` holds the current one
   `[man page]`, visible at width 140 as `<h 4:bash- 5:bash*`.

**So: what drops first.** In order — (i) the window list, entirely, the moment the two halves
fill their caps; (ii) inside the right half, the **last** enabled item in `tmux_right`, and
then the one before it; (iii) inside the left half, likewise from the end. The default
`tmux_right` ends `… memory #swap disk #whoami #hostname #ip_address #time_utc date time`
`[local /usr/share/byobu/status/status:35]`, so the first things to vanish are **`time`, then
`date`, then `disk`** — the clock goes before the load average, because the list is read left
to right and the truncation is not.

**And byobu makes the list's starvation certain rather than occasional.** `w/4 + 3w/4 = w`:
the two caps sum to exactly the terminal width, so there is no width at which the caps leave
the list a guaranteed column. Whenever both halves are full — which on a narrow bar is always
— the clickable window switcher gets zero columns. The operator's own config sidesteps this by
setting `status-left ""` and `status-right ""` `[local ~/.emacs.d/byobu/.tmux.conf:52-56]`,
which is why *their* switcher is always visible; a stock byobu's is not.

## 2. How a click becomes an action

### 2.1 tmux's mouse is off by default and on in this operator's config

`mouse` defaults to **off**: *"If on, tmux captures the mouse and allows mouse events to be
bound as key bindings"* `[man page]`, and measured `[local run]`
(`tmux -L p -f /dev/null show-options -g mouse` → `mouse off`). The operator's
`.tmux.conf` turns it on, with the reason written next to it:

```
# Track the mouse so wheel/touchpad scroll enters tmux copy-mode and scrolls the
# pane content while the status line stays pinned at the bottom.  ghostel
# forwards wheel events to tmux as button 4/5 only when the app requests mouse
# tracking; without this it scrolls ghostel's own grid (status line included).
set -g mouse on
```

`[local ~/.emacs.d/byobu/.tmux.conf:9-13]`

### 2.2 The default bindings *are* the plumbing

There is no byobu mouse code path for the chrome. `grep -rn "Mouse" /usr/share/byobu/ /usr/bin/byobu`
returns only the two `mouse.tmux.{enable,disable}` files and the one key that sources them
`[local run]`. Everything is tmux's default bindings, read off this box
`[local run]` (`tmux -L p -f /dev/null list-keys -T root`):

```
bind-key -T root MouseDown1Status          switch-client -t =
bind-key -T root MouseDown3Status          display-menu -T "#[align=centre]#{window_index}:#{window_name}" …
bind-key -T root MouseDown3StatusLeft      display-menu -T "#[align=centre]#{session_name}" …
bind-key -T root WheelUpStatus             previous-window
bind-key -T root WheelDownStatus           next-window
bind-key -T root MouseDown1Pane            select-pane -t = \; send-keys -M
bind-key -T root MouseDrag1Border          resize-pane -M
bind-key -T root MouseDrag1Pane            if-shell -F "#{||:#{alternate_on},#{pane_in_mode},#{mouse_any_flag}}" { send-keys -M } { copy-mode -M }
bind-key -T root WheelUpPane               if-shell -F "#{||:#{alternate_on},#{pane_in_mode},#{mouse_any_flag}}" { send-keys -M } { copy-mode -e }
bind-key -T root DoubleClick1Pane          select-pane -t = \; if-shell -F "#{||:#{pane_in_mode},#{mouse_any_flag}}" { send-keys -M } { copy-mode -H ; send-keys -X select-word … }
bind-key -T root TripleClick1Pane          select-pane -t = \; if-shell -F "#{||:#{pane_in_mode},#{mouse_any_flag}}" { send-keys -M } { copy-mode -H ; send-keys -X select-line … }
```

The location suffixes are `Pane`, `Border`, `Status`, `StatusLeft`, `StatusRight`,
`StatusDefault`, `ScrollbarSlider`, `ScrollbarUp`, `ScrollbarDown` `[man page]`.

### 2.3 Clicking a window in the list

Three pieces, and the third is the one worth stealing.

1. **The event is named by where it landed.** A left press on the window list is the key
   `MouseDown1Status` `[man page]`. The `Status` suffix means *the status line window list*
   `[man page]`.
2. **The target is resolved by a token, not by arithmetic.** The binding is
   `switch-client -t =`, and *"The special token `{mouse}` or `=` may be used as target-window
   or target-pane in commands bound to mouse key bindings. It resolves to the window or pane
   over which the mouse event took place (for example, the window in the status line over
   which button 1 was released for a `MouseUp1Status` binding)"* `[man page]`. So tmux does the
   hit-test, not the binding.
3. **The hit-test is made possible by a range marker emitted at render time.** The default
   `status-format` wraps each window in `#[range=window|#{window_index} …]`, and *"range=session|X,
   range=window|X and range=pane|X are ranges for a session, window or pane. These trigger the
   `Status` mouse key with the target session, window or pane given by the `X` argument"*
   `[man page]` `[local run]` (the format string). `range=user|X` does the same for a
   user-defined target, and `X` *"must be at most 15 bytes in length"* `[man page]`.

So: **the renderer writes the action into the frame as a range, and the mouse path reads it
back out.** Nothing recomputes a column. This is the opposite of what letibot does today
(§5.1), and it is the single most transferable idea in byobu's stack.

### 2.4 The chrome's mouse and a program's mouse

This is the part the operator's own comment names (`[local ~/.emacs.d/byobu/.tmux.conf:9-13]`,
quoted in §2.1). The mechanism:

* With `mouse on`, tmux **asks the outer terminal for mouse reporting.** Measured by capturing
  every byte the client writes `[local run]`: with `mouse off` the client sends
  `?1000l ?1002l ?1003l ?1005l ?1006l`; with `mouse on` it sends `?1000h ?1002h ?1006h` —
  basic button tracking, button-event tracking, and SGR extended coordinates. `?1003h` (any
  motion) is **not** requested, and neither is `?1015h` (urxvt) or `?1005h`.
* A pane that wants the mouse says so itself, with its own `?1000h`/`?1002h`/`?1006h` on its
  own pty. tmux records that as a **format variable**, and it is the switch that separates the
  two mice. Measured `[local run]`: a pane that emitted `ESC[?1000h ESC[?1006h` reports
  `mouse_any_flag=1 mouse_sgr_flag=1 mouse_standard_flag=1`; a pane that did not reports all
  three zero. The full set is `mouse_all_flag`, `mouse_any_flag`, `mouse_button_flag`,
  `mouse_sgr_flag`, `mouse_standard_flag`, `mouse_utf8_flag` `[man page]`.
* The default bindings then branch on it: `WheelUpPane` and `MouseDrag1Pane` forward with
  `send-keys -M` **when `#{mouse_any_flag}` (or the alternate screen, or copy-mode) is set**,
  and do tmux's own thing otherwise (§2.2). *"The send-keys -M flag may be used to forward a
  mouse event to a pane"* `[man page]`.
* Chrome events never reach a pane at all: they are bound under a `Status*` location, and a
  `Pane` binding is what forwards. There is no ambiguity to resolve, because the location is
  decided before the binding is looked up.

Two consequences worth carrying:

* tmux **re-asserts its modes**, which is why a program that turns the mouse off cannot keep
  it off. Measured `[local run]`: over a 3-second attach spanning one window switch, the client
  emitted the group `?1006h ?1000h ?1002h ?25l` twice — once on attach, once after the switch.
  This is the mechanism behind letibot's own note at
  `[local crates/tui/src/app.rs:34524]` that *"Switching byobu windows fixes it because tmux re-asserts
  its modes on focus"*.
* A pane that asks for the mouse **gets the drag too** — `?1002h` is button-event tracking, so
  a drag inside `mc` is `mc`'s, not tmux's. Which is §4.

### 2.5 What byobu adds, and the inverted file names

byobu adds exactly one key and two files. `f-keys.tmux` binds
`bind-key -n M-F12 source …/mouse.tmux.enable` `[local /usr/share/byobu/keybindings/f-keys.tmux:82]`,
and the two files are:

```
# mouse.tmux.enable                       # mouse.tmux.disable
set -g mouse off                          set -g mouse on
set -g mouse-utf8 off                     set -g mouse-utf8 on
set -g mouse-resize-pane off              set -g mouse-resize-pane on
set -g mouse-select-pane off              set -g mouse-select-pane on
set -g mouse-select-window off            set -g mouse-select-window on
set -g mode-mouse off                     set -g mode-mouse on
bind-key -n M-F12 source …/mouse.tmux.disable \; display-message "Mouse: ON"
bind-key -n M-F12 source …/mouse.tmux.enable  \; display-message "Mouse: OFF"
```

`[local /usr/share/byobu/keybindings/mouse.tmux.enable:1-9]` and `…disable:1-9`.

**The file names are inverted with respect to their contents.** Sourcing the file called
`enable` sets `mouse off` and says `Mouse: ON`; sourcing the one called `disable` sets
`mouse on` and says `Mouse: OFF`. Whatever the intent, the names and the messages disagree with
the effects, and `M-F12` on a stock byobu ends up with the mouse *off* — so a fresh byobu does
**not** have a clickable window list until the key is pressed an even number of times. The four
`mouse-*-pane`/`mouse-select-*`/`mode-mouse` lines are pre-tmux-2.1 options that tmux 3.6 no
longer has; the files carry them for old tmuxes `[local /usr/share/byobu/keybindings/mouse.tmux.enable:4-8]`
and this tmux accepts them silently, so they are inert here.

## 3. The embedding pattern

### 3.1 What tmux owns, what byobu owns, and where the seam is

| | tmux | byobu |
|---|---|---|
| the pty per pane, and the shell on it | **owns** | — |
| the VT parser and the per-pane screen | **owns** | — |
| the client's terminal I/O, and the modes it sets | **owns** `[local run]` §2.4 | — |
| windows, panes, sessions, the layout tree | **owns** | — |
| the status line's **rendering**, layout and truncation | **owns** `[man page]`, §1.6 | — |
| the window list's format | **owns** (default `status-format`) | only restyles it `[local /usr/share/byobu/profiles/tmux:53-56]` |
| mouse handling and hit-testing | **owns** `[man page]` §2.2 | — |
| copy-mode, scrollback, paste buffers | **owns** | — |
| the *content* of the left and right halves | — | **owns** `[local /usr/share/byobu/profiles/tmux:76-77]` |
| the palette | — | **owns** `[local /usr/lib/byobu/include/colors:25-34]` |
| the keybindings | executes them | **owns** `[local /usr/share/byobu/keybindings/f-keys.tmux]` |
| session bootstrap | executes it | **owns** `[local /usr/bin/byobu:164]` |

**The seam is a config file and a `#()` command.** There is no byobu API, no socket, no
plugin. byobu's contribution to the running system is: a set of tmux option values, four
palette variables, a directory of shell scripts invoked through `#()`, and a keybinding file.
Everything else in the sentence "byobu is a terminal multiplexer" is tmux. `man byobu`'s own
first line is *"wrapper script"* `[man page]`.

The consequence for the operator's *"it does exactly what we want - embedding"*: **byobu is not
embedded in anything, and nothing is embedded in byobu.** It is a launcher plus a status
generator. The embedding is *tmux's*: it is a server, and clients attach to it. What byobu
demonstrates is that **you can own the chrome without owning the terminal** — as long as the
thing you are decorating hands you a string to fill and a set of bindings to override. That
is exactly the arrangement letibot would need, and tmux's version of it is coarse: you get one
string per half, one cadence, and character truncation.

### 3.2 tmux control mode: what it gives a program

`tmux -C` (and `-CC`, which *"disables echo"* `[man page]`) makes a client that speaks text
instead of drawing: *"In control mode, a client sends tmux commands or command sequences
terminated by newlines on standard input. Each command will produce one block of output on
standard output. An output block consists of a `%begin` line followed by the output (which may
be empty). The output block ends with a `%end` or `%error`"* `[man page]`. Measured
`[local run]`, a private server, `printf 'list-panes -F "#{pane_id} …"\n' | tmux -L p -C attach -t probe`:

```
%begin 1791288365 286 0
%end 1791288365 286 0
%session-changed $0 probe
%begin 1791288365 291 1
%0 80x6 sleep
%end 1791288365 291 1
```

What it gives, with evidence:

* **The program's bytes, per pane.** `%output pane-id value`, where *"value escapes
  non-printable characters and backslash as octal `\xxx`"* `[man page]`. Measured
  `[local run]`: `%output %0 echo hello-from-control\015\012`.
* **Key injection, literal and raw.** `send-keys`, and `-H` for hexadecimal bytes
  `[man page]`. Measured `[local run]`:
  `send-keys -H -t %0 1b 5b 3c 30 3b 31 30 3b 32 4d` put `ESC[<0;10;2M` on the pane's pty
  (it came back as `%output %0 ^[[<0;10;2M`, echoed by the tty). **That is a raw byte path into
  the pane**, and it is how a driver *could* synthesise a mouse report — but it must compute
  the report itself.
* **Resize.** `refresh-client -C widthxheight` sets the control client's size, *"If this is not
  used, control mode clients do not affect the size of other clients no matter the value of
  the window-size option"* `[page]`. Measured `[local run]`:
  `refresh-client -C 100x20` then `display-message -p "#{window_width}x#{window_height}"` → `100x20`.
* **Structural notifications.** `%window-add`, `%window-close`, `%window-renamed`,
  `%window-pane-changed`, `%layout-change`, `%session-window-changed`, `%sessions-changed`,
  `%pane-mode-changed`, `%client-detached`, `%exit` `[man page]` — so a driver does not poll to
  learn that a window appeared.
* **A rendered-screen oracle.** `capture-pane -p` `[man page]`.
* **Flow control.** `refresh-client -f pause-after=seconds` and `-A '%0:pause|continue|off|on'`,
  with `%pause`/`%continue`/`%extended-output` `[page]` `[man page]`.
* **Format subscriptions.** `refresh-client -B name:what:format`, reported by
  `%subscription-changed`, *"at most once a second"* `[page]` — a way to watch a fact without
  polling.

### 3.3 Control mode: what it does not give

* **The chrome.** *"Note that output generated by tmux itself (for example in copy or choose
  mode) is not sent to control mode clients"* `[page]`. Measured `[local run]`: with a control
  client attached, changing `status-left` produced **no** notification of any kind — only
  `%begin`/`%end` and `%exit` appeared. The window list's *contents* must be fetched with
  `list-windows -F`. **A control-mode driver owns its chrome by necessity, exactly as byobu
  does.**
* **A mouse.** `send-keys -M` has nothing to forward. Measured `[local run]`:
  `send-keys -M -t %0` → `%begin … / no mouse target / %error …`. So a control-mode pane cannot
  hand a program the operator's mouse through tmux's own plumbing; you would synthesise the
  report and inject it with `send-keys -H`, which is you re-implementing the client half.
* **A screen.** `%output` is the byte stream *"exactly what the application running in the pane
  sent to tmux … may contain escape sequences"* `[page]`. It is not a grid, and it has no frame
  boundary — a driver that wants a screen must run its own VT over the stream. Measured
  `[local run]`, the same program read two ways: the `%output` stream is `\015\012`-laden
  escapes, while `capture-pane -p` is the composited grid.
* **The cursor, except by asking.** There is no cursor event; `#{cursor_x}`, `#{cursor_y}` and
  `#{alternate_on}` are format variables you poll `[local run]`.
* **A client that is not attached.** The `%output` notifications belong to the *client*; the
  client is attached to one session, and `%output` covers *"any pane in any window in the
  attached session"* `[page]`. Following a pane means staying attached to its session.

### 3.4 Is `capture-pane -p` good enough to hand a language model as "the screen"?

**Yes, with three flags, and no, on one point.** Measured `[local run]` on a private server, a
pane 40×6 containing `short`, then a long line that wraps:

| command | what comes back |
|---|---|
| `capture-pane -p` | 6 rows, trailing whitespace stripped, hard-wrapped at the pane width |
| `capture-pane -p -J` | the same rows with the wrapping **joined** — the logical lines |
| `capture-pane -p -N` | trailing spaces preserved (`short     `) |
| `capture-pane -p -e` | SGR escapes included (`^[[2m[14:06:04]^[[0m …`) |
| `capture-pane -p -S -` | the same, from the start of the history |

`-J` *"preserves trailing spaces and joins any wrapped lines; -J implies -T"* and `-S`/`-E`
select history by line number, `-` being the start of the history `[man page]`.

So for a model the right invocation is **`capture-pane -p -J`** — plain text, no escapes,
logical lines, and *"exactly the visible contents"* by default or the history with `-S`. What
it is **not** good enough for:

* **it is a snapshot, not a stream.** It says what the screen looks like now and never what was
  written, so it cannot say how much of the glass a redraw touched. letibot already knows this
  and says it at `[local crates/tui/src/term.rs:32-39]`: *"`tmux capture-pane` shows the rendered pane,
  so it can say what the screen ended up looking like and never how much was written to get
  there — and 'how much of the glass did that redraw' is the question a lost mouse selection
  asks"*. That is why the head counts its own writes (`WriteStats`, same file).
* **it is the pane's screen, not the terminal's.** The status row and the composer are not in
  it. A model handed `capture-pane -p -J` is handed *the pane*, which is exactly right — and
  it is not the same thing as "the screen".
* **it does not say where the cursor is.** `#{cursor_x}`/`#{cursor_y}` is a second call.
* **it has no notion of a frame.** A program mid-redraw is captured mid-redraw, honestly.

letibot already uses this technique for its own testing: `docs/tui-testing.md` documents
`tmux capture-pane -p` and `-p -e` as the way to read a head `[local docs/tui-testing.md:15-23]`.

## 4. Selection

**With mouse reporting on, the terminal's own drag-select is gone** — not because tmux does
anything to it, but because tmux asked the terminal for the mouse and the terminal gave it up.
Measured `[local run]`: with `mouse on` the client sends `?1000h ?1002h ?1006h` to the outer
terminal; with `mouse off` it sends the corresponding resets. Once `?1002h` is on, every press
and drag inside the pane is reported as bytes, so the terminal never sees a selection gesture.

The escape hatch is a **terminal-side convention, not a tmux feature**: *"many terminal
emulators (including xterm) use the `shift` modifier to disable mouse reporting temporarily,
allowing native text selection to work"* `[page]`, and the same page documents
`XTSHIFTESCAPE` (`CSI > n s`), which lets a program ask for shift to be *reported* instead —
which then breaks selection by design. So **Shift+drag** is the gesture, and it is the
terminal's, not tmux's: tmux never sees those bytes and cannot help or hinder.

Concretely, what byobu/tmux users do — and what this operator has already done:

1. **Shift+drag for a one-off copy.** Nothing to configure; the events never reach tmux.
   letibot's own decoder states the same rule `[local crates/tui/src/term.rs:986]` and the
   head's key list repeats it `[local crates/tui/src/app.rs:1289-1292]`.
2. **Or give the drag to tmux on purpose, and let tmux put it on the clipboard.** The
   operator's config does exactly this `[local ~/.emacs.d/byobu/.tmux.conf:37-43]`:
   *"A mouse drag is forwarded to tmux (it requests mouse tracking), so tmux — not ghostel —
   owns the selection; with this on, tmux's copy-selection also emits OSC 52, which ghostel
   honors (`ghostel-enable-osc52 t`) and writes to the Emacs kill ring + system clipboard"*,
   with `set -g set-clipboard on`. tmux's default is `set-clipboard external` `[local run]`
   (`show-options -g set-clipboard`), i.e. external applications may read the clipboard but
   tmux does not set it.
   The default bindings that make the drag a tmux selection are
   `MouseDrag1Pane → copy-mode -M`, `DoubleClick1Pane → copy-mode -H ; send-keys -X select-word`
   and `TripleClick1Pane → … select-line`, each guarded so that a pane that wants the mouse
   keeps it `[local run]` §2.2.
3. **Or take the wheel for scrollback.** `WheelUpPane → copy-mode -e` when the pane is not in
   the alternate screen and does not want the mouse — which is why the operator's comment says
   the wheel *"enters tmux copy-mode and scrolls the pane content while the status line stays
   pinned"* `[local ~/.emacs.d/byobu/.tmux.conf:9-11]`.
4. **And the thing that does *not* work: repainting while a selection exists.** Any write into
   a selected cell clears it — `TODO.md` records the measurement, `tmux pipe-pane` on both
   heads for a twenty-two minute turn with leticl erasing nothing and still losing the
   selection `[local TODO.md:341-346]`. The head cannot detect the selection (the events go to
   the terminal), so the reader holds the view (`[local crates/tui/src/app.rs:11976-12040]`).

The trade is a real one and it is worth stating plainly: **mouse tracking and local selection
are mutually exclusive for the *unmodified* gesture.** tmux spends the plain drag on copy-mode
and gives back Shift; a head that wants the drag for its own chrome (letibot's pickers,
`[local crates/tui/src/app.rs:7561]`) spends it the same way and must document Shift the same way.
letibot has already chosen, and said so in the code: clicks are decoded and *"selecting text
stays the terminal's own Shift+drag, which mouse tracking does not take away"*
`[local crates/tui/src/term.rs:986-988]`.

## 5. What letibot should take

### 5.1 (a) The chrome — take the shapes, fix the span, steal the range marker

letibot already has the machinery byobu lacks, and lacks the one thing byobu's stack has.
The mapping, byobu shape → letibot machinery:

| byobu's shape | letibot's equivalent | what to do |
|---|---|---|
| `status-left` / `status-right`, two halves | the bottom bar has two halves already: `hint_bar` is *"the composer owns the first half and changes it after the first Esc or Ctrl+C… the head owns the second half"* `[local crates/tui/src/app.rs:12676-12681]`; `box_edge` is a left legend, a fill and a right legend `[local crates/tui/src/app.rs:12647-12674]` | keep the two-half shape, but compute the split instead of capping it |
| a segment list (`tmux_left`, `tmux_right`) | `chrome: Vec<String>` — an ordered list of rows `[local crates/tui/src/app.rs:12291]` | the unit differs: byobu's segments are cells on a row, letibot's are rows. A status *row* with cell segments is a new, small thing: one `Vec<Segment>` per bar row |
| a **truncation order** (implicit: the tail of the list) | the fit loop at `[local crates/tui/src/app.rs:12236-12288]`, which drops in an explicit order — `hint`, then `notice`, then composer rows, then `stuck`, then the turn's status row, then the box, then content — and never drops `stopping` or `link` | **already better than byobu's.** Extend it from rows to segments: give each segment a rung |
| `status-left-length` / `status-right-length` (a cap on a half) | `visible_width` is already used to lay out `box_edge` `[local crates/tui/src/app.rs:12661]` | a **span**, not a cap: `#[list=focus]`'s idea — reserve the window list's columns first, then give the halves what is left |
| the four palette variables `BYOBU_DARK/LIGHT/ACCENT/HIGHLIGHT` `[local /usr/lib/byobu/include/colors:25-34]` | `Role` `[local crates/ui/src/style.rs:51]` and `Palette::open` `[local crates/ui/src/style.rs:159]`, with the rule *"name the roles, not the colours"* `[local crates/ui/src/style.rs:8-10]` | **do not take byobu's.** byobu's colour decisions are spread across 30+ scripts, each printing `#[fg=…,bg=…]`; `Role`/`Palette` is the fix for exactly that and it is already built |
| a per-segment cadence (`status_freq`, primes) `[local /usr/lib/byobu/include/shutil:229-280]` | the head has a wall-clock constant (`NOTICE_MS = 1_600` `[local crates/tui/src/app.rs:1858]`) and a frame loop | take the shape: **`last_run + freq` per segment**, so a clock and a disk are not both recomputed at the frame rate. Prime intervals are the cheap part of byobu worth copying literally |
| a **reserved** row, not a conditional one — *"keep the line reserved for `Responding...` always free, or we have these ugly jumps"* `[local crates/tui/src/app.rs:12214-12219]` | already present | this is byobu's cap idea done right; apply the same rule to a segment's columns |
| `#[range=window\|#{window_index} …]` + `switch-client -t =` | `Key::Click { x, y }` `[local crates/tui/src/app.rs:1299]`, decoded from SGR at `[local crates/tui/src/term.rs:1008]`, consumed at three sites that **each re-derive the row arithmetic by hand**: the session picker `[local crates/tui/src/app.rs:7561-7577]`, the mode card `[local crates/tui/src/app.rs:7680-7694]`, the todos pane `[local crates/tui/src/app.rs:7849-7856]` | **this is the one to steal.** Each site re-implements the renderer's layout and guards itself with a "did the frame actually draw that row" flag (`picker_rows_drawn`, `mode_rows_drawn`, `todo_stop_at_row`). tmux instead has the renderer emit the target into the frame (`range=`) and the click reads it back. letibot's equivalent: **have `compose_screen` record a per-frame `Vec<(row, col_lo, col_hi, Action)>`**, and let `Key::Click` be one lookup. That deletes three hand-written arithmetics, makes a new clickable segment cost no arithmetic at all, and answers the guard question structurally instead of per-site |

**Concretely, the four things I would build:**

1. **A segment type with a declared span and a declared rung.** `Segment { text: String, span: usize, rung: u8, action: Option<Action> }`, composed into one bar row. The span is *reserved*; the rung is the order in which a too-narrow bar drops segments whole. This is byobu's `tmux_left`/`tmux_right` list plus the `list=focus` reservation, with the rung made explicit instead of emergent from string order.
2. **Drop whole segments before truncating any.** byobu can only truncate characters, so it cuts a segment in half (`<ba>` in §1.6). A segment is the smallest unit that means anything; `status_freq`'s design already treats a segment as the unit of cost, and the rung list should treat it as the unit of loss.
3. **The frame records its own hit map.** As above — the range-marker idea, in Rust, replacing `picker_rows_drawn`-style reconstruction.
4. **A per-segment cadence, in the head's own clock.** byobu's prime table, but owned by the composer: each segment says how stale it may be, and the head recomputes only what is due. This is the shape that makes a clock cost nothing to the disk.

What I would **not** take: byobu's colour model (§5.1 row 5), and byobu's `status-left-length`/`status-right-length` caps — the caps are the bug.

### 5.2 (b) Should the pane be a tmux client?

**Two facts narrow this a lot, and the first is usually missed.**

**Fact 1 — attaching a real tmux client means giving up the chrome.** tmux draws the whole
screen, the bottom row included, and the only way to put anything in that row is
`status-format` with `#()` commands — which is byobu's arrangement exactly, i.e. our chrome
would become shell scripts again. That is the opposite of what `Role`/`Palette` and the
frame-diffing head exist for. **Rejected.**

**Fact 2 — a control-mode client gives no screen, so `crates/vt` is not on the table either
way.** `%output` is the program's bytes `[page]`, not a grid. A control-mode pane must be
rendered by us. So the choice is **not** "tmux instead of `crates/vt`". `crates/vt` stays in
both worlds.

What tmux would actually replace is the **session layer** — which is precisely the part of
`crates/tools/src/exec/shell.rs` that is unfinished. Its own header lists what is not built
`[local crates/tools/src/exec/shell.rs:231-293]`, and the overlap with tmux is almost total:

| shell.rs TODO | line | tmux already has it |
|---|---|---|
| streaming — `run` returns when the trailer arrives | `[local crates/tools/src/exec/shell.rs:275]` | `%output` is a stream |
| `SIGWINCH`, and who sends it | `[local crates/tools/src/exec/shell.rs:279]` | `refresh-client -C` + the kernel `[local run]` |
| scrollback — a program that scrolls off the screen is gone | `[local crates/tools/src/exec/shell.rs:284]` | `capture-pane -S -` `[man page]` |
| the daemon's registry — when a session's shell is started | `[local crates/tools/src/exec/shell.rs:245]` | sessions, windows and panes, with `list-*` |
| the input path — keystrokes down, and one way out | `[local crates/tools/src/exec/shell.rs:250]` | `send-keys`, literal and `-H` `[local run]` |
| a pane that shows a full-screen program | `[local crates/tools/src/exec/shell.rs:233]` | what tmux is for |

And it is not a new direction for this tree: `DECISIONS.md` already settled that a byobu/tmux
session *"already provides everything the ask wanted — a cwd that sticks, exported variables
that persist, background jobs that keep running"*, and that the tool runtime's shell and an
operator's attached head should become *"one mechanism instead of two"*
`[local DECISIONS.md:56-65]`. The design brief already requires multi-head attach over
byobu/tmux `[local docs/design-brief.md:295]`.

**Against, and these are the reasons I would not simply adopt it:**

* **No mouse for the pane.** `send-keys -M` from a control client fails — *"no mouse target"*
  `[local run]`. A program's `?1000h` would be answered by us synthesising SGR reports and
  injecting them with `send-keys -H`, which works (`[local run]`, the bytes reached the pty)
  but is us writing the client half of the mouse protocol. Note that our own VT *also* refuses
  it — `[local crates/vt/src/screen.rs:27]` says mouse reporting *"is consumed and dropped. A program
  that turns it on gets no events, because the pane has no input path of its own: keys and
  clicks are the head's, and the head must not hand a program the operator's mouse"*. So this
  is a wash today, and a tmux session layer at least leaves the door open.
* **A second daemon.** A tmux server is a process tree with its own lifetime, and adopting it
  means expressing that lifetime in the same terms as the session cgroup — which
  `DECISIONS.md` says is fine `[local DECISIONS.md:58-62]`, but it is a policy call and not a
  technical one.
* **Version coupling.** tmux 3.6 here; the operator's config targets tmux 3.3+ features
  (`allow-passthrough`, `terminal-features`) `[local ~/.emacs.d/byobu/.tmux.conf:7,35]`. A
  private server on a private socket is fine (`docs/tui-testing.md` already does this
  `[local docs/tui-testing.md:15-23]`) but it is a dependency with a floor.
* **`%output` has no frame boundary.** The screen still has to be assembled by us from a
  partial byte stream — the same problem `crates/vt` already solves, with the same need to
  carry an incomplete escape across reads.

**What I would do:** keep `crates/vt` as the only screen, and **do not adopt tmux for the pane
until the spike below passes.** The reason is not conservatism, it is that tmux's value here
is concentrated in *one* property — `capture-pane` is an oracle for our own screen, which we
cannot get from our own pty — and that property is worth nothing if our screen and tmux's
disagree. If they agree, tmux is a strictly cheaper session layer with a free test oracle and
the shell.rs TODOs above mostly evaporate. If they disagree, then either we adopt tmux's screen
(and lose the thing we control and can test) or we keep ours (and tmux buys us only the pty
plumbing, which is the cheap part). **So the decision is the fidelity question, and the spike
is the way to ask it.**

### 5.3 The one spike

**`spike/tmux-session-layer` — one screen, two readers, exact agreement or nothing.**

*Setup.* One private server: `TMUX_TMPDIR` under the test's own scratch dir, `tmux -L
letibot-spike -f /dev/null new-session -d`, one pane, running a program that draws a
full-screen TUI (`mc` is the one the tree's own header names
`[local crates/tools/src/exec/shell.rs:20-25]` and it does not ask `CSI 6n`, which is the one
gap that would otherwise confound the result `[local crates/tools/src/exec/shell.rs:255-270]`).

*The two readers.*

* **ours:** attach a control client (`tmux -L letibot-spike -C attach`), `refresh-client -C
  <cols>x<rows>` set to the rectangle the head would give the pane, octal-decode every
  `%output %0 …` payload, and feed the bytes into one `letibot_vt::Screen`
  (`crates/vt/src/screen.rs`, `Screen::feed`);
* **tmux's:** `tmux -L letibot-spike capture-pane -p -J -t %0` at the same rectangle.

*The pass condition.* After the program has settled, `Screen::rows()` and `capture-pane -p -J`
agree **cell for cell** at **two** sizes — say 100×28 and 60×20 — with a mid-run
`refresh-client -C` between them, and the comparison normalised only by the two rules already
documented (`capture-pane` strips trailing whitespace; `crates/vt` has no 256-colour or
truecolour fidelity `[local crates/vt/src/screen.rs:36-38]`, so the comparison is on characters
and the four attributes `crates/vt/src/attr.rs` does carry, with the colour slots compared as
slots). Anything else — a missing row, a wrapped row that lands differently, a cursor in the
wrong cell, a screen that diverges only after the resize — is a **fail**.

*Why this settles it.* It is the only question whose answer changes the decision. If it
passes, the pane can be a tmux session with `crates/vt` unchanged, and the shell.rs TODOs for
streaming, `SIGWINCH`, scrollback and the registry become tmux's. If it fails, the failure is
itself the finding: it names the sequences `crates/vt` is missing, and that list is worth
having whether or not tmux is adopted. **The spike costs a day and produces either an adoption
or a gap list.** And it leaves behind a test the pane needs either way — *"our screen, fed from
a real program, matches an independent emulator"* — which is stronger than anything the pane
has now.

*What the spike does not settle, and should be put to the operator as a separate sentence:*
whether a second long-lived tmux server belongs in the product at all. That is a policy call
about process trees and lifetimes, not a fidelity one, and no measurement answers it.
