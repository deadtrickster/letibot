## 1. A page's `session_id` is never read, so a page in flight across a switch lands in the session the head moved to — **severity: high (silent wrong rows), reachability: narrow**

`crates/tui/src/app/events/frames.rs:297-308`, `crates/tui/src/app/scroll.rs:889-957`,
`crates/sessionlog/src/server.rs:1313-1320`.

```rust
ServerFrame::RowsFetched { from, rows, .. } => {
    // The ask is spent whatever came back. Which ask it was is the ordinal it names, the
    // same rule `apply_rows` places by, and what a page that does not join means - the
    // daemon's last word - is settled there too, so nothing is asked again here.
    if from >= self.items_base + self.items.len() {
        self.fetch_below = None;
    } else {
        self.fetch_asked = None;
    }
    self.apply_rows(from, rows);
    Disposition::Rendered
}
```

The protocol names the session it is about — `RowsFetched { session_id, from, rows }`
(`crates/sessionlog/src/protocol.rs:1044`) — and the arm drops it in `..`. The frame is answered on
the connection's own writer from whatever session the request named
(`crates/sessionlog/src/server.rs:1313-1360`), so after a `/sessions` switch the answer to session
A's `FetchRows` arrives on a connection that is now in session B, with nothing to say so.

`apply_rows` then places it by ordinal alone:

```rust
if !rows.is_empty() && from.saturating_add(rows.len()) == self.items_base {
    let n = rows.len();
    let lead = self.items_lead;
    self.items.splice(lead..lead, rows);
```

**Scenario (the bad one).** The reader scrolls up in session A (long, trimmed: `items_base` 1000)
and a page of 100 rows is asked for, `from = 900`. They switch to session B, whose snapshot also
starts at `items_base` 1000 — two conversations long enough to have been trimmed arrive at the same
count of dropped rows, since both are bounded by the same function. `900 + 100 == 1000` holds, so
`rows.splice(lead..lead, rows)` puts **session
A's rows into session B's window**, at its base, where they draw as B's conversation. Nothing
reports it: `fetch_asked`/`no_more_above` were reset by B's snapshot (`events/mod.rs:240-242`) and
the splice is the ordinary path.

**Scenario (the common one).** The same page arrives and the bases differ (A trimmed, B not): the
front-join fails, so the arm falls through to the branch in finding 2 and tells the operator *"the
daemon holds no rows above the oldest one this head has, so the transcript stops here"* about a
session it never asked about, and sets `no_more_above` for the rest of B's life.

**Why the tests cannot see it.** Every fixture passes the right id — `scroll.rs:4252`,
`:4346`, `:4435`, `:4469`, `:4836`, `:4940` all write `session_id: "s"` — and a check that compares
it would pass every one of them. There is no test that applies a page for a session the head has
left.

**Smallest fix.** Match `session_id` and drop the answer when it is not `self.session_id` (before
any flag is cleared, since a dropped answer must not spend an ask either).

## 2. A page that does not join is read as "the transcript starts here" — for a page asked *below* too — and that answer can become a loop — **severity: high (a false claim, a permanent loss of paging, and an ask per frame), reachability: narrow**

`crates/tui/src/app/scroll.rs:872-884` (the ask), `:889-905` (the join test), `:946-957` (the only
other outcome).

The below ask names the ordinal after the window as `items_base + items.len()`:

```rust
let from = self.items_base + self.items.len();
```

That is the ordinal only while `items_lead == 0`. The field's own doc says otherwise
(`crates/tui/src/app/mod.rs:311-313`):

```rust
/// How many of the rows this head holds are ABOVE that base - the tail of the transcripts a
/// resume republished, which a fork's base does not number. Ordinal `items_base` is the row at
/// this index, and a page of the base belongs here rather than at the front of the list.
pub(crate) items_lead: usize,
```

With `items_lead > 0` the row after the window is `items_base + (items.len() - items_lead)`, so this
ask is `items_lead` rows too far ahead. The join test repeats the same arithmetic
(`let end = self.items_base + self.items.len(); if from == end`), so the two agree with each other and
never with the daemon.

**Scenario.** A session was compacted and then reseated, so the head holds the republished ancestor
rows above the new base (`rows_replaced`, `events/mod.rs:593-658`, sets `items_lead`). The reader
parks in the scrollback on a session over the 8 MiB window, rows arrive below them
(`items_below` counts them, `events/transcript.rs:21-24`) until the trim lets those rows go
(`drop_rows_below`, `scroll.rs:828-846`). They come back down to the bottom, which asks for rows
from `base + len` — `lead` rows past the end of what the head holds. The daemon answers from that
ordinal (rows exist there, or the answer is empty). Either way `from != end` and the front-join
fails, so the only remaining outcome runs:

```rust
self.no_more_above = true;
self.say(if rows.is_empty() {
    "nothing is above this window — the daemon holds no rows above the oldest one this \
     head has, so the transcript stops here"
} else {
    "the page above this window did not join it: a row in it could not be read, so the \
     transcript above stops here"
});
```

Three things follow at once. The tail is never filled (`items_below` is only zeroed in the
`from == end` arm). `no_more_above` — a field about the *other* direction — is set for the life of
the session, so upward paging is dead. And the answer is `Disposition::Rendered` while `items_below`
is still non-zero and the anchor is still `None`, so the next draw asks again from the same wrong
ordinal: one `FetchRows` and one full frame compose every other tick (the head reads the terminal at
`VMIN=0 VTIME=1`, `head.rs:1235`), for as long as the reader stays at the bottom.

**Why the tests cannot see it.** Every page fixture is built with `items_lead == 0` — the field is
mentioned in `app/mod.rs` and `scroll.rs` only, never in `src/app/tests/` — so the ordinal
arithmetic is exercised only in the case where it happens to be right.

**Smallest fix.** Name the next ordinal `items_base + (items.len() - items_lead)` in both places
(one helper, since the ask and the join must not be two copies of it), and make the no-join branch
answer in the direction it was asked: a below page that does not join is a stale tail, not the
start of the transcript.

## 3. The edge's gate step pushes the two counts that ask for a person off an eighty-column edge, and takes the click target with them — **severity: medium (a count the operator cannot see, and a door that stops being a door), reachability: every 80-column terminal with a gate running**

`crates/tui/src/ui/panes/queue.rs:355-393`, `crates/tui/src/ui/screen.rs:683-694`, `:786-790`;
tests `crates/tui/src/app/tests/queue.rs:826-863` and `:891-921`.

`Standings::words` builds one string, in this order, and the gate's step is written *inside* the
merge column:

```rust
for (n, word) in [
    (self.review, "in review"),
    (self.merging, "to land"),
    // **Rows a person has to move** - the store's `stuck`, said as what it wants.
    (self.stuck, "stuck"),
    // **`done`, not `landed`**: the edge's whole line has to fit eighty columns (see
    // `the_longest_standings_fit_on_an_eighty_column_edge`), and the day's successes are
    // the one column that asks nothing of the reader.
    (self.landed, "done"),
] {
```

and the doc above it still promises the opposite of what the code now does:

```rust
/// The order is the pane's and `red` leads it, because
/// the edge is cut from its right end. The step is parenthesised and last, so it is lost first.
```

The step is fourth of six, not last. `box_edge` truncates the right-hand line keeping its head
(`rano`, pinned rev `f4c624e`, `src/agent/composer.rs:57-59`: `truncate(right, room)`), so on an eighty-column
terminal the tail is what goes. The two fixtures each pass and the combination is what overflows:

* `the_longest_standings_fit_on_an_eighty_column_edge` pins all six columns and measures **70
  cells** (`assert_eq!(words.chars().count(), 70, "the premise: seventy cells")`) with a green/red
  target and **no running gate**.
* `the_edge_names_the_gates_step_at_eighty_columns` pins the gate step with **one** column
  (`"queue: 2 to land (gate step 3 of 4)"`) and nothing else.

Put together: 70 − 9 (`1 to land`) + 28 (`1 to land (gate step 3 of 4)`) = **89 cells**, against the
**73** an 80-column edge gives the right block (`box_edge`: `inner 76 − left_cols 0 − 3`). The
drawn row keeps its head, so the operator reads
`queue: 1 red · 1 unjudged · 1 in review · 1 to land (gate step 3 of 4)…` and **never sees
`1 stuck`** — the one column the comment above calls *rows a person has to move*. With the longest
step (`12 of 12`) it is 90 cells and the cut lands inside the parenthetical itself.

The click goes with it: the rectangle is read off the finished row, and the search needs the words
whole —

```rust
fn drawn_span(line: &str, words: &str) -> Option<(usize, usize)> {
    let cells = crate::app::keyhints::cells(line);
    let want: Vec<char> = words.chars().collect();
```

— so `box_bottom` returns `at = None` (`screen.rs:789`) and no `Target::QueueStandings` hit is
recorded (`screen.rs:594-610`). While a gate is running, which is exactly when a reader wants it,
the standings stop being the one queue door a person finds without `/queue`.

**Smallest fix.** Keep the stand inside its room: drop the parenthesised step when the words do not
fit (or draw it as its own trailing span), so the six counts keep their columns and `drawn_span`
still matches. Whichever way, the doc line about the step being *last* has to go, or become true
again.

## 4. The window bounds `items` but not the three id-keyed tables the renderer reads, so the head still grows for the life of the session — **severity: medium (memory, on the exact input the window was introduced for)**

`crates/tui/src/app/scroll.rs:781-846` (both drop paths), `crates/tui/src/app/events/transcript.rs:51-59`,
`crates/tui/src/app/mod.rs:863-872`, `crates/tui/src/app/events/mod.rs:99-104` and `:556-587`.

`trim_held` lets rows go from `items` — that is the whole point of `HELD_LIMIT` — and nothing else
is pruned with them. The three maps are filled once per `tool_result` row:

```rust
if let Some(ms) = carried {
    self.call_ms.insert(item_id.clone(), ms);
}
if let Some(e) = carried_edit {
    self.call_edits.insert(item_id.clone(), e);
}
if let Some(d) = carried_decision {
    self.call_decisions.insert(item_id.clone(), d);
}
```

and the only doors that shrink them are a **session switch** (`events/mod.rs:102-103`) and — for
two of the three — nothing else. `prune_to_the_rows` (`events/mod.rs:556-587`), which is the one
function the snapshot and the fork both call to prune id-keyed state, prunes `bulk` and
`bound_prompts` and leaves `call_ms`, `call_edits` and `call_decisions` alone. A snapshot of the
same session does not prune them either.

**Scenario.** An agent session runs for a day with a few hundred tool calls. `items` stays at or
under 8 MiB (the window is doing its job) while `call_edits` holds one `ToolEditExcerpt` per
`edit`/`write` row ever seen, and that excerpt is not small — `before: String` and `after: String`
of the changed lines (`crates/transcript/src/lib.rs:195-216`, which `TranscriptItem::bytes` counts as
*"what makes a `read` or an `edit` row large"*). The head's RSS grows with the session's history
even though the transcript it draws does not.

Two smaller facts in the same family: `call_decisions` is **not** cleared on a session switch while
its two siblings are (`events/mod.rs:102-103`), and a fork (`rows_replaced`) clears none of the
three, so rows of the replaced transcript keep their entries.

**Why the tests cannot see it.** `the_head_holds_a_window_of_a_long_session_and_not_the_whole_of_it`
(and its neighbours) assert `a.items_base + a.items.len()` and `a.hist_lines.len() < rows / 4`; no
test looks at the three maps after a trim.

**Smallest fix.** Call `prune_to_the_rows` at the foot of `drop_rows_above`/`drop_rows_below` (and
extend it to the three maps), so a row that leaves the window takes its facts with it.

## 5. A note filed at the first row the trim drops stays a seam at `items.len()`, so it is drawn as the newest line of the conversation instead of being filed beside it — **severity: low**

`crates/tui/src/app/scroll.rs:835-841`.

```rust
// A note filed past the window is one the head no longer draws, the rule a fork's seams
// follow: reachable through `/notes`, which is where a note off the screen is read.
for (place, _) in &mut self.notes {
    if matches!(place, Placed::Seam(at) if *at > keep) {
        *place = Placed::Before;
    }
}
```

`keep` is the first index that went (`self.items.truncate(keep)`), so a seam at exactly `keep` is a
seam at a row the head no longer holds.

**Scenario.** The reader is parked above the tail (`trim_held_below`, `:757-777`) and a note — a
warning, a settled child — is filed at the row boundary that is about to become the window's end.
The trim keeps `Seam(keep)` with `keep == items.len()`. The draw loop accepts it
(`window.rs:751-753`, `matches!(place, Placed::Seam(at) if *at <= *hist_upto)`, and `hist_upto ==
items.len()` after the trim), so the note is drawn at the very bottom of the conversation: a
sentence about a row the head no longer has, in the position reserved for what just happened, while
the comment above says it is reachable only through `/notes`. The above-direction sibling uses
`*at >= n` (`:807-813`), which is why only this side dangles.

**Smallest fix.** `>= keep` instead of `> keep`.

## 6. A refused `FetchRows` has no path in the head: the in-flight flag is never spent, and the refusal is reported as a seq disagreement — **severity: low**

`crates/tui/src/app/events/frames.rs:400-425`, `crates/tui/src/app/scroll.rs:851-884`,
`crates/sessionlog/src/server.rs:1313-1320`.

The daemon answers an unknown session with `Rejected { client_request_id: format!("fetchrows:{session_id}/{from}"), … }`.
The head's `Rejected` arm has no case for it: it calls `answer_refused`, ends the attach wait, sets
`behind`, and says

```rust
self.say(&format!(
    "rejected: {reason} (you saw {expected_seq}, the session is at {actual_seq})"
));
```

`fetch_asked` (or `fetch_below`) is left set, and both asks are gated on it
(`if … || self.fetch_asked.is_some() … { return; }`), so that direction is dead until a snapshot
resets it. The message is also about the wrong thing: nothing in a `FetchRows` is a `seq`.

**Scenario.** A session is closed (or renumbered by the daemon) between the ask and the daemon
reading it, which is the one case the ask can be refused in. The reader's next scroll sends
`FetchRows`, gets `Rejected`, and is told their view of the conversation is behind the session's
`seq`, which it is not — and paging in that direction then silently stops, because the flag the
ask needs is never spent. (`registry.resolve` is the only refusal this path produces;
`server.rs:1316-1322`.)

**Smallest fix.** Match the `fetchrows:` prefix in the `Rejected` arm and clear both flags, with the
daemon's sentence as the notice.

## Decisions

Every finding reproduced in this tree; each was made to fail as a test before the fix, and every
fix carries one commit.

1. **`RowsFetched`'s `session_id` ignored**, fixed in `e360c579`. The arm names the field and
   drops the frame when it is not this head's session, before any flag is cleared, so a page of a
   session the head has left neither lands by ordinal nor spends the ask. Test:
   `a_page_for_a_session_the_head_has_left_lands_nowhere` (reproduced: 100 rows of A spliced into
   B). Three fixtures that never attached had to name their session, since a head with none cannot
   have asked.
2. **The below-window ask ignored `items_lead`**, fixed in `0f50ff12`. One helper,
   `App::end_ordinal` (`items_base + len - items_lead`), is now the only spelling of *the first row
   this head does not hold*: the ask, the join test, the ask-spending rule in the frame arm and
   `rows_in_session`. The no-join branch answers in the direction it names: a page that starts past
   the window clears `items_below` and says the tail is behind a hole, instead of setting
   `no_more_above` and claiming the transcript above stops. Tests:
   `the_page_below_the_window_starts_after_the_rows_the_base_numbers` (reproduced: ask named 60 for
   a window that ends at 58) and
   `a_page_below_the_window_that_does_not_join_does_not_say_the_transcript_stops`.
3. **The edge's gate step pushed `stuck`/`done` off an eighty-column edge**, fixed in
   `db94ea70`.
   `App::box_bottom` composes the right block and, when it does not fit the room rano gives it
   (`w - 5`), composes again with `Standings::gate` dropped and searches for those words, so the six
   counts keep their columns and the click target matches what was drawn. The doc line promising
   the step was *last* is corrected in `Standings::words`. Test:
   `the_gate_step_is_dropped_rather_than_the_counts_at_eighty_columns` (reproduced the review's own
   row: `… 1 to land (gate step 3 of 4)…`, no `1 stuck`, no target).
4. **The window bounded `items` and not the three id-keyed tables**, fixed in `221db9d7`.
   `prune_to_the_rows` prunes `call_ms`, `call_edits` and `call_decisions` to the rows still held,
   and both `drop_rows_above` and `drop_rows_below` call it, which also covers the switch and the
   fork (both already called it, and `load` still clears the two it always did). Tests:
   `a_row_that_leaves_the_window_takes_its_call_facts_with_it` (reproduced: 60 entries of 35 rows)
   and `a_switch_takes_the_last_sessions_call_decisions_with_it` (reproduced: `s.1` survived a
   switch).
5. **A note at the first dropped row stayed a seam at `items.len()`**, fixed in `6e7fab78`.
   `drop_rows_below` now files a seam at `>= keep` beside the conversation, matching the
   above-direction sibling. Test: `a_note_at_the_row_the_window_drops_is_filed_beside_it`
   (reproduced: `Seam(18)` with eighteen rows held).
6. **A refused `FetchRows` had no path in the head**, fixed in `c89ff516`. The `Rejected` arm
   matches the `fetchrows:` prefix, clears both asks and says the daemon's sentence alone: no
   `behind` movement and no seq wording, since nothing in a page is a seq. Test:
   `a_refused_page_spends_its_ask_and_says_the_daemons_reason` (reproduced: the ask stayed in
   flight, `behind` moved to 7, and the notice claimed a seq disagreement).
