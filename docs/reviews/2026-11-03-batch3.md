## Findings, most severe first

### 1. `f3fcea73` — a stop during a retry wait is consumed without stopping the children
`crates/harnessd/src/harness/turns.rs:1608-1615` (the new `Waited::Interrupted` arm) vs `crates/harnessd/src/harness.rs:1511` (the only door that runs `stop_children_first` + sets `stopped`)

The interrupt is taken out of the hub queue (`take_queued_interrupt`, `sessionlog/src/hub.rs:1737`) and nothing else happens: the one place that stops the subtree is the steering arm the command never reaches now.

**Scenario.** A parent with running `task` children is in a 429 retry ladder; the operator presses esc-esc. The turn ends, the interrupt is **gone**, `self.stopped` stays false, and the children keep computing. Before this commit the command stayed queued and the next steering poll stopped them. A second press is needed, in a turn that now has to exist. **Plausible (read through, exact lines); not run.**

### 2. `268f63ca` — a failed turn's held results are never re-offered, but the activity still says a turn is owed
`crates/harnessd/src/jobwatch.rs:653` (`how == TurnEnd::Done` gates the wake) with `crates/harnessd/src/activity.rs:122` (`watching.held > 0` ⇒ `delivery: true`, "each is a turn this session will take by itself")

Two commits' assumptions contradict: the jobwatch now deliberately declines to wake a session whose turn failed, while the activity readout keeps asserting a turn is coming.

**Scenario.** A job settles mid-turn (held). The turn then fails (ladder exhausted, guard, wall). Nothing rings. From then on the head draws `waiting on: delivery` and it never changes until a person types; `Bridge::wait` does not arm on `Delivery` alone, so an orchestrator's wait burns its deadline and returns `Attention::Timeout` on a parked session. **Plausible (code + comment contradict); severity high, confidence medium.**

### 3. `8b641d09` — a genuinely red step that also shows a kill is classified as infra, so the queue retries it for ever
`crates/harnessd/src/mergequeue/gate.rs:618` — `if !code_failed && let Some(sig) = shown_kill(out)`

`code_failed` already excludes any output containing `(signal: 9, SIGKILL`; the new arm applies that exclusion to `StepExit::Code` as well, so the *output's* kill overrides the leader's own exit. Before this commit the same input fell through to `RedCause::Code`.

**Scenario.** `cargo test --workspace --no-fail-fast` where one target fails AND another test binary/rustc was killed (this box has OOM-killed children before). The row says *unjudged, not red*, the target goes back to `gating`, and the failure is never reported.

**PROVED.** Scratch test `b3_scratch_a_failed_test_beside_a_kill_is_still_red` (output with `test result: FAILED` **and** a `(signal: 9, SIGKILL` line, exit `Code(101)`): got `KilledBySignal(9)`, expected `Code`. Reverted. A second reviewer found this independently (`gate.rs:618`).

### 4. `2a79756b` (kept by `15528268`) — the R66 daemon test asserts `VmRSS > 0` on a machine with no `/proc`

The commit whose message is "assert the daemon's bound on its own census, not on resident memory" left the one RSS assertion in place. **Verified by reading (file, spawn args, no guard).**

### 6. `20786e9f` — `out.is_ok()` is passed where the contract wants *did the row go in*, so a failed turn re-holds results the model already read

## Worth knowing, not bugs
