## 1. `[github] token_path` gates posting and never authenticates anything — HIGH

**Where.** `crates/github/src/seat.rs:42`, `:86-90`; `crates/github/src/gh.rs:44-47`,
`:247-272`.

**Evidence.**

`crates/github/src/seat.rs:40-43`
```rust

    /// token is the "token missing" state the pane draws, not an attempt that fails per push.
    pub fn posting(&self) -> bool {
        self.post && self.token.is_some()
```

`crates/github/src/seat.rs:86-90` — `token` is the *path*:
```rust
        Ok(Config {
            post: true,
            token: Some(path.to_string_lossy().into_owned()),
            ..config
        })
```

`crates/github/src/gh.rs:44-47` — the whole of how `gh` is invoked:
```rust

        let mut c = Command::new(&self.gh);
        c.args(argv);
```
There is no `c.env(…)` anywhere in `gh.rs`, no `GH_TOKEN`, no `--hostname`, and `Gh` holds no
`Config`. `post_review` (`gh.rs:247`) and `reply` (`gh.rs:274`) build `gh api -X POST … --input -`
and read an id back; neither is handed the token.

The commit that added the mode check says what was meant (`eb5efe89`): *"Posting is the one act
this seat does under the operator's own identity, so the config is resolved once, where the file is
named … A child that read the token later would be the first to notice, and it would notice by
posting."* The child never reads it.

**Scenario.** The operator writes

```toml
[github]
post = true
token_path = "~/.config/letibot/github.token"
```

and `chmod 600`s that file, as `Config::resolved` demands (`seat.rs:71-85`). `letibot attach github
stroppy-io` prints `posting as letibot` (`crates/letibot/src/github.rs:117-121`). Every review the
seat sends then goes out through `gh api` **authenticated from `gh`'s own store** — usually the
operator's personal `~/.config/gh/hosts.yml` — so the comment lands under whatever account `gh` is
logged in as, which is precisely the account the key existed to keep out. On a box where `gh` has
no auth, every post fails 401 while the seat's own row says posting is on. Either way the one key
that was supposed to decide the identity decided nothing, and it is the difference between "a draft
on the seat's row" and "a comment on a stranger's repository".

**Smallest fix.** One line at the one door: have `Config` carry the file's *contents* (read in
`Config::resolved`, where the mode is already checked) and set `c.env("GH_TOKEN", &self.token)` in
`Process::run`. Alternatively delete `token_path` and say in the doc that `gh auth` is the only
identity, so nobody believes a key that does not act.

## 3. A project file can START the seat by supplying the token the user named nothing of — MEDIUM

**Where.** `crates/leticode-config/src/lib.rs:565-576`; the invariant it breaks is the doc comment
on that same function, and the test that is supposed to hold it is
`crates/leticode-config/src/lib.rs:1988-2037`.

**Evidence.** `crates/leticode-config/src/lib.rs:565-576`
```rust
    /// The two levels as one. **A project file may stop the seat and may not start it**: it is a
    /// file a session with `write` can edit, and starting it posts under the operator's identity
    /// on a stranger's repository.
    pub fn overridden_by(&self, other: &GithubKeys) -> GithubKeys {
        GithubKeys {
            post: match (self.post, other.post) {
                (_, Some(false)) => Some(false),
                (mine, _) => mine,
            },
            token_path: other.token_path.clone().or_else(|| self.token_path.clone()),
        }
    }
```
`post` is guarded; `token_path` is not. `posting()` (`:561-563`) is `post.unwrap_or(false) &&
token_path.is_some()` over the *merged* value, so the two facts may come from two different levels.

**Scenario.** The user file, written before the token exists:

```toml
# ~/.config/letibot/leticode.toml
[github]
post = true
```

and a project file a session with `write` can edit:

```toml
# <repo>/leticode.toml
[github]
token_path = "~/.config/letibot/github.token"
```

Merged, `post = Some(true)` (the user's) and `token_path = Some(…)` (the project's) →
`posting() == true`, and `crates/letibot/src/github.rs`'s `plan` accepts it because after the merge
both facts are there. The project started the seat, with the operator's token, on somebody's
repository — the sentence at `:565-567` says it cannot. The unit test covers only
`GithubKeys::default().overridden_by(&project_on)`, i.e. the case where the *user* file said nothing
(`:2033-2036`), which the `post` arm already refuses.

**Smallest fix.** `token_path: self.token_path.clone(),` — a project file may stop the seat and may
name no token; one line, and the existing test keeps passing.

## 5. The provider's EINTR retry re-POSTs the completion, and nothing bounds it — MEDIUM

**Where.** `crates/provider/src/openai.rs:414-427`.

**Evidence.**
```rust
        let resp = loop {
            match self
                .agent
                .post(&self.url)
                .header("Authorization", &format!("Bearer {}", self.creds.key))
                .header("Content-Type", "application/json")
                .header("Accept", "text/event-stream")
                .send(payload.as_bytes())
            {
                Ok(resp) => break resp,
                Err(ureq::Error::Io(e)) if e.kind() == std::io::ErrorKind::Interrupted => {}
                Err(e) => return Err(BackendError::Unreachable(e.to_string())),
            }
        };
```
No attempt counter, no deadline, no backoff: the arm falls through to the top of the loop and posts
again. `d4280baa`'s own measurement is one SIGINT; the loop is written for an unbounded number.

**Scenario.** A round is hung on a provider that never sends headers (exactly the case the commit
was written for). The operator presses Ctrl-C: EINTR, and the whole `POST /chat/completions` with
its full history is sent again. Press it three times while the daemon's five-second grace runs
(`crates/harnessd/src/daemon.rs`'s `stop_on_signal`) and three generations of the same prompt are in
flight at the provider — billed, and none of their streams is ever read, because the first
`Ok` breaks the loop and the others' bodies are dropped with their sockets. A signal delivered
repeatedly by anything else that interrupts the timed read turns this into a spin that re-posts once
per interruption.

**Smallest fix.** Count and give up:
`Err(ureq::Error::Io(e)) if e.kind() == Interrupted && tries == 0 => { tries += 1 }`, then
`return Err(BackendError::Unreachable(…))` — one retry covers the daemon's Ctrl-C, and a storm ends
in the same failure the old code reported instead of in N duplicate requests.

## 9. The remote embedding tier never uses the endpoint's batch field — LOW

**Where.** `crates/embeddings/src/tier.rs:230-246` and `:248-262`; `crates/embeddings/src/remote.rs:127-143`.

**Evidence.** `crates/embeddings/src/tier.rs:47-54` — the only call into a remote engine:
```rust
        let mut vectors = match self {
            Engine::Internal(m) => m.embed(&[text]).map_err(TierError::Model)?,
            Engine::Remote(r) => r.embed(&[text]).map_err(TierError::Remote)?,
```
and `Tier::vectors` walks the corpus one document at a time (`tier.rs:237-244`), each through
`embed_or_get`, which holds `Embedder::inner` for the whole fill (`tier.rs:249`). `Remote::ask`
already accepts many texts and `parse` already checks the count it asked for
(`remote.rs:143`, `:179-184`), so the batch shape is dead off the fill path.

**Scenario.** `mode = "http://127.0.0.1:8080"`, a 300-note corpus: a fill is 300 sequential HTTP
round trips, not the ten a batch of 32 would be, and every one of the other callers on the box
blocks on `Embedder::inner` while it runs. Nothing here is wrong — one vector per text, in order —
but the mode's cost is a function of the corpus size where the endpoint offered not to make it one,
and the request body's `input` array is never longer than one element.

**Smallest fix.** Either batch in `Embedder::vectors` (collect the misses of a chunk of 32 into one
`engine.embed(&texts)` under the same lock), or take `&[&str]` off `Remote::ask`/`parse` so nobody
believes the field is used.

## Decisions

Every finding was re-read on the code before anything was written, then a test that fails was
added, the fix applied and the test seen to pass. One test per fix, and each one is named below.

### 1. `[github] token_path` gates posting and never authenticates anything — fixed in 8c11ac92

`Process` now carries the token file and hands its contents to `gh` as `GH_TOKEN`; `Gh::new` takes
the path `Config` resolved, and a file that has gone is refused by name rather than posting as
whatever account `gh`'s own store holds. Proven red by removing the `env` line:
`the_token_file_is_handed_to_gh_as_gh_token` (`crates/github/src/gh.rs`) then fails with
``/bin/sh ["-c", "printenv GH_TOKEN"]` failed``, because the child was given no token at all.

### 2. The built-in model is documented as fetched and nothing fetches it — not reproduced

The finding was true of `9d781d83`, the review's base: `crates/embeddings/src/builtin.rs` does not
exist at that commit (`git cat-file -e 9d781d83:crates/embeddings/src/builtin.rs` fails), and the
`lib.rs` doc is the sentence quoted. It is already fixed on this branch by `60f6afc2` ("the built-in
model is fetched on first use, hashed before it lands"), which is not an ancestor of `9d781d83` and
is an ancestor of `HEAD`, and refined by four commits after it. `builtin::ensure` fetches the three
pinned files over `letibot_http`, checks each against the pin's sha-256 and renames only what
hashed; `tier.rs`'s `Embedder::open_pinned` calls it for `internal` with no `model` while `download`
is on, and with `download = false` looks in the pin's own directory and refuses by naming it. The
crate measures this against a loopback server with no network: `cargo test -p letibot-embeddings
--lib builtin::` is eight passing tests, including
`the_builtin_model_is_fetched_once_and_then_found_on_disk` and
`a_file_that_does_not_hash_to_the_pin_is_not_renamed_into_place`. No change made.

### 3. A project file can start the seat by supplying the token — fixed in a403eec7

`GithubKeys::overridden_by` keeps the user level's `token_path`: a project file may stop the seat
and may name no token, so it can neither add one nor replace the user's. Proven red by restoring
the old `other.token_path.clone().or_else(…)` line: the new assertions in
`the_github_table_reads_both_keys_and_a_project_file_cannot_start_posting`
(`crates/leticode-config/src/lib.rs`) fail, `post = true` from the user plus a path from the
project answering `posting() == true`.

### 4. `tests/launcher.sh` lost its executable bit — fixed in 60b120da

The mode is `100755` again, and the suite now checks its own lists: a script in `BASH32` or
`POSIX_SH` that is not executable is a `FAIL`, because a script nobody can run is not a check.
Proven red before the chmod (the guard printed `FAIL modes: tests/launcher.sh is not executable`,
`launcher: 1 failed`, exit 1) and green after: `./tests/launcher.sh` runs all 187 cases and prints
`launcher: all cases pass`.

### 5. The provider's EINTR retry re-POSTs the completion, unbounded — fixed in e95aeadb

`ask_again` is the bound: an interrupted send is asked again once, and a second interruption — or
any other transport failure — is `BackendError::Unreachable`, which is what the old code reported
for a storm. Proven red by making the rule retry every interruption, which is the old loop:
`an_interrupted_send_is_asked_again_once` (`crates/provider/src/openai.rs`) fails on its second
assertion.

### 6. A cache row this build cannot read costs the round's score — fixed in d6b1111a

A blob that does not unpack is deleted and answered `Ok(None)`, so the caller embeds the text
again; `CacheError::Corrupt` is gone, because a variant nothing constructs reads as an outcome that
does not exist. Proven red by answering the refusal the old way:
`a_corrupt_blob_is_dropped_and_the_text_embedded_again` (`crates/embeddings/src/cache.rs`) fails
at the `embed_or_get` that should have embedded and instead returned `Err`.

### 7. An unknown MCP tool is a tool failure, against the module's own contract — fixed in b5ebfc4a

`call_tool` answers `Result<Value, (i64, String)>`, and the two caller mistakes — an unknown tool,
a missing `name` — are `-32602` with the client's id, which is the code MCP names for it. What the
module reserves for `isError: true` is a tool that ran and refused, and that is unchanged. Proven
red by answering both as a tool result again:
`an_unknown_tool_is_an_invalid_params_error_with_the_list` and
`a_tools_call_with_no_name_is_an_invalid_params_error` (`crates/bridge/src/mcp.rs`) fail.

### 8. `letibot attach github` reads only the user level — fixed in 2343f8fb

`merged` discovers and loads the project file at or above the working directory and puts the user
level under it, so a repository whose file says `post = false` stops the seat; a project file that
will not parse is a refusal rather than a guess, because it may be the one carrying that `false`.
Proven red by returning the user level unchanged, which is what the verb did:
`a_projects_file_stops_the_seat_and_its_syntax_is_not_ignored`
(`crates/letibot/src/github.rs`) fails on the stop.

### 9. The remote embedding tier never uses the endpoint's batch field — fixed in 26523567

`Engine::embed_many` asks a remote engine once for a slice, and `Embedder::vectors` collects the
cache misses and sends them `BATCH` (32) at a time under the one lock, so a 300-note corpus is ten
