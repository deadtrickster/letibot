## 1. HIGH — the peer check never sees the first frame, and the first frame is what hands out a head's seat

**`crates/sessionlog/src/server.rs:482`, `:486`, `:536`, `:546`; `crates/sessionlog/src/peer.rs:63`, `:24-31`, `:57-63`**

The connection is classified once, and then the guard is only consulted inside the reader loop —
which begins *after* the handshake has already been served:

```rust
// :486

...
// :536

// :540-546 - the loop, i.e. everything AFTER the seat exists
let result = loop {
    match reader.read::<ClientFrame>() {
        Ok(frame) if peer.refuses(&frame).is_some() => {
```

and `door()` resolves `Attach` to "served on any connection":

```rust
// crates/sessionlog/src/peer.rs:63
ClientFrame::Attach { .. } => return None,
```

`seat_in` takes no `Peer` at all and writes the whole seat:

```rust
// crates/sessionlog/src/server.rs:1747

...
// :1772-1783
w.write(&ServerFrame::Hello {
    protocol_version: PROTOCOL_VERSION,
    session_id: session_id.clone(),
    head_id: head_id.clone(),
    dropped: a.dropped,
    snapshot: a.snapshot.map(Box::new),
    resumed_from: a.resumed_from,
    scrubbed: a.scrubbed,
    wiring: registry.wiring(&session_id),
    sessions: registry.list(),
```

`kind`, `identity` and `caps` come straight off that first frame (`server.rs:487-493`), and
`registry.resolve` (`crates/sessionlog/src/registry.rs:1167`) hands out **any** session the daemon
holds — an empty id means "current", any other id means that session.

**Concrete scenario.** A model runs `bash` with a few lines that connect to `$LETIBOT_SOCKET`
(handed to every command at `crates/harnessd/src/harness/open.rs:941-947`) and write one
`Attach { session_id: "<another session>", kind: "tui", identity: "dead", caps: { can_decide:
true }, since_seq: 0 }`. The daemon, having already read that frame before consulting `peer`,
answers `Hello` with that session's full snapshot, its whole backlog, its wiring and the list of
every session; the connection is then a registered head and receives every `SessionEvent` the
session publishes. The `Rejected` arm that the module exists for (`:546`) never runs, because
`Attach` is exempt.

The second consequence is on the refusal text this window also changed. `Hub::deciding_heads`
(`crates/sessionlog/src/hub.rs:1234-1241`) counts `caps.can_decide`, and `HubDenials::denied`
(`crates/harnessd/src/harness/hub_io.rs:61-64`) uses that count to decide whether the model is
told *"The operator has been told"*. A tool call that attaches with `can_decide: true` and
`identity: "dead"` makes every later refusal claim a person is holding it, when nobody is — the
exact claim commit `9676492b` was landed to stop making.

The module doc states the property that is false here:

```rust
// crates/sessionlog/src/peer.rs:5-6
//! the kernel is asked which process connected, and a connection from inside this daemon's own
//! tree is a tool call, never a head.
```

`crates/sessionlog/tests/peer_doors.rs:131-133` relies on the hole — the child comments
`"a tool call's command can attach"` — because the askpass helper must `Attach` before it can
reach the one door it is allowed.

**Why it is deliberate and still wrong.** The chatty part is not that an inside connection may
attach; it is that attaching hands it a *head's* estate: another session's transcript, the
session list, a live subscription, and a vote in `deciding_heads`.

**Smallest fix.** Give `seat_in` the `Peer` (`server.rs:536`), and for `peer.inside` attach with
`since_seq` as given but write a reduced `Hello` — `snapshot: None`, no backlog, `sessions:
Vec::new()`, `wiring` omitted — and override `caps.can_decide = false` before `hub.attach`. The
askpass door keeps working, because it needs none of those.

## 2. MEDIUM — a refused fetch whose retry has no time left is reported as a 300-second timeout, and the refusal's words are dropped

**`crates/tools/src/remote.rs:2275-2277`, `:2281`, `:2293`, `:3671-3678`; `crates/tools/src/rpc.rs:501-511`**

`fetch_within` keeps the last attempt's output and only uses it when the *slot wait* fails:

```rust
// :2270-2277
let budget = FetchBudget::new(within);
let mut last: Option<std::process::Output> = None;
for attempt in 0..2 {
    if budget.left().is_zero() {
        break;                       // last is DISCARDED: the loop ends with Ok(last)
    }
```

```rust
// :2281
let _slot = match rpc::enter_git(&self.host.name, budget.wait(self.bound)) {
    Ok(slot) => slot,
    Err(why) => {
        return Err(match &last {
            Some(out) => refused_then_no_slot(&out.stderr, &why),   // the only reader of `last`
            None => why,
        });
    }
};
```

Two holes, both on the same value:

1. **The refusal words are lost.** Attempt 0 is refused by the mux (`mux_refusal` matches, so
   `refused` is true) and attempt 1 finds the budget gone: the `break` at `:2275-2277` leaves
   `last = Some(out)` with `out.stderr` holding `administratively prohibited`. `fetch_within`
   returns `Ok(Some(that output))`, and `bring_back` (`:3661-3670`) then prints
   `"`git fetch` said \"administratively prohibited\""` — which is right — **unless** the budget
   was exhausted during attempt 0's *run*, in which case `last` is `None` and the operator is
   told `"got no answer within 300 s and was killed, so the connection is the suspect"`
   (`:3671-3678`) although the refusal that actually happened is in the stderr of a run that was
   killed. `last` is a `Option<Output>` that `TimedOut` renders as `None`
   (`remote.rs:2547-2552`), so the words exist and are thrown away.

2. **git is spawned with a zero deadline after the slot wait.** `budget.left()` is checked
   *before* `enter_git` (`:2275`) and never again; `:2293` passes what is left to `run_bounded`.
   `rpc::run_in_scope` kills on the first loop pass when `began.elapsed() >= within`:

```rust
// crates/tools/src/rpc.rs:502-511
let status = loop {
    match child.try_wait() {
        Ok(Some(status)) => break Some(status),
        Ok(None) if began.elapsed() >= within => {
            kill_group(pid);
```

   With `within == 0` that is a real `git` forked and SIGKILLed within 20 ms — a killed transfer
   can leave `FETCH_HEAD.lock`/`shallow.lock` behind, and the sentence the operator then reads
   claims a 300 s wait that never elapsed. The commit message of `36752792` says *"A fetch that
   spends the whole bound in the queue says so instead of running git with no time to answer"*;
   there is no such branch in the code, and the test added with it
   (`a_fetch_that_queued_for_a_slot_runs_on_what_is_left_of_its_bound`, `remote.rs:5965`)
   only exercises the case where 1.2 s of a 2 s bound is left.

**Concrete scenario.** A fanout of sessions closes at once, all eight git slots are held, the
first attempt is refused by the mux, and the retry's `enter_git` waits out `GIT_BOUND`. The
operator reads "got no answer within 300 s and was killed" for a transfer that was refused in
milliseconds and never retried.

**Smallest fix.** After `enter_git` succeeds, re-check `if budget.left().is_zero() { return
Err(refused_then_no_slot(...)) }` (one `if`, above `:2290`) so nothing is spawned at zero; and
carry the elapsed time into the `Ok(None)` arm's sentence instead of printing `GIT_BOUND`.

## 3. MEDIUM-LOW — a job that leaves a process behind never releases its own scope, so the leak this window fixed survives for exactly those jobs

**`crates/tools/src/exec/host.rs:815-822`, `:1553`, `:1686`, `:2126-2136`**

```rust
// :815-822
/// Release a job's own scope once its leader has gone. Only an EMPTY one goes: a scope still
/// holding a process is one the command left behind and somebody's live work, and `end` would
/// kill it. Left alone, each of these is a cgroup directory per command a session ever ran.
fn release_settled_scope(tree: &dyn ScopeTree, scope: &ScopeId) {
    if tree.members(scope).is_ok_and(|m| m.is_empty()) {
        let _ = tree.end(scope);
    }
}
```

Called once, from the settling thread (`:1553`) and once from an adopted job's watcher (`:1686`).
It is the *last* look the scope ever gets: the waiter thread returns after it, and nothing else
in the tree revisits a job scope. `prune` — the other net — runs only when the host is dropped:

```rust
// :2126-2136
impl Drop for HostProcesses {
    fn drop(&mut self) {
        ...
        self.tree.prune();
```

**Concrete scenario.** `bash { "command": "nohup ./server > /dev/null 2>&1 &" }`. The leader
exits immediately; the child stays in `job-<id>`; `members` is non-empty, so the scope is kept —
correctly, since `end` would SIGKILL the child. When that child is later stopped, nothing looks
again, and `job-<id>` (plus its `cgroup.events`, `memory.*`, …) stays under the session's scope
until the daemon's host is dropped. A session that starts a background server per checkout
accumulates one directory each, which is the state `5d28ce2f` was landed to end — its own test
asserts `scopes == 1` but the fixture's commands leave nothing behind.

**Smallest fix.** Keep the scopes this function declined to release and re-check them where the
host already does housekeeping on every spawn (`release_settled_captures`, `:828`, called from
`:1597`), or call `tree.prune()` there instead of only at `Drop`.

## 4. LOW — one path outside the view fails a whole `read_many` page, turning one round trip into N

**`crates/tools/src/remote.rs:4140-4143`, `crates/tools/src/backend.rs:120-128`**

```rust
// crates/tools/src/remote.rs:4140-4143
let abs: Vec<String> = paths
    .iter()
    .map(|p| self.in_view(p))
    .collect::<Result<_, _>>()?;
```

`in_view` answers `Err(BackendError::Outside)` for one path; `collect::<Result<…>>` propagates
it as the failure of the *call*, which by the trait's own contract means "the channel failed and
says nothing about any path, so fall back to `read`" (`backend.rs:120-128`). So every path in the
page — including the ones well inside the view — is then read one ssh call at a time.

**Concrete scenario.** `outline` (`crates/tools/src/builtins/outline.rs:239`) with 64 model-named
paths, one of which is `/etc/passwd`: 64 ssh round trips at ~0.5 s each instead of one, and the
note corpus (`notes.rs:117`) does the same for any page containing a path that has left the view.
No wrong answer; a whole verb's budget spent on the fallback.

**Smallest fix.** Replace the `collect::<Result<_,_>>()?` with a per-path split: out-of-view paths
become `Err(Outside(path))` in the result vector, the rest stay batched.

## 5. LOW — the batch reader answers an unreadable file as a missing one, so a corpus with one unreadable note is reported whole

**`crates/tools/src/firecode.rs:1482-1489`, `crates/tools/src/builtins/notes.rs:185`**

```sh
# crates/tools/src/firecode.rs:1483-1485
if [ -d "$f" ]; then printf '\036d\n'; continue; fi; \
n=$(wc -c < "$f" 2>/dev/null | tr -d '[:space:]') || n=; \
case "$n" in ''|*[!0-9]*) printf '\036-\n'; continue ;; esac; \
```

`wc -c < "$f"` fails for a file that exists and is unreadable (`EPERM` from the redirection), so
`n` is empty and the slot is `-`, which `parse_batched_reads` (`:1521`) turns into
`BackendError::NotFound`. `notes.rs`'s `text_of` then maps that to `Ok(None)` — *the note is not
there*:

```rust
// crates/tools/src/builtins/notes.rs:185
Err(crate::backend::BackendError::NotFound(_)) => Ok(None),
```

**Concrete scenario.** A placed session's `.letibot/notes/locked.md` is mode `0600` owned by
someone else (or is a directory the account cannot traverse). `notes {action:"list"}` shows it;
`search` and the similarity corpus drop it silently and the answer reads as a complete corpus
over the notes that could be read. The window's own commit `d61b5ab6` is titled *"answer an
unreadable notes corpus as unreadable, not empty"* — this is the same conflation reached through
the new batch door.

(The single-file `read_abs` conflates the two the same way — `if [ ! -e q ]; then exit 22; fi`
then everything else is `NotFound`, `remote.rs:2353-2368` — so this is not a regression, it is a
new path that inherits the old answer.)

**Smallest fix.** Give the batch a fourth header for "exists but could not be read" (`printf
'\036!\n'` on the redirect's failure) and map it to `BackendError::Io` rather than `NotFound`.

## 6. LOW — two new tests on the boundary's grant path are skips on many boxes, and a skip reads as a pass

**`crates/tools/src/exec/confine.rs:2696-2698`, `:2630-2632`**

Both tests landed in this window, both guard the new claim that an absence note's promised grant
is actually asked for:

```rust
// :2696-2698
let Some(cargo) = on_path("cargo").filter(|p| b.view.outside(p)) else {
    eprintln!("no cargo outside the fixture's view; nothing to assert");
```

```rust

    eprintln!("no directory outside the fixture's view; nothing to assert");

```

**Concrete scenario.** Both tests pass in 0.00 s on a Linux gate box whose `cargo` lives under

were written to catch (commit `96569337`'s subject) is free to come back.

a temp dir that is deliberately outside the fixture view, put that dir first on the `PATH` the
boundary resolves against, and assert on it — no `else { return }`.

## Decisions

Every finding was re-checked against the tree first, and each is one commit on
`remote/56935000`.

**One thing about the box, said once here rather than six times.** The offline crate cache this
was worked on is missing 77 crates that `letibot-embeddings` needs (`candle-core`, `gemm`,
`tokenizers` and their dependencies), so the real workspace does not resolve with `--offline` at
all: `cargo test --offline -p letibot-sessionlog` stops at `no matching package named
candle-core`. Verification ran in a workspace trimmed to the crates under test, with a local
stub for `letibot-embeddings` that carries the same public types and answers nothing. Neither the
trim nor the stub is in any commit; `git status` is clean. On that basis `cargo test --offline -p
letibot-tools --lib` is **1388 passed, 4 failed**, and all four failures are the stub, each
panicking with `settings: Toml("this build has no embeddings")`:
`similarity::tests::the_corpus_scores_through_the_one_function`,
`similarity::tests::a_tier_that_cannot_answer_falls_back_to_the_words`,
`similarity::tests::a_corpus_in_a_tier_lifts_a_paraphrase_with_no_shared_word`,
`builtins::notes::tests::a_paraphrase_with_no_shared_word_is_refused_by_the_second_tier`. Those
four pass on a box whose cache is whole, and nothing in them is touched by this work.

### 1. HIGH, the peer check never sees the first frame
**Fixed in `f5604259`.** `seat_in` now takes the `Peer`. A connection from inside the daemon's
tree attaches with `since_seq` as given, but is written a `Hello` with no snapshot, no session
list and no wiring, is handed no backlog, gets no pump, and its caps reach `hub.attach` with
`can_decide: false`. The askpass door needs none of those, and the existing tool-tree test still
shows it working. The test is `peer_doors::a_tool_calls_seat_holds_none_of_a_heads_estate`: a real
child process of the daemon attaches asking for a head's caps, prints what it was given, and waits
while a real head arrives to see whether an event reaches it. RED before the fix with
`SEAT snapshot=true sessions=1 wiring_empty=false`; GREEN after with `snapshot=false sessions=0
wiring_empty=true`, `EVENT none`, and `hub.deciding_heads()` empty.

### 2. MEDIUM, a refused fetch whose retry has no time left
**Fixed in `4b4769c6`.** Half of it did not reproduce as described. A run that `run_bounded` kills
returns `TimedOut` and its `Output` is dropped inside the runner, so there are no refusal words
sitting in `last` to be thrown away; and the sentence was true whenever the whole bound really had
elapsed. What did reproduce is the consequence of the answer being an `Option`: a fetch killed at
200 ms and one killed at the production 300 s were the same value, so the operator always read
`GIT_BOUND`, and nothing could distinguish the zero-budget fork from a real transfer. `fetch_within`
now answers `FetchEnded::{Ran, Killed(Duration)}`, `bring_back` prints the elapsed time, and the
budget is re-checked after the slot wait so nothing is forked with nothing left. The test,
`remote::tests::a_fetch_that_is_killed_says_how_long_it_was_given`, is RED on HEAD (`Ok(None)` for
a zero bound and for a 200 ms one, with the sentence claiming 300 s) and GREEN after. The
zero-budget window itself is a knife edge between `enter_git` returning and the budget running out,
so what the test proves is the answer a kill produces, not that race.

### 3. MEDIUM-LOW, a job that leaves a process behind never releases its own scope
**Fixed in `93f85044`.** `settle_scope` keeps the scopes it declined to end, and
`release_kept_scopes` looks at them again at the next spawn, which is where this host already does
this housekeeping. Calling `tree.prune()` there was read and rejected: on a cgroup v2 tree it also
removes any EMPTY scope directory, and a session's own scope holds no process of its own (the
kernel's no-internal-process rule), so pruning at a spawn would delete a scope the host still
names. RED before with a hand-built scope holding a live pid: it survived its settle and then the
next spawn; GREEN after, with the kept list emptied.

### 4. LOW, one path outside the view fails a whole `read_many` page
**Fixed in `f36bd584`.** The page is split per path in one place (`batched_page`): an out-of-view
path becomes its own `Outside` answer and the rest go over the wire in one command. RED before,
measured rather than argued: HEAD's own page expression answered `Err(Outside("/etc/passwd"))` for
a three-path page, which the trait reads as a failed channel.

### 5. LOW, the batch reader answers an unreadable file as a missing one
**Fixed in `4464bf25`.** The guest command asks whether the path is there before it counts it, and
a file it cannot count gets a fourth header (`0x1e !`) that `parse_batched_reads` maps to `Io`.
`builtins/notes.rs` needed no change: `text_of` already propagates everything that is not
`NotFound`. RED before with `Err(NotFound("locked.md"))` for a mode-0000 file, GREEN after with
`Io`. The fixture proves it really cannot read the file first, so a box running as root fails at
that assert instead of passing.

### 6. LOW, two tests on the boundary's grant path are skips
**Fixed in `d21b044e`.** Writing a stub into a directory outside the view needs a writable path
under `$HOME` or a mutation of the process `PATH`, and the second is racy across a test binary's
threads; so the fixture's view now has no system roots at all. Nothing of this box's own is in it,
which makes a program that really exists here deterministically outside it. Both tests assert, and
`a_fixture_that_finds_no_program_outside_fails_instead_of_passing` is a `#[should_panic]` guard on
the search itself: a fixture that finds nothing now fails rather than returning.
