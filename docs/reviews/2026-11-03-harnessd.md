## 1. HIGH — a turn the child runs *inside the hold* settles its slot, so a failing one makes a child that answered look failed and has its worktree reaped

`crates/harnessd/src/harness/children.rs:1106-1113` (the guard), `:1134` (the settle),
`:288-303` (`TaskSlot::settle`), `:364-372` (`finish_child_thread`);
`crates/harnessd/src/harness/deliverable.rs:96-108`; `crates/mergequeue/git.rs:1096-1107`.

`cf44e17d` says in its own message that "a turn of the hold, which runs before the slot settles, is
part of the answer the hold ends with rather than a settlement of its own". The flag honours that;
the settlement does not:

```text
crates/harnessd/src/harness/children.rs:1109-1113
    let silent = settled_before && matches!(&out, Some(Ok(reply)) if reply.text.trim().is_empty());
    if let Some(slot) = &turns.slot
        && somebody_spoke
        && let Some(ended) = &out
        && !silent
    {
```

```text
crates/harnessd/src/harness/children.rs:1137-1143
        let again = match &out {
            Some(Ok(reply)) if settled_before => {
                slot.spoke_again(reply.text.trim());
                true
            }
            _ => false,
        };
```

`settled_before` guards `again` and nothing else. The hold itself is
`serve_child_with(…, hold = true)` (`:3554`), whose loop returns only when the child has no
unsettled children (`:874`) — so every `OwnWork::Wake` in between runs `later_turn(Door::Wake)`
(`:920`) with the slot still `Running`, and `answer.say(Done{…})` (`:3593`) happens after it.

`settle` latches the reap flag exactly when the previous state was `Running`:

```text
crates/harnessd/src/harness/children.rs:288-303
        let mut g = self.state.lock().expect("task slot");
        // The first settlement is the answer the parent was handed; a parked child's later turn
        // overwrites the slot and must not turn the tree that answer named into debris.
        if matches!(*g, letibot_tools::builtins::task::TaskStatus::Running { .. }) {
            self.answer_failed.store(
                matches!(status, letibot_tools::builtins::task::TaskStatus::Failed { .. }),
                std::sync::atomic::Ordering::SeqCst,
            );
        }
        *g = status;
```

**Scenario.** A `task_start` child answers, has its own child out, and holds. The grandchild
settles; the hold's wake turn fails (a provider refusal, a `429` ladder that ends, a context wall).
`later_turn` settles `Failed` over a `Running` slot → `answer_failed = true`. The hold then ends,
`answer.say(Done)` settles `Done` over a `Failed` slot — the `matches!(*g, Running)` test is false,
so the flag is **never cleared**. `enqueue_finished` puts the branch in the review queue with
`worktree: Some(placement.path)` (`crates/harnessd/src/mergequeue/review.rs:1063`), the child parks,
`finish_child_thread` runs:

```text
crates/harnessd/src/harness/children.rs:364-370

        let d = slot.deliverable.lock().expect("task slot").clone();
        let _ = deliverable::reap_failed(d.as_ref());
    }
```

`reap_failed` → `remove_worktree`, which refuses a dirty tree (`git.rs:1096-1103`) and otherwise
runs `git worktree remove --force` (`:1104-1107`). So the tree a *successful* child answered from,
which that answer names and which the review row's `worktree` column points at, is removed while the
branch is queued. `7b73f370` wrote this flag for exactly this class — its message: "a
`task_message` turn that fails on a refusal made a child that had answered look failed, so the tree
its answer named was removed while the parent's transcript still pointed at it" — and it keys on
"the FIRST settlement and never a later one". A turn of the hold is the first settlement, so the
same damage comes back through the one door the fix does not look at.

**Smallest fix.** Add `&& settled_before` to the guard at `:1110-1113`, so a turn of the hold
neither settles nor hands up — which is what the commit message already claims. (One line; the
existing `again` guard then becomes redundant.)

## 3. MEDIUM — the room a fold's verbatim tail is given is not the room `plan_fold` left it, so `keep` can spend the record's own reserve

`crates/harnessd/src/harness/wall.rs:1094-1099` and `:1118-1122`;
`crates/harnessd/src/compaction_relevance.rs:67-118`; `crates/turn/src/compaction.rs:1825-1858`,
`:867-875` (`MIN_SUMMARY_ROOM`, `WRITE_ROOM`, `CUT_MARGIN`), `:102-132` (`summary_budget`).

```text
crates/harnessd/src/harness/wall.rs:1094-1103
                // The room a fold's verbatim tail may spend: the number `plan_fold` plans against
                // itself, halved where the smaller-tail fold halves its budget.
                let fold_room = {
                    let room = window
                        .saturating_sub(prefix_tokens)
                        .saturating_sub(self.cfg.headroom());
                    if smaller { room / 2 } else { room }
                };
```

The premise is not what `plan_fold` computes. It splits at `total / 2` and bounds the second
half by its own reserve, never by `headroom`:

```text
crates/turn/src/compaction.rs:1845-1852
    let half = total / 2;
    …
    if prefix_tokens + first + WRITE_ROOM > window
        || prefix_tokens + second + WRITE_ROOM + CUT_MARGIN > window
    {
        return None;
    }
```

so the plan's bound on the whole verbatim tail is `window - prefix - 24 576` (`WRITE_ROOM`
16 384 + `CUT_MARGIN` 8 192, `:872-875`), while `fold_room` is `window - prefix - headroom` with
`headroom = clamp(window/16, 2 048, window/4)` (`config.rs:1103-1105`, `:1178-1183`). And `keep`
treats `room` as the budget for the region it returns — `free = room - kept` where `kept` is the
whole tail (`compaction_relevance.rs:79-83`).

The two numbers cross at `headroom = 24 576`, i.e. a window of 393 216 tokens. **Below that — which
is every default window this box runs — `fold_room` is the larger**, by `24 576 - headroom`: 12 076
tokens at a 200 000-token window, 22 528 at 32 768. `keep` may therefore grow the tail past what the
plan left, and the reserve it eats is the record's: `summary_budget` gives the record
`window - resident - ASK_ROOM` (`compaction.rs:196-201`), which at the wall is about
`headroom - 2 000`.

**Scenario.** A 200 000-token session at the wall with the second tier on and enough old exchanges
scoring above `FLOOR`: `plan_fold` leaves about 10 000 tokens of slack against
`resident + headroom >= window` (`wall.rs:1868-1872`), and `keep` may spend 12 076 of it. The fork
then builds `summary ++ tail` with `resident ≈ window - 2 000`, so the very next round is at the
wall again, and `keep` is deterministic and the items unchanged by being summarised — the same
exchanges are pulled again. Every turn pays a summary and a round and the history does not shrink.
The arithmetic is derived from the constants above, not observed in a run; the damage needs the tail
to reach its budget.

**Smallest fix.** Take the record's reserve out of the same number, e.g.
`room.saturating_sub(self.cfg.headroom().max(WRITE_ROOM + CUT_MARGIN))`, or pass
`summary_budget(..).tokens` as the record's cost — restoring `prefix + tail + record + headroom <= window`.

`later_turn`'s other two acts are missing: `slot.settle`/`slot.spoke_again` (which populates

## 7. MEDIUM — a later turn's settlement rewrites the record's `outcome` and clears `later_answer`, so a failed later turn becomes the child's verdict after a restart

`crates/harnessd/src/harness/children.rs:282-287` and `:1134`; `crates/harnessd/src/subagent_record.rs:233-262`;
`crates/tokencore/src/store/subagents.rs:194-203`.

`TaskSlot::settle` writes the record on **every** settlement, a later turn's included, and the row
write is an overwrite that also drops the later answer:

```text
crates/tokencore/src/store/subagents.rs:200-203
            "UPDATE subagent_run SET state = ?2, outcome = ?3, later_answer = NULL,
                    delivered = 0, updated_ms = ?4
              WHERE child_id = ?1",
```

**Scenario.** `C` answers its task (`state=done`, `outcome=answer #1`). `P` messages it; that later
turn fails. `later_turn` → `slot.settle(Failed)` → `record.settled` → the row becomes
`state=failed`, `outcome=<the later error>`, `later_answer=NULL`. `spoke_again` is skipped on a
failure, so `later_answer` is never put back. Restart: `decide`/`recorded_status` hand `P`
`TaskStatus::Failed` and answer #1 is gone from the row. On a *successful* later turn the ordering
(`settle` then `answered_again`) leaves `outcome` holding the later answer, so
`latest_answer`'s doc — "`outcome` keeps the first either way, so a reader that wants it has it"
(`subagent_record.rs:474-476`) — is false, and a daemon that dies between the two writes hands the
parent a later turn with no "a later turn of this child" prefix.

after the first; `later_turn_began`/`later_turn_ended` already bracket the turn and
`answered_again` already writes the later answer.

## 8. MEDIUM — a snapshot does not say where the base starts, so a head's ordinals drift by the rows above it

`crates/sessionlog/src/view.rs:227-237` (`Snapshot`), `:672-686` (the fork arm), `:824-833`
(`lead`), `:837-845` (`row_at`); `crates/tui/src/app/events/mod.rs:228-234`.

`8a44d5b5` keeps the rows a resume republishes above the base and numbers the base past them
(`row_at` is `row - items_dropped + lead`), which is right. But the offset it keeps is private to
the view, and the snapshot carries only the other half:

```text
crates/sessionlog/src/view.rs:236-237
    pub items_dropped: u64,
    pub items: Vec<SnapshotItem>,
```

so the head has to guess, and says so:

```text
crates/tui/src/app/events/mod.rs:231-234
        // A snapshot does not say which of its rows are above the base - a resume's republished
        // ancestors and the base's own rows arrive as one list - so the head takes them all as the
        // base's until a fork tells it otherwise.
        self.items_lead = 0;
```

**Scenario.** A session is compacted (`s#t0` → `s#t1`) and the daemon restarts; the resume
republishes the chain's tail, so the view holds `[5 rows of s#t0, rows of s#t1]` with
`items_dropped = 0` — exactly the fixture `a_fork_leaves_the_rows_of_the_transcripts_it_did_not_replace`
asserts (`25` rows, `items_dropped == 0`, and `row_at(0) == Some("s#t3.0")`, the sixth row). A head
attaches or resyncs there: `items_base = 0` and `items_lead = 0`, so it believes its first row is
ordinal 0 while the daemon calls that row ordinal 5. Its window then trims
(`items_base += n - items_lead` = `n`, where the daemon's own trim adds `n - 5`), and every page it
asks for above the window is answered `5` rows further into the base than it thinks: the page
repeats rows the head already holds and the rows between are never drawn. Nothing announces the
drift, and it lasts until the next fork.

**Smallest fix.** Publish the lead — `Snapshot { #[serde(default)] items_lead: usize, .. }`, zero
for a daemon that has none, so no protocol number moves — and have the head take `s.items_lead`
where it now writes `0` (and derive it on its own `rows_replaced`, as it already does).

## 10. LOW — a settlement hops one level, and the watcher's push path does not hop at all

`crates/harnessd/src/jobwatch.rs:261-281` (`Up`, `route`), `:912-946` (`stop`), `:1079-1099`


**Scenario.** The head asks; the reader thread reads the rows (old) and is descheduled before
`writer.lock()`; the harness calls `set_settings` with new rows, `push_frame` queues them and
`notify_all`s; the pump takes the writer lock first and writes the new rows, then the reader writes
the old ones. The head applies the answer last and keeps the old rows until the next change. The
window is the gap between the registry read and the writer lock — real but narrow.

**Smallest fix.** Read the rows inside the `writer.lock()` that writes them (or send the answer
through `push_frame_to`, so it is ordered with the pushes).

## 12. LOW — a batch put back after a refused door is never rung for again

`crates/harnessd/src/harness/deliveries.rs:718-722` → `crates/harnessd/src/jobwatch.rs:746-753`;
`crates/harnessd/src/harness/turns.rs:1195`, `:223-225`; `crates/sessionlog/src/hub.rs:824-827`.

```text
crates/harnessd/src/harness/deliveries.rs:718-722
    pub(crate) fn put_back(&self, untold: Vec<JobCompletion>) {
        if !untold.is_empty() {
            self.watch.hold(untold);
        }
    }
```

`hold` extends the held set and calls `say_held()`; it does not ring the bell. The ring was already
spent: `submit_items_then` calls `begin_turn_clock` before appending, and that calls
`w.turn_began()`, clearing `settlement_in_flight`. And a held result alone is not
`work_pending()` — that is `!commands.is_empty() || own_wake`.

**Scenario.** A door's append or persist is refused, so the batch is put back. The session then
reads `waiting on: delivery` but nothing is scheduled to say it: the court sits in
`take_own_work_until` until an unrelated prompt, a monitor firing or a due row. The row is owed, not
lost — the state `a_settlement_a_refused_door_never_said_is_still_owed` deliberately constructs.

**Smallest fix.** Ring on the same bell in `the_batch_arrived`'s `else` arm (or in `put_back`).

## 13. LOW — a failed child's survivors are handed to the parent before the tree they run in is reaped

`crates/harnessd/src/harness/children.rs:3528-3540` and `:364-370`; `crates/harnessd/src/mergequeue/git.rs:1096-1107`.

On the first-turn-failure path the estate is settled first (`sub.settle_estate(heir.as_deref())`,
a `letibot_tools::exec::hand_over` of the child's `explicit`-scope processes to the parent), and
`return Err(...)` then reaches `finish_child_thread`'s `reap_failed`. A handed-over process whose cwd
is inside the tree keeps running with a removed directory: its next relative write fails. Code-path
reading only — not observed, and a dirty tree is kept by `remove_worktree`, which narrows it.

**Smallest fix.** Reap before the hand-over, or hand over the child's `cwd` as part of the estate.

* **The extraction series is behaviour-preserving.** `open_with_registry`'s four steps
  (`43f26515`, `2b0701a2`, `3ce469cf`, `592241c4`) and `run_to_completion`'s (`c86e6f44`) were
  checked by extracting the old body and the new step bodies, stripping indentation and diffing the
  statement sequence. `open.rs` differs in four places only — `dialect_sha.clone()` →

  fresh-session arm, and the `notes` initialiser moving into `open_the_stored` — none of which moves
  a side effect. `children.rs`'s `seat_the_child` is byte-identical under `self.base` → `base`,
  `sub_cfg` → `cfg`, in the original order.
* **`ends_turn` and the activity are consistent.** A round's `TurnFinished{ends_turn:false}`
  (`harness/turns.rs:1820`) is closed either by the loop's `finish(false)`/`finish(true)` or by
  `end_turn_clock`'s `publish_activity` after `prompt_in_flight` is cleared (`turns.rs:259-272`),
  and the head treats a quiet `ActivityChanged` as the ending (`crates/tui/src/app/events/turn.rs:39-43`)
  — so the two exits at `turns.rs:1810` and `:1840` do not leave a head stuck on `Responding`.
  A `CapturingSink` dropped with a held ending is covered by `publish_failure`'s `TurnFailed`.
* **The `rounds` split preserved its loop.** `7aa68541`, `60a3af8a`, `8e3b3a9a`, `8767a6f6` were
  read against the pre-split body: the three exits (`finish(false)` + return, `finish(true)` +
  continue, `finish(true)` then the backgrounded return at `:1840`) are the same, `nudges_left` is
  still one `&mut usize` per turn decremented at both sites, and `after_the_round` builds the same
  non-holding `CapturingSink` the inline block did. `harness.rs` lost no function across the window.
* **The peer gate is coherent on Linux.** `Peer::of` is read before the stream is moved
  (`server.rs:480-482`), the refusal arm is first in the loop and before every door (`:546-573`),
